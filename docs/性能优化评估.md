## 〇、一句话结论

卡顿的原因**不是"屏幕上显示了一张大图"**，而是**每画一笔就把整张画布的所有图层重新合成一遍**。

实测（本机，3840×2160 / 3 图层）：**每次鼠标移动要 431 ms**（≈2.3 fps）；
6000×4000 / 3 图层要 **1256 ms**（0.8 fps）。

解法不是"编辑缩略图"，而是**只重算被改动的那一小块**。同一个笔尖，实测 **0.25 ms**
—— 快 **约 1700 倍**，而且**逐位精确、零质量损失**。

## 一、根因（已定位到函数）

### 1.1 每帧的调用链（改造前）

```
鼠标移动
 └─ CanvasView::mouseMoveEvent
     └─ BrushTool::mouseMove
         ├─ paintSegment()          ← 只算脏矩形，很快
         ├─ applyRegion()           ← 只写脏矩形，很快
         └─ Document::markDirty()   ★★★ 整画布失效 ★★★
             ├─ m_compositeValid     = false
             ├─ m_contentBoundsValid = false
             └─ emit contentChanged()
                 └─ CanvasView::onDocumentContentChanged → update()
 └─ CanvasView::paintEvent
     └─ drawComposite()
         └─ Document::composite()   ★★★ 整画布全图层重算 ★★★
             └─ blend::compositeLayers()
                 └─ 每层：base.copy() + 全画布逐像素 blend
```

（行号随各批次演进会漂移，故只记函数名。）

★ **画笔本身是全项目最干净的实现**（只算脏矩形、只写脏矩形、整笔压一条命令）。
瓶颈**完全**在于它把"我只动了这一小块"这条信息**丢掉了** —— 只对下游说了一句"整张图都脏了"。

### 1.2 当初设计的前提已被实测推翻

`Document.h` 原先的注释写着：

> 缓存的失效粒度是"整个画布"。更精细的做法是脏矩形，但标准版的画布尺寸通常在几百万像素量级，
> **一次合成为 10~30ms**，配合下面的降采样策略已经够用。

实测（AMD Ryzen 7 4800H / 8 核 16 线程 / MSVC `/O2` / Release）：

| 画布 | 图层数 | 一次全画布合成 | 等效帧率 | ns / 像素 |
| --- | --- | --- | --- | --- |
| 1920×1080 | 1 | 36.8 ms | 27 fps | 17.8 |
| 1920×1080 | 3 | **108.3 ms** | 9 fps | 52.2 |
| 1920×1080 | 5 | 179.0 ms | 5.6 fps | 86.3 |
| 3840×2160 | 1 | 146.3 ms | 6.8 fps | 17.6 |
| 3840×2160 | 3 | **430.9 ms** | **2.3 fps** | 51.9 |
| 3840×2160 | 5 | 707.1 ms | 1.4 fps | 85.3 |
| 6000×4000 | 1 | 425.1 ms | 2.4 fps | 17.7 |
| 6000×4000 | 3 | **1256.0 ms** | **0.8 fps** | 52.3 |
| 6000×4000 | 5 | 2112.8 ms | 0.5 fps | 88.0 |
| 8000×6000 | 1 | 856.8 ms | 1.2 fps | 17.9 |
| 8000×6000 | 3 | 2494.8 ms | 0.4 fps | 52.0 |
| 8000×6000 | 5 | **4134.4 ms** | **0.24 fps** | 86.1 |

→ 实际是 **146 ~ 4134 ms**，比注释里的假设慢了 **5 ~ 140 倍**。

注释里的"几百万像素"大概是按 2000×1500 量级估的；而今天一张 24MP 相机照片（6000×4000）
就是 **2400 万像素**，正好落在最坏的几行上。**设计前提过期了，不是实现写错了。**

★ 该注释**已在批次一改正**（`Document.h` 头部现在记的是实测数据与"局部为主、全量为兜底"的模型）。

### 1.3 第二处"整块重算"：选区轮廓（已解决）

改造前 `CanvasView::onDocumentContentChanged()` **无条件**调用 `invalidateSelectionOutline()`
→ 下一帧重扫整个 `selection.bounds()`。**有选区时，每个画笔事件都要重建一次选区轮廓。**

**先量后决（批次二第 2 步）**：4000×3000 活动蒙版整张扫描 **约 0.4 ~ 0.5 s**
（多次实测 411 / 440 / 480 / 525 ms），只扫 200×200 包围盒 **1 ms**。
当初代码推断的 20~60 ms **低了 7~20 倍** —— 它和"一次全图合成"同量级，比预想的更值得除掉。
（该组断言在 `tests/perf_test.cpp` ⑧·成本，每次全量都会打印当前值。）

**结论：不拆信号**（`contentChanged` 签名不动、不改 3 处 `connect`、不动 2 个测试文件），
改用**修订号门控**：`CanvasView` 按 `(selection.revision(), canvasSize)` 判断"该不该重建"，
而不是"有没有像素脏"。详见 `实现铁律.md` §20.12。

## 二、方案 A：脏矩形增量合成【已采用】

### 2.1 目标与正确性基石

把每帧合成成本从 `O(画布面积 × 图层数)` 降到 `O(改动面积 × 图层数)`。

**为什么可以只算一小块而结果完全一样**：本项目 22 种混合模式**全部是逐像素（pointwise）运算** ——
每个输出像素只依赖**相同坐标**的输入像素，没有任何空间邻域运算（无模糊、无位移、无卷积）。

因此：**"某矩形内独立合成的结果" 与 "全图合成结果的对应子区域" 逐位相等。**

★ 这条是本方案的**正确性基石**，也是它的**适用范围**：哪天有人加了一个需要邻居像素的
混合模式（例如"移动平均"），本方案立刻失效。`tests/perf_test.cpp` ① 组把
"22 种模式 × 9 个矩形**逐位相等、容差 0**"钉死，加模式时会红。

★ **容差必须是 0**，不能是"误差 ≤ 1" —— 见 §4.1 的说明。

### 2.2 实测收益（与 §1.2 同一台机器）

对比"全画布合成"与"只合成笔尖脏矩形（所有图层都算）"：

| 画布 | 图层 | 笔尖 64 px | 笔尖 200 px |
| --- | --- | --- | --- |
| 1920×1080 | 3 | 0.248 ms（441×） | 1.135 ms（97×） |
| 3840×2160 | 3 | 0.248 ms（**1739×**） | 2.132 ms（202×） |
| 3840×2160 | 5 | 0.427 ms（**1670×**） | 3.742 ms（190×） |
| 6000×4000 | 3 | 0.247 ms（**5107×**） | 2.111 ms（599×） |
| 8000×6000 | 5 | 0.413 ms（**10011×**） | 3.584 ms（1149×） |

→ 4K / 3 层：**431 ms → 0.25 ms**。这就是"幻灯片"和"流畅"的差别。

### 2.3 失效规则表 ★ 最容易漏的地方，必须穷举

| 操作 | 应调用 | 粒度 |
| --- | --- | --- |
| 画笔 / 橡皮 / 形状 / 文字 / 油漆桶 写像素 | `markDirtyRegion(脏矩形)` | 局部 |
| 移动图层（拖拽中） | `markDirtyRegion(上帧 ∪ 本帧包围盒)` | 局部 |
| 图层不透明度 / 混合模式 / 可见性 / 顺序 / 增删 | `markDirty()` | **全图** |
| 画布尺寸变化 / 缩放 / 旋转 / 裁剪 | `markDirty()` | **全图** |
| 选区变化 | 像素合成其实不受影响，只需让**轮廓**失效 | 见 §1.3 |
| 撤销 / 重做 | 命令能给出区域 → `markDirtyRegion`；拿不准 → `markDirty()` | 视命令 |
| 打开文件 / 拼合图像 / 合并图层 | `markDirty()` | **全图** |

★ **纪律**：无参版 `markDirty()` **永久保留**。任何"我不确定这次改了什么"的地方一律调它。
**局部失效是快路径，全量失效是正确性保证** —— 二者并存，风险才可控。

★ 特别注意"移动图层"这一行：**上帧位置也要脏**。只脏本帧会在画面上留下一条"残影"，
而且这个残影只在拖动过程中可见、松手后消失 —— 极难复现，必须靠自检抓（§2.5 植入第 2 条）。

### 2.4 三条定案

1. **两条路径必须共用同一个内核**。`compositeLayers()`（全图版）**转发**给
   `compositeLayersRegion()` —— 不允许出现第二份合成实现，否则"预览与实际不一致"
   这类 bug 迟早出现（本项目在蚂蚁线、画笔/形状写回上都吃过"两份实现漂移"的亏）。
2. **`IRegionAware` 是可选的，不实现 = 自动退回全量**。`CommandStack` 用 `dynamic_cast` 探；
   拿不准的命令什么都不用做，天然正确。
3. **不拆 `contentChanged` 信号**（§1.3 的结论），轮廓重建改用**修订号门控**。

### 2.5 必须配套的自检（写代码时一起写）

1. **正确性基石**：小画布（如 64×64、3 图层、随机像素），
   对比 `compositeLayers(全图)` 与 `compositeLayersRegion(region)` 在 `region` 内的结果：
   **逐位相等（容差 0）**。**22 种混合模式每种都跑一遍**（4 种分量模式尤其不能漏）。
2. **累积正确性**：连续 `markDirtyRegion(r1)` + `markDirtyRegion(r2)` → 结果 == 全量重算结果。
3. **兜底正确性**：`markDirtyRegion(r)` 后紧跟 `markDirty()` → 必须走整图重算（不能被局部路径吃掉）。
4. **遥测计数**：`fullCompositeCount()` / `regionCompositeCount()` ——
   **这是唯一能证明"真的走了快路径"的手段**，且**必须在真实调用链上驱动**（见 §3.3）。
5. **量它画出的像素**：不要只断言"函数返回非空"。加一条"**脏矩形外一圈的像素与改动前完全相同**"
   的断言 —— 这是抓"脏矩形算大了 / 算小了"最直接的判据。
6. **植入验证**（本项目纪律，先植入 bug 证明断言抓得住）：
   - 植入"图层不透明度改变时仍走局部路径" → 断言必须抓住
   - 植入"移动图层只脏本帧、漏掉上帧" → 断言必须抓住（残影）
   - 植入"脏矩形不与画布求交" → 断言必须抓住（越界写入）

### 2.6 风险

**中等。** 核心风险是"漏失效" → 画面残留旧内容（**不会崩溃，症状隐蔽**）。
缓解手段：兜底路径 + §2.5 植入验证 + **分两批接入**（先画笔/橡皮，再形状/移动/油漆桶）。

### 3.3 ★★ 批次一的漏网之鱼：一次真实的假绿 ★★

**这是本项优化里最值得记的一件事。**

批次一的自检（`perf` 637 项、5 条植入）**全部通过**，文档也据此写下"画笔已接入区域失效"。
但真实情况是：`BrushTool::applyRegion()` 收尾那句依旧是 `document()->markDirty()`
→ 拖动期间**每一帧整张画布重合成**。也就是说 **4K 画笔的卡顿（本评估的原始动机）一点没改善**。

**为什么全绿还是漏了**：

| 假象 | 真相 |
| --- | --- |
| 像素断言全对 | 工具确实只重算了 `region`，结果也正确 —— 断言没问题，只是不覆盖"失效范围" |
| "取消要还原"全对 | 与失效范围无关 |
| 两个构建 0 错 0 警 | 类型正确 |
| `perf` ⑤ 组"连续 20 次局部失效无全图重算" | ★ 那是**直接调 `Document::markDirtyRegion()`**，从没经过 `BrushTool` ★ |

→ **遥测计数只有接到真实调用链上才有价值。** 只断言 `Document::markDirtyRegion()` 的行为，
等于在测"我自己的测试"。

**修复**：`document()->markDirtyRegion(region);`（`region` 就是本帧写过的范围；
其余像素保留前几帧写入的正确值 —— `composeStroke` 是幂等的）。

**补的两条防线**（这是批次二真正的产出）：

1. `tests/brush_tool_test.cpp`（新短名 `brushtool`）—— **驱动真实 `BrushTool`**，
   断言"拖动 6 帧后 `fullCompositeCount()` 增量为 0"。
2. `tests/move_tool_test.cpp`（新短名 `movetool`）—— 同理管移动，
   外加"残影"的像素级取样。

★ 顺带发现：`brush`（engine）与 `brushtool`（tools）是**两件事**。
批次一只有前者，所以这个缺陷能藏整整一个批次。★

（更完整的复盘见 `实现铁律.md` §20.14。）

## 四、后续可选方向

### 4.1 方案 B：内层循环提速（倒数查表）——【已侦察，判定不做】

**依据**：§2.2 另一笔实测 —— **Multiply 模式与 Normal 模式耗时相同（0.99×）**。
换一个复杂得多的混合公式耗时完全不变，说明时间**不在混合公式里**，
而在它前面那段公共代码 —— "提取分量 / 还原非预乘"的**除法**。

**侦察方法**（探针 `.buildlog/probe_div.cpp`，可重跑）：把 `compositeLayer()` 的内层循环
**逐字拷贝**成 6 个变体，彼此只差"反归一化"那几行；先验证逐字拷贝 ≈ 真实函数，再看比值。
机器同上（Ryzen 7 4800H / MSVC `/O2` / Release），1920×1080 单层，取 3 次最快值。

| 变体 | 做法 | 相对逐字拷贝 | 相对现有真实函数 | 逐位相同？ |
| --- | --- | --- | --- | --- |
| 逐字拷贝 | 基线 | 1.00× | 0.84×（差在 mode 分派，见下） | ✅ |
| **B″** | 只表化 `/255.0`（2 KB） | 0.96× | **1.04×** | ✅ |
| **B′** | 整表 `T[a][v]=v/a`（512 KB） | **0.76×** | **约 1.26×** | ✅ |
| **B** | `kInv[a]=1.0/a`（2 KB） | 0.79× | 约 1.22× | ❌ 口径风险 |
| 天花板 | 除法全部换成乘法（不可用，仅测上界） | 0.79× | 约 1.24× | — |

★ **B′ 已经摸到天花板**（0.76× vs 0.79×）—— 再往下压没有空间；
★ **B″ 只有 4%**，可以忽略；★ 反直觉的是**随机 alpha 也打不垮 512 KB 表**
（同像素 3 次查表落在同一行，逐像素换行仍有 1.21×），原先"表被缓存击穿"的担心不成立。

**判定：不做。** 三条理由，按权重排：

1. **天花板只有 1.26×，且只作用冷路径。** 方案 A 已把热路径从 431 ms 压到 0.25 ms，
   B 于是在热路径上**价值归零**；剩下的打开文件 / 拼合 / 合并这些一次性操作，
   用户感知远低于"每帧卡顿"。
2. **代价不划算。** 唯一能摸到天花板的零口径变更形态 B′ 要 **512 KB 常驻表**，
   还要处理 `a==0` 的 256 个空位；B（2 KB）虽小，但它改变舍入 ——
   而它影响的正是 `adjust_test.cpp` 那批"专抓 alpha 细微错误"的精确断言。
   另外同构代码在 `Adjust.cpp`，验证面还要扩到调整类。
3. ★ **收益与 §4.5 高度重叠，且被全面压过。** B′ 赚得最多的场景（全不透明照片）
   恰恰是 §4.5 的 **7.8 ~ 9.4×**；而 B′ 的独占收益在半透明场景（只有 1.26×），
   那里正好是 alpha 边缘最敏感、最不该动内核的地方。

**顺带量到的两件事**（未做，记下来免得后人重测）：

- **混合模式的 switch 分派本身占 9 ~ 13%**（变体 V6 对 V0）。理论上"按模式特化循环"
  能拿回这部分，但要写 22 份代码，不值。
- 真实函数比"逐字拷贝 + 内联分派"还慢约 2 ~ 3 ms，差价在 `isComponentMode()` 的判断
  与 `blendChannel()` 可能未内联。同样不作为。


### 4.2 方案 C：呈现缓存

**现状**：每帧 `drawImage` 带 `SmoothPixmapTransform`，把整图（的可见部分）缩到屏幕。
实测成本：4K 2.9 ms / 8000×6000 14.8 ms（占 4K 一次合成的 **0.7%**）。

**做法**：在"视图变换或画布尺寸变化"时，把 `composite` 一次性缩放到**按当前缩放比最接近的 1/2ⁿ 层**；
之后绘制直接 1:1 贴图（放大 > 100% 时用"裁剪 + 1:1"，完全避免重采样）。

**收益**：每帧省 2~15 ms。**但有一个关键限制**：

★ 如果内容**每帧都变**（画笔拖动），呈现缓存也要每帧重建 —— 那等于**倒贴**一次 `scaled()`。
所以：

- **单独做 C**：只有"内容不变"的场景（平移、缩放、蚂蚁线动画、拖参考线）受益，**收益小**
- **A + C 配合才是完整方案**：A 让内容变化只脏一小块 → C 只需重建对应小块 → 两处同时受益

**结论：优先级低于 A。建议等 B 收口后再评估是否值得做。**

### 4.3 方案 E：瓦片化 + 多分辨率金字塔

把图层拆成 256²/512² 瓦片，只为可见瓦片分配内存与合成。适合 **>1 亿像素**的超大幅面。
工作量是方案 A 的数十倍，**当前不需要**。
但方案 A 的"脏矩形"机制是它天然的前置 —— 做了 A 之后，E 才有可选的余地。

★ 注意形态：超大幅面要的是**瓦片 + 金字塔**，不是"编辑缩略图"。

### 4.4 次要项

- **蚂蚁线定时器 120 ms**（`CanvasView`）在画笔拖动期间也会触发，每帧多一次重绘。
  原本可接受；但批次一把"每帧重画整个视口"改成 `update(rect)` 之后，
  它的**相对占比会上升**，值得再看一眼。

### 4.5 ★ 不透明上层直接覆盖【已采用】★

**来源**：做 §4.1 的侦察时顺手量的一个变体，结果比 B 好一个数量级。

**依据**：`compositeLayer()` 里，当 `qAlpha(src) == 255` 且 `layerAlpha == 1.0` 时，

- `sa = 255/255.0 = 1.0`（精确） → `effAlpha = 1.0`（精确）
- 于是 `1.0 - effAlpha == 0.0`（精确），`mixR = br*1.0 + dr*da*0.0 == br`（精确，第二项恒为 0）
- 而 Normal 模式下 `br = sr`，`sr` 反归一化再乘 255 取整**逐值还原**（256 个值穷举验证，0 例外）
- `outA = da + 1.0*(1.0-da)` 取整后恒为 255（256 个 alpha 穷举验证，0 例外）

→ **整条 source-over 退化成"把 src 直接写进 dst"**，且**逐位相同**。

**实测（同一探针、同一台机器、1920×1080 单层）**：

| 场景 | 改动前 | 快路径 | 加速 | 逐位相同 |
| --- | --- | --- | --- | --- |
| 全不透明上层（两层照片合并） | 35.9 ms | **4.6 ms** | **7.8×** | ✅ 0/2073600 像素差异 |
| 透明画布 + 照片（"打开为图层"） | 35.5 ms | **3.8 ms** | **9.4×** | ✅ 逐位相同 |
| 半透明 / 随机 alpha（画笔、文字、形状层） | 35.6 ms | 31.2 ms | 无收益 | ✅（不触发即不改变行为） |

**代价**：**3 行代码、零查表、零口径变更**（不需要改任何像素断言）。
它天然是"快路径 + 兜底"形态：不满足条件就原样走老路，慢路径一个字都没动 ——
写错了也只是"少走快路"，不会算错结果。

**为什么它比 B 更值得做**：B 的 1.26× 覆盖不到的场景它不做；而它覆盖的场景（真实照片）
正是用户最初报的那个痛点 —— 24 MP 照片导入成图层、两层照片合并。
按 §1.2 的数据换算：24 MP 单层合成 425 ms → **约 46 ms**；4K×3 层 431 ms → **约 50 ms**。

#### 4.5.1 实现（2026-09-22 落地）

落在 `src/engine/Blend.cpp` 的 `compositeLayer()`，三处改动：

| # | 位置 | 内容 |
| --- | --- | --- |
| 1 | 循环外 | 门槛 `opaqueCoverAllowed = mode ∈ {Normal, Dissolve} && layerAlpha >= 1.0` |
| 2 | 逐像素循环开头 | `if (opaqueCoverAllowed && qAlpha(src) == 255) { dstLine[x] = src; ++fastPixels; continue; }` |
| 3 | 函数出口 | 可选诊断输出 `fastPixelsOut`（默认 `nullptr`） |

★ **门必须带全**：只有"上层分量原样通过"的模式才成立 —— 其他模式的 `br` 不等于 `sr`，
覆盖会算错。探针的基准只跑了 Normal，这个门是从推导里得出来的。
`Dissolve` 目前在 `blendChannel()` 里也走 `blendNormal`，故二者都在列；
**将来若真实现"溶解"（随机抖动），必须同时把它从这两处拿掉** ——
`perf_test.cpp` 11.1 那条"由 `blendChannel` 反推候选集"的断言就是为这个雷埋的。

★ **判据在像素上，不是"整层"**：一张照片上叠了不透明笔迹时，笔迹那部分走快路、
柔边那部分照旧走慢路。**这正是收益能覆盖热路径的原因** ——
"在照片上画画"时，笔迹像素（不透明底上做 source-over）始终是不透明的。

★ **`fastPixelsOut` 只为自检存在**，且**按层累加**（两层不透明照片 → 2 × 像素数）。
理由：快路径产物与慢路径逐位相同 → **"结果对"根本证明不了它生效**，只能靠计数。
产品代码一律不传。

#### 4.5.2 自检（`perf` 第 ⑪ 组）

判据必须**同时**满足两条，缺一条都证明不了：

| 判据 | 抓什么 | 只有它会怎样 |
| --- | --- | --- |
| **逐位相同**（0 容差，结果与上层图逐位相等） | 快路径**算错** | 慢路径也算得对 → 说明不了快路径生效 |
| **命中计数吻合** | 门**写松 / 写紧** | 说明不了没写错 |

覆盖：11.1 候选集由 `blendChannel` 反推｜11.2 22 模式逐个（候选全命中且逐位等于上层；
非候选**一个像素都不许命中**）｜11.3 `opacity < 1` 时门必须关｜11.4 混合层只数不透明那半｜
11.5 经 `compositeLayersRegion` / `compositeLayers` **真实入口**驱动｜
11.6 区域路径只数被重算的那块｜11.7 上层小于画布时的边界。

★ 已用 **7 条植入**（`.buildlog/implant_blendfast.py`）证明这些断言抓得住：
Q 门漏模式 / R 门漏不透明度 / S 判据错成"整层"（**白优化方向**）/ T 判据放宽成 `>0` /
U 不计数 / V 覆盖时保留下层 alpha / W 计数漏了累加。

★ **写测试时踩的两个坑**（注释留在 `perf_test.cpp` 里，别删）：
1. 候选集判据不能只在**一个** `(base, blend)` 采样点上比较 —— "变亮"与"线性光"在那一点上
   碰巧恒等，候选集从 2 个虚增到 8 个。"在一点上取到同一个值" ≠ "恒等映射"。
2. `fastPixelsOut` 是按层累加的：两层不透明照片给出 2 × 像素数，不是算重了。

#### 4.5.3 边界

- 图层里只要**有一部分**像素不透明，那部分就受益；不是"整层被否决"。
- 半透明像素仍走慢路径，行为与改动前完全一致（实测 31.2 ms vs 35.6 ms：只多一次判断）。
