# 实现要点详解

> 逐项讲解"为什么这么写"：调整预览机制、选区、图层面板、跨图导入、导出 ICO、画笔撤销策略。
> 强制约束（会静默失效的那些）见 [实现铁律.md](实现铁律.md)。

## 调整对话框的预览机制

拖动参数时要"立刻看到结果"，最直接的写法是每帧都对整层重算一遍 ——
4000×3000 是 1200 万像素，一次 LUT 变换加格式转换要几十到上百毫秒，
滑块会明显滞后（手感像在拖一个卡住的控件）。

这里采用的方案是**降采样预览 + 临时呈现图**：

| 环节 | 做法 |
| --- | --- |
| 预览基准图 | 打开对话框时把图层缩到最长边 **1024**（约 100 万像素），只做一次 |
| 每帧运算 | `对话框->apply(预览基准图)`，约 6~10ms，落进 60fps 的预算内 |
| 显示 | 交给 `CanvasView::setPreviewImage()`，绘制时按尺寸比拉伸回整幅画布 |
| 文档 | **完全不碰** —— 预览只活在呈现层，不进 `Document` |
| 确定 | 用同一个 `apply()` 作用在**全尺寸原图**上，再压一条 `ImageCommand` |
| 取消 | 只需 `clearPreviewImage()`，不需要任何"还原"逻辑 |

这套设计有两个不太显眼但很关键的收益：

1. **预览与结果不可能不一致**。因为 `apply()` 是对话框的一个纯函数
   （`QImage + 参数 → QImage`），预览和提交调的是同一份代码，区别只有
   输入图的大小。如果预览走一条路径、提交走另一条，两者迟早分叉。
2. **"取消"天然免费**。文档从打开到关闭都没被改过，因此不存在
   "还原得不干净、用户带着假中间结果保存文件"的风险。这与选区工具
   "拖动期间不碰 Document"是同一个思路。

> 预览**也要按选区混合**。否则会出现"预览里整幅图都变了、确定后只有
> 选区内变"——这正是第 1 条要防的不一致。为此把混合逻辑从
> `blendWithSelection()` 里拆出了一个吃"蒙版 + 范围"的
> `blendByMask()`：预览用的是缩到预览尺寸的蒙版，最终提交用的是原始
> 蒙版，但走的是同一段代码。

**代价**：放大到 400% 以上看时，预览会比最终结果略糊（它本来就是一张
被放大的缩略图）。调色时用户看的是整体明暗与色彩倾向，这个代价换来的
跟手程度是值得的 —— 点确定后会立刻换成全尺寸运算的真实结果。

## 选区工具的两个设计要点

### 1. 拖动期间不碰 Document

画笔是"拖动即写位图"的所见即所得模式，但选区**不能**照抄这条路：

- **撤销栈会被刷屏**：每次 `mouseMove` 都真的更新选区蒙版，就要为每一次
  移动构造一条撤销命令。用户拖一下鼠标，撤销栈里躺着上百条记录，
  按 `Ctrl+Z` 要按到手酸。
- **算不过来**：选区蒙版是画布尺寸的（4000×3000 就是 12MB），
  一次布尔运算要遍历 1200 万像素。鼠标每秒发 60~120 次移动事件。

所以实现是"轻量预览 + 收尾一次性提交"：拖动期间只维护一个
`m_previewRect` 并由 `paintOverlay` 画虚线框，**完全不产生任何数据结构**；
松手时才渲蒙版、羽化、做布尔运算，然后包成**一条** `SelectionCommand`。

附带的好处：**按 Esc 取消是免费的** —— 整个拖动过程没改过文档，
所以"取消"就是把预览矩形丢掉，不需要任何回滚逻辑。

修饰键按 Photoshop 的约定分两个阶段解释：**按下瞬间**的 Shift/Alt 决定
运算方式（添加/减去/交集），**拖动过程中**的 Shift/Alt 决定几何约束
（正方形/以起点为中心）。同一组键分两阶段是因为"想画一个正方形"和
"想追加到选区"这两种意图只能靠"什么时候按的"来区分。

### 2. 蚂蚁线的绘制与性能

选区的边界蒙版是灰度图，要变成可描边的轮廓路径需要：
阈值化成 `QRegion` → `QPainterPath`。但 `QRegion` 的矩形是**逐扫描行的**，
直接 `addRegion()` 会把选区内部每一行的水平线都画出来（一片横条纹）。

所以实现改成**逐像素找"内/外交界"并把连续段合并成一条线段**（双向扫描，
横向找上下边界、纵向找左右边界）。合并成段还顺带解决了虚线的问题：
Qt 的虚线图案是**按子路径分别起算**的，如果每条子路径只有 1 像素长，
虚线会在每个像素处重新开始，画出来看着像实线，完全没有"蚂蚁"的效果。

三个性能决定：

- **轮廓路径必须缓存**。提取过程要对蒙版做多趟全图扫描，4000×3000
  要几十毫秒。而 `paintEvent` 是高频调用的，放在里面会让画布每次重绘
  都卡一下。选区只在用户松手时变化，缓存的性价比极高。
- **只扫描选区的包围盒**（`Selection::bounds()` 自带缓存）。包围盒之外
  全是未选中像素，那里的边界只可能是画布边缘，而画布边缘不需要画蚂蚁线。
  框一个小区域时扫描量能从"整张图"降到"那个小方块"。
- **动画定时器随选区开关**。动画意味着每 120ms 触发一次重绘，无条件常开
  会让用户完全没用选区时 CPU 也在空转。另外每帧**只重绘轮廓的外接矩形**
  而不是整块画布，框住一个小图标时重绘量能降两个数量级。

线条本身用 **cosmetic 画笔 + 关抗锯齿**，并且是**双层绘制**：先铺实心黑线，
再盖白色虚线。单色线在照片上必然有看不清的地方（白虚线在雪景上消失、
黑虚线在夜景上消失），黑白交替则任何底色都看得见。`paintOverlay` 里
正在拖出来的预览复用**同一个** `drawMarchingAnts()`，保证松手前后
线条风格完全一致。

## 图层面板的三个设计要点

### 1. 面板只读文档、只发信号 —— 撤销只有一条路径

`LayerPanel` 不允许修改 `Document` 的任何图层内容或元数据（唯一例外是
**活动图层索引**，它是纯 UI 状态、不进撤销栈）。用户点眼睛、拨滑块、拖拽排序，
面板都只是 `emit` 信号出去，由 `MainWindow` 把它包成**一条 `LayerCommand`**
压进 `QUndoStack`。这样换来三件事：

- **撤销/重做只有一条入口**，不可能出现"某个操作忘了压栈"或"压了两条"；
- 面板可以在**没有 `CommandStack` 的情况下单独构造** —— `layer_panel_test`
  正是靠这一点才能不链 `commands/` 就把它测了；
- 与裁剪工具（`CropTool` 只发 `cropRequested`）是同一条纪律的两次应用。

不透明度滑块单独做了区分：**拖动中只改内存、不压栈**（等同于其它对话框的
"实时预览"），**松手才压一条命令**。否则拖一次滑块会在撤销栈里塞几十条记录。

### 2. 视图行序 ⇄ 文档索引是倒序的

```
Document 索引 0  = 最**底**部图层
面板第 0 行      = 最**顶**部图层     →  row = count - 1 - index
```

这是面板里最容易写反的一处，而且写反了**不报错、不崩溃** ——
表现只是"「上移图层」在界面上看着往下走"。所以全工程只允许
`layerpanel::rowToLayerIndex()` / `layerIndexToRow()` 两个函数做这个换算，
并给它们配了互逆性断言。同族的还有拖拽落点：`QList::move(from, to)` 的 `to`
是"**取出 `from` 之后**"的坐标，源项原本在落点之上时插入位置要往前挪一位 ——
这条靠"纯函数算完之后**真的调一次 `Document::moveLayer`** 再对拍"来守。

### 3. 自绘的行：绘制与命中必须共用同一套矩形

行是用 `LayerItemDelegate` 自绘的，不是 `setItemWidget`。理由是后者会让项
**不能拖拽排序**（`QListWidget` 的 `InternalMove` 在拖动时销毁/重建项，
子控件随之丢失）。代价是"眼睛 / 锁点哪儿"要自己算，于是
`eyeRect()` / `lockRect()` / `nameRect()` 被抽成纯函数，**绘制与命中判定
共用同一套数字** —— 分两份写的话，改一个忘一个，症状是"眼睛画在这里、
点了没反应"。

行还要有"量它画出来的像素"的断言（与画布、示意图同一个思路）：
`grab()` 列表视口后量缩略图的红色占比、点眼睛/锁前后的差异像素数、
隐藏行名字区是否变淡。**最后这条要量文字像素**，所以测试里得给 offscreen
平台设 `QT_QPA_FONTDIR=C:/Windows/Fonts` —— Qt 5 起不随包分发字体，
不设的话文字画成空白，两张图完全一样，断言就莫名其妙地红了。

> ★ 面板接上之后立刻回出**两个真 bug，都在 `Document` 而不是面板** ★
>
> | bug | 症状 |
> | --- | --- |
> | `mergeLayerDown()` 把 `upper` / `lower` 取反 | "向下合并"实际是"把下层合到上层去"，画面差异不大但**哪一层的属性被保留**全错 |
> | `mergeVisibleLayers()` 的插入位置在**删掉可见层之后**才算 | 数隐藏层时索引已经偏了，结果层落在错误槽位 |
>
> 两条都是"数学看着对、结果全错"的形态，被 `mainwin_test` 的**不变式**断言
> （不是写死某个层序）当场抓出。详见 `docs/实现铁律.md` 第十一章。

## 跨图导入：「打开为图层」

用户的原始需求是“从第二幅图片中选择一个区域，复制到第一幅图片上”。
这句话里真正缺的**不是复制粘贴**（复制走系统剪贴板、粘贴为新图层早就有了），
而是**同时看到两张图**。

有两条路可以解决：

| 方案 | 代价 |
| --- | --- |
| 多标签页 | 要重构中央控件（`setCentralWidget` → `QTabWidget`），影响面大 |
| **打开为图层** | 零架构改动，多用一步 |

当时先选了后者，于是“跨文档”问题退化成“跨图层”问题 ——
选区、反选、删除、移动这些图层内操作**全部是现成的**。
实际操作变成：`文件 → 打开为图层…` → 在新层上框选 → 反选 → 删除。

> 多标签页**后来也已落地**（见上方特性列表与「已实现进度」表，实现口径见
> `docs/实现铁律.md` 第十七章）。两条路现在并存、各有各的用处：
> **多标签页**负责“同时看到两张图”（跨页复制粘贴），
> **「打开为图层」**负责“把一张图并成当前文档的一层”
> —— 导入进来的图层与原生图层完全平等，可单独调不透明度 / 混合模式。

> ★ `DocumentManager`（数据层）早就完整了 —— `addDocument` / `openDocument` /
> `closeDocument` / `currentChanged` / `titleAt` / `hasUnsavedChanges` 都在。
> 缺的只是中央控件那一层 UI 外壳。这正是“打开为图层”能零架构改动落地的原因。

### 1. “把一张图变成一个图层”只有一份实现

「编辑 → 粘贴为新图层」(`Ctrl+V`) 与「文件 → 打开为图层…」要做的是**同一件事**，
所以它们共用 `MainWindow::addImageAsNewLayer()`。两条约束如果各写一遍，
就会有“改一处忘一处”，而且第二份没有自检守着：

- 新图层的位图**必须填满画布**
- 必须用 `CompositionMode_Source` 而不是 `SourceOver`

> **为什么"填满画布"是硬约束**：`Document::addLayer()` 在图层**大于画布**时
> 会静默调用 `setCanvasSizeInternal()` 扩画布，而那条路径**不压任何命令** ——
> 撤销时画布尺寸回不去。先把位图开成画布大小、再把图像画进去，
> 这条不变量就守住了。
>
> ★ 对应的断言必须用**比画布大**的图才测得出来：小图上 `addLayer` 只会
> 把它重排到左上角，画布尺寸照样不变 —— 小图根本测不出问题。

### 2. 尺寸决策必须问用户，而“没人可问”不能默认成裁剪

导入图比画布大时必须做决定：扩大画布（不丢图，但改了画布尺寸）
还是裁剪（保住画布，但丢了图的一部分）。两个都不是能替用户默认做的事。

判定用两个**纯函数**（`engine/Geometry`，可被断言而不是只能看截图）：

```cpp
QSize  unionSize(const QSize &a, const QSize &b);              // 逐维取大
QPoint centeredOffset(const QSize &canvas, const QSize &item); // 居中偏移
```

`unionSize` 只能是**逐维**取大 —— 写成“取较大的那一张”会让导入图被裁掉一条；
`centeredOffset` 不能加 `qMax(0, …)` 钳位 —— 那会把“尺寸算错了”藏起来，
让内容悄悄贴到左上角。两条都做过植入验证。

### 3. 带对话框的功能，必须把“干活的那半”做成公开入口

这是最可复用的一条。`openAsLayer()` 第一件事是模态的 `QFileDialog`；
在无人的自动化环境里，模态框会让进程**永久挂死**。所以拆成两半：

```
openAsLayer()                          ← 只负责“选文件”，选完就交棒
    └─ importImageAsLayer(path, policy)   ← public，真正干活的那一半
```

拆开之后立刻得到三样东西：截图工具能驱动它（于是有了人眼可看的两张图）、
自检能断言它（三种策略 + 撤销粒度 + 失败不动文档）、
而且**“不弹任何模态框”成了结构性保证**（失败汇报统一走一个 lambda：
交互时弹框、自动化时只写状态栏）。

`GrowPolicy` 就是“谁来回答那个问题”：

| 取值 | 谁回答 |
| --- | --- |
| `Ask` | 弹三选一框问用户（`openAsLayer()` 用，= 产品默认） |
| `Grow` | 调用方替用户答了 —— 扩大画布（自动化用） |
| `Crop` | 调用方替用户答了 —— 裁剪到画布（自动化用） |

> 这与 `TextTool::placeText()`（绕过 `QTextEdit` 浮层）是同一个套路：
> **把“有对话框”和“真正干活”分开，干活的那半必须能脱离 UI 被调用。**
> 本工程凡是带对话框的功能都该长成这样，否则它永远只能靠人眼验证。

### 4. 证据

- 引擎侧：`geometry_test` 的 `unionSize` / `centeredOffset` 组（`180 项`中新增 18 项）；
- 装配与行为：`mainwin_test` 的「打开为图层：装配」+「三种尺寸策略 …」两组
  （含 ①放得下 ②`Crop` ③`Grow` ④锁定图层拒绝 ⑤读不出文件不动文档）；
- **十条植入验证**：`.buildlog/implant_openaslayer.py`；
- 视觉证据：`shot.exe … openaslayer` 生成
  `.buildlog/openaslayer.png`（放得下 → 画布尺寸不变、新层居中）与
  `.buildlog/openaslayer_grown.png`（放不下 → 画布**只变宽**，
  底图在新层上下露出来），并自带 **13 项像素自证**。

详见 `docs/实现铁律.md` 第十六章。

## 导出 ICO：自己写一个二进制格式

「另存为」的格式列表里一直有 `ICO 图标 (*.ico)`，本来也一直是 `QImageWriter` 在写。
现在换成了自写编码器（`engine/IcoWriter.*`）。原因不是"想练手"，是**实测出来它不能要**：

```
QImageWriter(path, "ico").write(300×300 的图)   →  返回 true
                                              写出的却是 256×256（270398 字节）
                                              errorString() = "Unknown error"
```

★ **qico 插件会把超过 256 的图静默缩到 256，程序一声不响** ★
用户存一张 512×512 会拿到 256×256，而且没有任何提示 —— 属于"看起来成功了"的失败，
是最难被用户描述、也最难被自检抓住的一类。另外两处不适配：**512 上限没有地方可拦**；
`qico.dll` 属于 `imageformats` 插件、要单独部署，漏打的症状是"PNG 能存、ICO 存不了"，
而且**只在运行期暴露**。

### 两种条目：≤256 走 BMP，257~512 走 PNG

`ICONDIRENTRY` 里的宽/高**各只占 1 个字节**，而且**其中 `0` 表示 256**：

| 尺寸 | 条目 | 理由 |
| --- | --- | --- |
| 1~255 | BMP | 字节能原样表达 |
| 256 | BMP | 用 `0` 表达（`0` ⇔ 256） |
| 257~512 | **PNG** | 1 个字节**结构上就装不下** 256 以上 |
| > 512 | — | **拒绝** |

- **BMP 条目** = 40 字节 `BITMAPINFOHEADER` + 自下而上的 32bpp BGRA + 自下而上的 1bpp AND 掩码。
- **PNG 条目** = 整段 PNG 直接塞进去（Vista 之后的官方扩展）。此时目录项的宽高写 0，
  **真实尺寸以 PNG 头为准** —— Windows 与 Qt 都是这么读的。

### 512 是产品定案：**超限拒绝，不默默缩小**

默默缩小的后果是"导出成功了"，用户回头才发现图被改小。所以超限时**返回失败**，
并由界面层弹一句话，里面带**实际尺寸 + 上限 + 怎么办**：

> 图像尺寸 3840 × 2160 超出 ICO 格式的上限 512 × 512。
>
> ICO 是图标格式，边长上限为 512 像素（Windows 官方口径是 256，本程序放宽到 512）。
>
> 请先用「图像 → 图像大小」把图像缩小到 512 像素以内，再另存为 ICO。

★ 这句话是**引擎层**出的（`ico::rejectionMessage()`），界面层不重复写 "512" ★
两边各写一份就有两份真相：哪天上限改了，"拦住用户的数字"与"真正生效的数字"会不一致。
★ 判据是 `>` 不是 `>=`：**512×512 恰好放行** ★ 差一像素写反是这里最容易犯的错。

### 三个"写进去就错、肉眼看不出来"的坑

1. **`biHeight` 必须是 2 × 高**（XOR 图 + AND 掩码的**合计**高度）。
   漏乘的后果：读图程序把像素数据的前一半当图像、后一半当掩码 ——
   图标上下错位、下半张变成黑白噪点。
2. **AND 掩码：置 1 = 全透明**，且**最高位对应最左边的像素**；
   只对 `alpha == 0` 置位，**半透明不置位**（半透明还有墨，置位等于把它挖空）。
   掩码**自己按位拼**，不用 `Format_Mono` + `createAlphaMask()` + `invertPixels()`
   —— 后者的阈值语义与"要不要盖住背景"并不等价，而 `invertPixels()` 在 1bpp 上
   到底改颜色表还是改位、跨 Qt 版本口径不一。
3. **进文件前必须把预乘还原成非预乘**。`qRed()` 直接读
   `Format_ARGB32_Premultiplied` 拿到的是"乘过 alpha"的值，写出去半透明区域明显偏暗；
   而不透明像素完全正常 —— 只有带透明边缘的图才会暴露。这件事**放在编码器内部**
   （`ico::encode` 自己转），不散给调用方：散出去就必然出现"这条路径转了、那条路径忘了"。

### 分流点只有一处

```cpp
// MainWindowCommands.cpp —— writeImage() 的第一件事
if (format.compare(QStringLiteral("ico"), Qt::CaseInsensitive) == 0) {
    QString err;
    if (exportIcon(path, &err)) return true;
    QMessageBox::warning(this, tr("无法保存为 ICO"), err);   // 只有 UI 路径弹窗
    return false;
}
```

`saveDocument()`（Ctrl+S 存到已有 `.ico`）与 `saveDocumentAs()`（另存为）**都经过
`writeImage`**，所以在这里分流 = 两条路自动覆盖，不可能出现"另存为能存 ICO、
Ctrl+S 又走回插件"这种不一致。

`MainWindow::exportIcon(path, errorOut)` 是 **public 且不弹窗**的 —— 与
「打开为图层」的 `importImageAsLayer()` 同一套路（见第十六章）：另存为的入口是
`QFileDialog`，模态框在无人环境里会把进程**永久挂住**，所以"选路径"与"真正干活"
必须拆开，后者才驱动得动、也才有断言守着。

### 怎么验：字节级结构 + 用别人的读取器往返

自写二进制格式，"本程序能写"毫无意义（本程序根本不读它）。所以两路夹：

1. **字节级结构**（手写小端 `putU8/putU16/putU32`，不用 `QDataStream` ——
   它默认大端，漏设 `setByteOrder()` 的话产出文件"看着完全正常"但谁也打不开）。
   逐字段对拍，外加一条最强的**整体不变量**：
   `dwImageOffset + dwBytesInRes == 文件总长` —— 它一次就覆盖"条目里记的长度"
   与"实际写出去的字节数"是否一致，比逐个字段更能抓住"某处算错了一个字节"。
2. **往返**：写出去之后用 **Qt 自带的 ico 读取器**读回来逐像素比。
   两套独立实现互相印证，这条最像"用户真的能打开吗"。覆盖尺寸**跨过 256 这条
   分界线**（16/32/48/256 走 BMP，300/512 走 PNG），测试图**四种 alpha 各一份**
   （不透明 / 半透明 / 全透明 / 另一种不透明）—— 否则"透明通道被丢掉"根本测不出来。

## 画笔的撤销策略（值得单独说明）

一次鼠标拖动（按下 → 移动若干次 → 抬起）只产生**一条**撤销命令，
按一次 `Ctrl+Z` 就退回一整笔。

实现上并没有用 `DrawCommand` 的 `mergeWith` 机制，而是用更直接的办法：
拖动期间不碰撤销栈，把整笔的像素变化攒在工具内部，松手时一次性构造命令。
两种方式最终存的数据量相同（都等于"整笔脏矩形的前后两份像素"），
但一次性构造少了一堆"每步构造-销毁中间命令对象"的开销，也避开了合并
逻辑里的边界错误。

另外三个关键设计（详细理由都在 `engine/Brush.h` 与 `tools/BrushTool.h`
的注释里）：

1. **落笔用"取最大"而不是"累加"合成到累积蒙版。**
   累加会让同一笔内重叠处越涂越深，一条均匀的线变成竹子状。
2. **每帧从"落笔前快照"重算，而不是在上一帧结果上继续画。**
   画笔的 source-over 与橡皮的乘法都不可逆，叠加式实现会累积误差
   （典型症状：橡皮反复经过同一处却擦不干净）。重算式实现是幂等的 ——
   按住鼠标不动时手抖也不会让线条变深。
3. **只重算"本帧新增落笔点覆盖的矩形"**，不是整笔包围盒。
   落在该矩形外的像素，其覆盖度本帧没变、值已经正确，不需要重算。
