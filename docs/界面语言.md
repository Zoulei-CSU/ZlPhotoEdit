# 界面语言（i18n）

> 多语言支持的**路线定案 + 实现规格 + 实测结论**。分两阶段：
> **阶段 1**（已完成）= 基础设施，翻译文件内嵌进可执行文件，源码仍是中文；
> **阶段 2**（未开始）= 源码英文化 + 填中文翻译。
> 构建总览见 [构建与运行.md](构建与运行.md)；自检见 [自检与验证.md](自检与验证.md)。

## 1. 路线：B（英文源码 + 各语言 .qm 翻译）

**用户拍板的硬约束**：翻译文件**编译后内嵌进应用程序**，用户机器上不存在独立的翻译文件夹。

```
translations/zlphotoedit_zh_CN.ts     （源，入库）
      │  lrelease（构建期）
      ▼
build/i18n/zlphotoedit_zh_CN.qm       （中间产物，不入库）
      │  rcc（构建期）
      ▼
可执行文件里的 qt_resource_data        （运行时从 ":/i18n/xxx.qm" 读）
```

路线 B 的语义（阶段 2 英文化之后）：

| 界面语言 | 翻译器 | 控件显示什么 |
| --- | --- | --- |
| `en` | 不装 | `tr()` 里的英文源码 |
| `zh_CN` | 装内嵌 .qm | `tr()` 走中文翻译 |

源码语言由 `src/core/UiLanguage.cpp` 的 `kSourceLanguage` 一个常量决定：
阶段 1 是 `"zh_CN"`，阶段 2 英文化改成 `"en"`。**改它一行，整个决策链翻转**，
不需要动别处 —— 这正是把语言决策集中到一个文件的原因。

### 1.1 为什么语言决策要集中在一个文件

"当前界面是什么语言"有三个消费方：

| 消费方 | 用途 |
| --- | --- |
| `main.cpp` | 启动时装不装翻译器（必须早于第一个窗口） |
| `MainWindowActions.cpp` | 语言菜单当前项、写入用户选择 |
| `AppInfo.cpp` | 窗口标题显示名（英文界面显示英文名） |

三方各写一份"怎么读设置、怎么推断 locale"，迟早出现"菜单说已经切成英文、
标题还是中文"这种对不上的 bug —— 而这种 bug 双构建 0 错 0 警，只有真的
去看窗口才会发现。`zl::uilang` 把"选哪个、存哪、怎么装"收成一处，
调用方只管问结论。

### 1.2 为什么可用语言是声明式列表，不运行时扫 `:/i18n/`

`availableLanguages()` = 源码语言 + `kEmbeddedLanguages`（编译期常量）。

运行时扫 qrc 目录听着更"自动"，但它把"构建有没有成功内嵌"变成了运行时的
隐藏状态：**测试程序（不编 i18n.qrc）与真机行为会不一致**，而语言菜单的
有无正是一件该被测出来的事。声明式列表让两者行为一致：菜单结构在测试里
可断言；真正的 .qm 缺失由装载失败 + qWarning 兜底（§3.2），且 rcc 在构建期
就会因 qrc 引用不存在的文件而报错 —— 到不了运行。

## 2. 构建链路（两条路径等价，同一批 .ts、同一个 prefix）

### 2.1 qmake 侧（ZlPhotoEdit.pro「多语言」段）

```
translations/zlphotoedit_zh_CN.ts
  → lrelease → build/i18n/zlphotoedit_zh_CN.qm
  → write_file 生成 build/i18n/i18n.qrc（列出 .qm 清单）
  → RESOURCES += → rcc 编进二进制 → 运行时 :/i18n/xxx.qm
```

lrelease 与 qrc 生成都在 **qmake 解析期**完成，rcc 留给 nmake。
lrelease 位置：优先 `$$[QT_INSTALL_BINS]/lrelease.exe`，找不到回落 PATH。

### 2.2 CMake 侧（CMakeLists.txt「多语言」段）

```
translations/zlphotoedit_zh_CN.ts
  → cmake -E make_directory 先建输出目录（lrelease 自己不建，见 §5.2）
  → lrelease（add_custom_command，逐 .ts）→ .qm
  → cmake -P packaging/i18n/gen_i18n_qrc.cmake 生成 i18n.qrc
    （内容 = glob 真实产出的 .qm 清单，DEPENDS 全部 .qm）
  → target_sources + AUTORCC 自动 rcc
```

lrelease 三个来源都要找（发行方式漂移）：
Qt 官方包的 `bin/lrelease`（与 qmake 同目录，走 IMPORTED 目标）→
`Qt6Core_DIR` 往上三级的 `bin` / `libexec`（Qt6 起工具链拆去了 libexec）→
裸 `find_program`（Debian/Ubuntu 的 Qt5 在 /usr/bin）。
**找不到只 message(WARNING)，不失败** —— 翻译是增强项，缺它界面回落到源码
文本（§3.2），不该让一个可选的 Linguist 组件把整个构建挡死。

### 2.3 新增一种语言要同步三处（漏一个不报编译错）

| 位置 | 内容 |
| --- | --- |
| `ZlPhotoEdit.pro` | `I18N_LANG_CODES` |
| `CMakeLists.txt` | `ZLPE_TRANSLATIONS` |
| `src/core/UiLanguage.cpp` | `kEmbeddedLanguages` |

外加 `translations/` 下的 .ts 文件本身。漏一个的后果不是编译错误，而是
"菜单里少一种语言 / 多一种死语言"——双构建 0 错 0 警，只有真的去点菜单才会
发现。**靠人对账，对账时机就是"新增一种语言"那一刻**（极低频，可接受）。

### 2.4 改完 .ts 必须重跑一次 qmake

Makefile 里没有 .ts → .qm 的依赖（qmake 体系里加它要动 QMAKE_EXTRA_TARGETS，
为一年改两次的翻译文件不值当）：编辑翻译内容后，**重新 qmake + nmake**。
CMake 侧有 DEPENDS，不受此限。

## 3. 运行时装载与决策

### 3.1 决策链（currentLanguage()）

```
① QSettings "ui/language" 里用户显式选过的值
② 没选过 → 按系统 locale 推断（中文环境 → zh_CN，其余 → en）
③ 结果不在可用列表里 → 回落源码语言
```

任何情况下返回值一定在 `availableLanguages()` 里 —— 所以不存在"存了个不存在
的语言"这种状态，下游不需要到处写兜底分支。键名 `ui/language` **发布后不要改**
（改了等于重置用户的选择）。

### 3.2 装载（installTranslator()）

- 进程内**只保留一个翻译器**（函数内 static + unique_ptr）。重复安装会让两份
  翻译叠在一起 —— Qt 按安装顺序反序查找先装的后生效，行为取决于谁后装，极难查。
- 不设 parent：QObject 父子机制会在 app 析构时再 delete 一次，与
  removeTranslator + reset 冲突；static 的析构发生在 main() 局部对象之后，顺序安全。
- **.qm 加载失败 → qWarning + 返回 false，界面保持源码文本**。不让"少一个翻译
  文件"把程序挡在启动之前。
- `needsTranslation(code)` = `code != sourceLanguage()`：源码语言本身不装翻译器。

`main.cpp` 的 `setupUiLanguage()` 在 `setupUtf8Encoding()` 之后、第一个窗口之前
调用，并往 stderr 打一行结论（`界面语言: zh_CN（源码文本）`）—— 用户报
"界面语言不对"时，这一行能直接告诉排查者是"没装上"还是"装错了语言"。
**这行用 fprintf 不用 qInfo**，原因见 §5.2。

### 3.3 菜单与持久化（v1：重启生效）

「语言(&Y)」菜单（MainWindowActions.cpp，挂在「帮助」之前）：

- **`availableLanguages().size() > 1` 才建菜单**。阶段 1 只有一种可用语言，
  整个菜单不出现 —— 刻意为之，避免只有一项的"死菜单"；阶段 2 源码英文化后
  自动出现，**代码零改动**。
- QActionGroup 互斥单选，当前项 `setChecked`。
- 单项**不设 objectName**：对账规则是"有名字的菜单动作必须有图标"，为两个
  语言项各配一张图标纯属噪音（与「标尺单位」子菜单同款处理）。定位靠
  `findChild<QMenu*>("menuLanguage")`。
- 点击后 `setCurrentLanguage()`（写 QSettings 并立即 `sync()`——落盘要赶在
  "重启生效"提示框之前，否则用户看完提示直接 Alt+F4，这次选择就丢了）+
  QMessageBox 提示"下次启动生效"。运行中切换要重翻译整个 UI（动态拼的标题、
  状态栏、对话框文本全部重新生成），v1 不做，宁可诚实地说清楚，也不给一个
  "点了没反应"的死开关。
- 语言显示名走 `displayName()`：**母语显示，不走 tr()** —— 中国人看到
  「简体中文」、英国人看到 "English"，与系统设置、浏览器一致。若把语言名也
  翻译成当前语言，反而要用户先认字。

`AppInfo::displayName()`：界面语言 en → 英文工程名，否则中文品牌名；
`titleSuffix()` 两个名字相同时不拼成 "X (X)"。

### 4.3 两个 tr 上下文问题点（2026-10-12 实测，改法已定）

**背景机制**（Qt 5.15.16 + MSVC 2022 实测）：

| 调用形态 | 运行期 context | lupdate 记录的 context |
| --- | --- | --- |
| Q_OBJECT 类里 `tr()` | 类名（`staticMetaObject.tr()`） | 类名 |
| **无 Q_OBJECT 的 QObject 子类里 `tr()`** | **"QObject"**（继承来的） | **类名** ← 对不上 |
| 命名空间级自由函数里 `QT_TR_NOOP` | 取决于调用方怎么写 | 命名空间名（跳过匿名层） |

即：**无 Q_OBJECT 的类里调 `tr()`，翻译永远不命中** —— lupdate 把源文本记在
类名 context 下，运行期却去查 "QObject"。本仓正好踩中两处：

**① `src/tools/ToolOptions.cpp:189-192`（选区运算四按钮）**

`QT_TR_NOOP("新建")` + `QObject::tr(entry.text)`：lupdate 记 context `zl`，
运行期查 `QObject` → 8 条（4 文本 + 4 tooltip）永远翻不了。
**改法**：`QObject::tr(entry.text)` → `QCoreApplication::translate("zl", entry.text)`
（.ts 里的 context 就是 `zl`，不用重新生成）。

**② `src/ui/CanvasSizeDialog.cpp:54-64`（九宫格锚点按钮 tooltip）**

`AnchorButton`（匿名 namespace 里，无 Q_OBJECT）的静态函数 `anchorName()` 里
调 `tr()`：lupdate 记 context `zl::AnchorButton`，运行期查 `QObject` → 10 条
tooltip 永远翻不了。
**为什么不能加 Q_OBJECT**：moc 对匿名命名空间的类按 `zl::AnchorButton` 生成
`staticMetaObject` 等符号，而真实类在匿名命名空间里，编译直接
`error C2653: "zl": 不是类或命名空间名称`（实测）。
**改法**：`QT_TRANSLATE_NOOP` + 显式 context ——
`return QCoreApplication::translate("zl::AnchorButton", QT_TRANSLATE_NOOP("左上"));`
（context 与 .ts 里已记的一致；或把 anchorName 挪成 zl 命名空间自由函数、
统一走 `translate("zl", ...)`，两种都行，选前者 diff 最小）。

## 5. 实测坑（都踩过，别再踩）

### 5.1 qmake 语义（Qt 5.15.16）

| 现象 | 结论 |
| --- | --- |
| `write_file(file, VAR)` 只接受**变量名** | 传字面量写出空文件 |
| `$$lang.qm` | 被解析成变量名 `lang.qm`，必须写 `$${lang}.qm` |
| `exists()` 在 Windows 上不做 PATHEXT 解析 | 必须带 `.exe` 后缀 |
| `CONTENT +=` 用空格连接 | XML 无碍 |
| qmake 每次调用解析 .pro **3 遍** | `system()` 副作用执行 3 次，幂等可接受 |

### 5.2 lrelease 不创建输出目录（一级也不建）+ 生成器差异

`-qm` 指向缺失目录时，lrelease 直接 `cannot create ...: No such file or
directory`，exit=1 —— **本机 Qt 5.15.16 实测：缺一级、缺两级同样报错，
一级都不建**。所以两侧都必须先建目录：

- qmake 侧靠 `write_file` 建目录（它自动创建父目录，正好）；
- CMake 侧在自定义命令里显式 `cmake -E make_directory`。

**为什么不能指望生成器代劳（2026-10-12 CI 第 15 轮的真失败）**：

| 生成器 | 建输出目录？ | 证据 |
| --- | --- | --- |
| Ninja | **会** | 本机实测：自定义命令输出放缺失的 `gen/deep/` 下，Ninja 建目录后 lrelease 产出 26 字节 qm |
| Make（Unix Makefiles） | **不会** | CI 实证：唯一用 Make 的 job 第一个自定义命令即失败 |
| MSBuild（VS 生成器） | 会 | CI 的 Windows job 通过 |

⇒ 本机 CMake 验证**只跑过 Ninja 路径**（本机没装 make），Make 路径是盲区，
CI 一跑就现形：AppImage-Qt6 job（rockylinux:8 基础镜像只有 make，工作流
刻意不装 ninja）挂在 `cannot create '/work/build/i18n/...qm'`。
修法就是显式 `make_directory` —— 与生成器无关，Ninja/Make/MSBuild 全一致。
**教训：验证构建链改动时，"本机过"不等于"各生成器都过"**。

### 5.3 qInfo/qDebug 在 Git Bash（MSYS）重定向环境下全部静默丢失

同一程序：PowerShell 下 qInfo 正常输出，Git Bash 下四个日志级别全部无声
（连重定向到文件也抓不到）；`QT_LOGGING_RULES` 三种写法都救不活。
**诊断日志一律用 `fprintf(stderr)`**。顺带修了一个真 bug：
`logSupportedImageFormats()` 的 qInfo 从未输出过（不是"没必要输出"，是
"写了却没生效"），改 fprintf 后"可读/可写格式"两行恢复可见。

### 5.4 rcc 把资源名存成 UTF-16 码元表

.qm 以压缩字节进 `qt_resource_data`，资源名以 UTF-16 码元表存储 ——
**二进制里 grep ASCII 路径串搜不到**。验证内嵌要看 `build/rcc/qrc_i18n.cpp`
的 `qt_resource_data`（本次实测到 26 字节的 qm 数据表）。

### 5.5 MSYS 路径转换（老坑复踩）

`build_env.sh` 设 `MSYS2_ARG_CONV_EXCL="*"` → `cmake -B /tmp/xxx` 会把
`/tmp/xxx` 当字面量传给 cmake，实际建到**当前盘的 `\tmp\xxx`**（`D:\tmp\cmake-i18n`）。
详见用户级记忆的 Git Bash 路径转换陷阱。

### 5.6 tr() context 三连（见 §4.3）

QObject::tr → "QObject"；无 Q_OBJECT 子类 → "QObject"（翻译不命中）；
匿名 namespace 加 Q_OBJECT → moc 生成的 `zl::X` 引用编不过（C2653）。
