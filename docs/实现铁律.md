## 一、LUT 流水线（`engine/Lut.*`）

亮度 / 对比度 / 反色 / 阈值 / 去色 / 曲线 / 色阶**统一走同一个入口**
`applyLuts()`（`applyLutRgb()` 是它的单表便捷版），不要各写一套逐像素循环。

- 烘焙 256 项，参数一变就重烘焙；逐像素阶段只查表。
- 图像 < 1MP 时**不要**走并行分支（线程开销大于收益）。

### 1.1 预乘陷阱（最容易错、症状最隐蔽）

图层位图是 `Format_ARGB32_Premultiplied`，R/G/B 分量**已经乘过 alpha**。
一个纯白 50% 透明的像素：

| 空间 | 存储值 |
| --- | --- |
| 非预乘 | `(255, 255, 255, 128)` |
| 预乘 | `(128, 128, 128, 128)` |

曲线期望的输入是 255，实际拿到 128 —— 半透明区域被当成暗部处理，颜色明显
偏差，但因为只有半透明像素受影响，在照片上极易被当成"原图就这样"。

**正确做法**：预乘 → 非预乘（除以 alpha）→ 查表 → 乘回 alpha → 预乘。
`applyLuts()` 内部已经处理，调用方不需要也不应该再关心格式。

**例外（务必区分）**：`Blend.cpp` 混合模式、`Resample.cpp` 重采样
**不做**这个往返 —— 它们的运算本就定义在预乘空间。
只有"按原始 RGB 值查表"的调整类运算需要往返。

### 1.2 ★ 通道广播：`isMonochrome()` 优化过的坑 ★

`ChannelLuts::isMonochrome()` 的含义是**三条曲线长得一样**：

```
lutR(x) == lutG(x) == lutB(x)     对任意 x
```

它**不**意味着"像素的 R/G/B 三个分量相等"。这两件事毫无关系。

历史实现把它误解成后者，写成：

```cpp
if (mono) { const int v = lutR[ir]; r = g = b = v; }   // ← 错误：只查红通道再广播
```

后果：任何 `R≠G≠B` 的像素，其 G/B 都被红通道的查表结果覆盖 ——
**用户拉一下亮度滑块，彩色照片整体变成"用红通道值渲染"的单色图。**

它能潜藏很久，是两个巧合叠加：

1. `applyLutRgb()` 构造的 `ChannelLuts` **天然**满足 `isMonochrome()`，
   所以这条错误分支覆盖了亮度 / 对比度 / RGB 主曲线的**全部调用**；
2. 当时所有 LUT 断言用的都是**灰度像素**。灰度图上"各查各的"与
   "查一个再广播"结果完全相同，**测不出来**。

**正确做法**：判断提到循环外，只让 `lutG`/`lutB` 指向同一张表
（省的是 256 字节表的 cache 占用，**不是**查表次数），
三个通道**始终用各自的输入值**查表。

**教训**：测试数据的取值范围必须覆盖实现的隐含假设边界。用同样的假设
去写测试，等于没测。改进/对比度/RGB 曲线的测试**必须包含彩色像素**。

## 二、曲线（`engine/Curves.*`，设计见 [曲线调整设计.md](曲线调整设计.md)）

三条铁律：

1. **插值必须用 Fritsch–Carlson 单调三次样条**。普通 Catmull-Rom 会在段内
   产生过冲（先升后降的"回勾"），表现为暗部色带和高光里的反相噪点。
2. **控件绘制曲线必须复用 `Curves::bake()` 的 `m_bakedLut()`**，
   保证"看到的曲线"与"实际映射"完全一致。
3. **预览必须始终在原始图像上重算**，不能在上次预览结果上叠加
   （舍入误差会累积成色偏）。

判据是"256 项**方向一致**"（不减**或**不增），不是"必须递增" ——
内置的「反相」预设本身就是一条递减直线，它完全正确。

### 2.1 `CurveEditor` 交互约定

- 左键空白处 = 新增点并进入拖动；右键点 = 删除点；端点不可删
- 相邻控制点 x 必须保持 **≥1 间隔**（否则插值除零）
- 内部状态**一律用 0..255 整数存储**，只在绘制和命中检测时转控件坐标
- 背景直方图**用对数缩放**，否则集中分布时柱形全被压平

### 2.2 四条曲线的叠乘关系

RGB 主曲线与 R/G/B 单通道曲线是**叠乘**，不是覆盖：

```
final(x) = curveB(curveG(curveR(curveRgb(x))))
```

实现上不必逐像素查四次表 —— 用 `composeLut()` 预先合成一条，
逐像素只查一次。`composeLut(inner, outer)` 语义为 `outer[inner[i]]`。
注意顺序：RGB 主曲线在最**内**层。

## 三、画笔 / 橡皮（`engine/Brush.*`）

1. 累积蒙版**取最大合成，不是累加**（累加会让同一处来回涂抹无限变浓）。
2. **从落笔前的快照幂等重算**，否则橡皮擦不干净。
3. 合成在**预乘空间**，且**选区蒙版乘法必须在颜色预乘之前**。
4. `finishStroke()` 用 `CompositionMode_Source` 写回。

## 四、选区（`core/Selection.*`）

- **`setFromPath()` / `applyPath()` / `selectRect()` / `selectEllipse()`
  在 `m_mask` 为空时会静默 return，一个标志位都不改。**
  表现是"第一次拉选区毫无反应"且无任何报错。
  → 首次操作前必须 `prepareCanvas(QSize)`：底色填 **255**、
  **不动 `m_active`**，保持 `isActive() == false` 走快路径。
- **`isAllSelected()` 必须返回 `m_allSelected`**
  （写成 `m_active && m_allSelected` 会恒为 false）。
- **羽化 `perPass = qMax(1, qRound(radius / 3.0))`**。
  三次盒式模糊是串联的，总扩散 ≈ 3 × 单趟半径。历史实现直接把 `radius`
  当单趟半径 → **实际羽化是标称值的 3 倍**，且不报错。
  灰度蒙版走 `filters::featherGrayMask()`（`boxBlur` 是 ARGB32 专用）；
  羽化作用在**形状蒙版**上，**再**合入。
- **蚂蚁线不能用 `QRegion::addRegion()`** —— 逐扫描行矩形会让内部全是横线。
  必须逐像素找交界并**合并连续段成线段**（合并才让虚线正确，Qt 的虚线按
  子路径分别起算）。用 **cosmetic 画笔 + 关抗锯齿 + 黑底白虚线**。
  共用实现 `tools/MarchingAnts.h`。
- 选区工具**拖动期间不碰 `Document`**，松手才渲蒙版 + 合入 +
  压**一条** `SelectionCommand`。
- Modifier 分两阶段：按下定运算方式、拖动定几何约束。
- `Subtract` 是**按比例扣减**：`a - a*b/255`。

## 五、尺寸 / 旋转 / 剪贴板 / 文件

完整规格见 [画布与文件操作设计.md](画布与文件操作设计.md)。三组易混概念：

- **图像大小** = 缩放像素；**画布大小** = 像素不动、改容器。
  两者都要作用于**所有图层 + 选区**。
- **内容旋转**（图层级，画布不变）vs **图像旋转**（图像级，画布跟着变）。
- **裁剪**是 `resizeCanvas()` 的特例，`CropTool` 内部直接复用。

统一入口 **`Document::applyGeometryChange(transform, newSize, interpolate, fillColor)`**
—— 缩放 / 画布 / 旋转 / 翻转全部归结为"一个 `QTransform` + 新尺寸"，
边界情况只写一遍。**`GeometryChangeCommand`** 覆盖全部尺寸类操作。

四条硬规则：

1. **尺寸类 Command 最耗内存**（4 图层 × 4000×3000 = 384MB/步）
   → `qCompress`（级别 3）+ 单独限步数。
   解压后 `QImage` **必须 `copy()`**（浅引用陷阱：不崩溃但悬空）。
2. **90° 整数倍旋转必须走无损路径**，判断用容差 `fmod` 不用 `==`。
   验证：旋转 90° 四次应与原图逐像素相同。
3. **任意角度旋转必须从基准图重算**，不能在预览结果上叠加
   （旋转的插值误差比 LUT 舍入严重得多）。
4. **选区复制要把蒙版值乘进 alpha**，否则选区外内容泄漏
   （椭圆选区粘出一个矩形）。必须在预乘转换**之前**做。

### 5.1 ★ 智能适配偏移只能有一个来源 ★

画布缩小时若严格按九宫格锚点平移，内容会被裁掉一截。为此有
`geometry::canvasResizeOffset(contentRect, oldSize, newSize, anchor, smart)`：

- **只在缩小时启用**智能适配；放大时锚点说了算，不做任何"帮忙"。
- 策略是两段式：先按锚点算出偏移，再判断平移后内容是否仍完整落在新画布内
  —— **放得下就保持锚点**（不再居中），**放不下才钳制**到最小裁剪位置。
  （曾经把这两个分支写反：内容 80×80 放进 100×100 的新画布，居中平移
  −50 反而把左上角推出画布。测试因此失败，见 `geometry_test` [2]。）
- **内容为空时退化为整个旧画布**（不是空矩形），否则"空图层文档改画布大小"
  会得到与"有内容文档"不同的偏移。

**唯一来源铁律**：对话框示意图与 `Document::resizeCanvas` **必须调用同一个
`canvasResizeOffset()`**。曾经两边各写一份策略，结果是"示意图说不会裁、
点确定却被裁了"。`geometry_test` [10] 专门做端到端对账：把对话框用的
公式与 `Document::resizeCanvas` 的实际结果逐项比较。

### 5.2 尺寸对话框的"单一真相"状态模式

`SizeChangeDialogBase` 是所有尺寸对话框的基类（`ImageSizeDialog` /
`CanvasSizeDialog`），它解决的是**输入控件与派生状态互相触发**的经典死循环：

- **真相只有一份**：`QSize m_target`。用户改输入框 → 先算出新的
  `m_target` → 再回写所有视图。**绝不让控件互为真相**。
- 回写时用 `QSignalBlocker` **加** 显式重入标志 `m_writing` 双保险。
  只有 `QSignalBlocker` 不够：`QSpinBox::setValue()` 有时会走
  `editingFinished` 之外的路径，而且长宽比联动会二次改值。
- **信号在 `buildLayout()` 之后才接线**，否则构造期的初始赋值就会触发
  `isChanged()` 计算。
- **相对模式只是"显示层的换算"**：勾选「相对」后输入框数字 = 目标值 − 原值，
  `m_target` 本身不变。所以切换勾选框只重画视图，不重算状态。
- ★ **单位（像素 / 百分比）也是显示层，且必须遵守同一条规矩** ★
  切换单位时 `m_target` **一个像素都不动**，只重算输入框的 range / suffix
  并回写显示。只有三种"视图修饰"：单位、相对模式、长宽比锁定 —— 它们
  都不许改尺寸。**最容易写出的错法是"切换时顺手把当前显示值按新单位解析
  一遍"**：

  ```cpp
  m_unit = unit;
  m_target.setWidth(inputToTarget(m_width->value(), m_original.width()));  // ✗
  ```

  用户只是拨了个显示开关，图就被真的改了，撤销栈里还会多出一条几百 MB
  的记录。（把这段临时植入，`ui_smoke_test` 立刻报 8 项失败。）
  换算本身只有一处：`geometry::percentToPixels()` / `pixelsToPercent()`，
  取整一律四舍五入（截断会让百分比往返每次少一像素）。
  输入框区间按 `(单位, 模式)` 且**宽高分别**计算 —— 完整规格见
  `画布与文件操作设计.md` 6.6 节。
- 「确定」按钮的可用性由 `isChanged()` 决定；子类改动状态后要调
  `refreshInfo()`（它负责置灰按钮 + 刷新信息面板）。
- ★ **Qt5 陷阱**：`QDialogButtonBox::button(QDialogButtonBox::Reset)` 对
  `addButton(text, ResetRole)` 加进去的**自定义按钮返回空指针**。要靠
  `setObjectName("buttonReset")` + `findChild<QPushButton*>()` 定位。
  （`ui_smoke_test` 曾因此报"复位按钮不存在"。）

**尺寸对话框不做实时预览**：尺寸操作是"换掉整份位图"，预览要做一次
降采样 + 一次插值，与最终结果必然对不齐。画布大小对话框预览的是
**几何示意**（新画布/原画布/内容/被裁内容四层色块），不是像素预览。

### 5.3 ★ 旋转包围盒：直角必须走整数路径 ★

`geometry::rotatedBoundsSize(size, angle)` 算旋转后的外接矩形，用于
"任意角度旋转要扩到多大画布"。

**直角（0/90/180/270）必须先精确处理**（`isRightAngle()` 按 90° 取模判据），
直接互换宽高，**不要让浮点三角函数参与**：

```
cos(90°) 在 double 下 = 6.1e-17  （不是 0）
→ newW = W·|cos| + H·|sin| 会得到 W·6.1e-17 + H
→ ceil() 在这个比整数略大的值上多进 1  → 100×50 转 90° 得到 51×100
```

症状是**每转一次就多 1 像素**，转四次回不到原尺寸，而"转四次逐像素
回到原图"的断言正好会失败（`geometry_test` [6]）。非直角路径最后要
`ceil(x - 1e-9)` 而不是裸 `ceil(x)`，否则"数学上正好是整数"的角度
（如 30° 配特定边长）也会多 1 像素。

---

**剪贴板**：自定义 MIME `application/x-zlphotoedit-layer`
（pixels + mask + sourceBounds）+ 同时提供 `image/png`。
**不要提供 BMP**（未压缩，大图进剪贴板会拖慢系统）。
粘贴位置：同文档原位（靠 `sourceBounds`）/ 跨文档居中 / 超出画布自动扩画布。

**另存为**：用 `QImageWriter` 而非 `QImage::save()`（前者能设质量/压缩）。
自定义参数控件必须 `DontUseNativeDialog`。`setDefaultSuffix()` 必设。
`closeEvent` 里 `save()` 返回 false 时 **必须 `e->ignore()`**。

**类名统一**：`ImageSizeDialog`（图像大小）、`CanvasSizeDialog`（画布大小），
共用 `SizeChangeDialogBase`。

### 5.4 ★ 示意图的绘制管线：路径必须映射到控件坐标 ★

画布大小对话框的示意图（`CanvasSizeWidget`）自己有一条绘制管线：把
"新画布/原画布/内容/被裁内容"四个**图像坐标**矩形等比映射到控件坐标后再画。
映射是唯一的入口 —— 一旦某条路径漏了映射，就变成"用图像坐标画在控件像素空间"。

实测踩过：内容色块写成 `rectPath(contentInNew)`（漏了 `m(...)`）。
一幅 4000×3000 的照片，其"内容路径"就是一个 4000×3000 的矩形直接铺在
两百多像素宽的控件上：

- `内容 ∩ 画布` 退化成**整块画布** → 蓝色铺满，看不出"新扩出来的透明区"
- `内容 − 画布` 退化成**控件里除画布以外的全部区域** → 红块从画布四周溢出
- 而虚线用的是映射后的值，**看起来还是对的**

于是画面上是"红底上一个蓝框"，与真实情况（蓝块只占旧画布范围）完全不符。
**不崩、不报错、信息面板文案全对**，只有量像素才能发现。

**守门断言**（`ui_smoke_test` 的渲染断言，与 `view_test` 的"渲染占位"同源）：

1. 放大时**不应出现任何深红像素** —— 放大不可能裁内容，这是纯逻辑必然，
   跟具体尺寸无关，所以容差可以开到 0。
2. **内容色块的右/下边缘与新画布边框之间必须有空白** —— 少了映射时
   间距会塌到 1~2 px。
3. **虚线的像素数必须可观** —— 内容包围盒常等于整幅旧画布，
   虚线若画在内容之前会被整条盖住（实测只剩 3 个可见像素）。

**绘制顺序**：底色 → 旧画布"将被移除"区 → 内容 → **原画布虚线** → 新画布边框。
虚线必须在内容**之后**（否则被埋）、边框必须最后（压在一切之上）。

### 5.5 ★ 旋转的轴心与平移：只有一处算法，且必须两个都写对 ★

任意角度旋转要同时做两件事：**围绕内容中心转**，再把转完的内容
**摆进新画布中央**。这两件事各自都能让人写错一次，而 90° 倍数恰好把
两个错误都掩盖住 —— 所以它们一直潜伏到"任意角度旋转"有了 UI 才现形。

**错误一：用未旋转的内容中心算偏移**

```cpp
// ✗ 错
const QPointF offset = newCenter - oldCenter;
```

`QTransform::rotate()` 是**围绕原点**旋转的，内容中心 `(w/2, h/2)`
转完之后自己也跑到了别处。想让它落回画布中心，必须用**转完之后**的中心：

```cpp
// ✓ 对
QTransform rotation;
rotation.rotate(angleDeg);
const QPointF offset = newCenter - rotation.map(oldCenter);
```

**症状**：内容整体偏出画布、被裁掉一角，四个角的填充区还一大一小。
看起来像"旋转轴心不对"，但代码里满是"围绕中心旋转"的注释，
光读代码很容易读过去。90° 倍数下**恰好正确**（中心绕原点转 90° 后
仍与画布中心对称），所以不会有人早发现。

**错误二：`applyGeometry()` 里把平移加了两遍**

```cpp
// ✗ 错 —— full 里已经含着 contentOffset 那次平移
rotation *= QTransform::fromTranslate(params.contentOffset.x() + full.dx(),
                                      params.contentOffset.y() + full.dy());
```

`full = params.transform * fromTranslate(contentOffset)`，所以 `full.dx()/dy()`
就是**最终**的平移量（contentOffset 已经被旋转矩阵耦合过一次）。
再加一遍，等于把内容朝偏移方向的斜下方多推了约一倍距离。

**为什么它能潜伏**：只有"需要插值 && 不是纯平移 && 不是 90° 倍数"才会
走到那个分支。90° 倍数走 `rotateQuarterTurns()` 无损路径、画布大小调整
走 `pureTranslate` 分支 —— 于是"任意角度旋转"成了唯一踩得到它的功能。

**守门断言**（`geometry_test` 的 [13] 组）：

1. **内容包围盒必须铺满整张画布**（每边容差 2 px）。包围盒的定义就是
   "刚好容纳旋转后的内容"，所以内容的外接矩形恰好等于画布 ——
   只要有一条边明显缩进，就是在裁内容。这条判据与角度、尺寸都无关，
   两个错误它都能抓到（实测分别报出内容像素 876/1200 与 952/1200）。
2. **四角必须是调用方指定的填充色**，而不是透明或内容色。
3. **90° 倍数必须与 `rotateQuarterTurns()` 逐像素相同**（含 `89.9999999°`），
   证明没有偷偷走插值。

> 调试这类"数学看着对、画面不对"的问题，**不要读代码猜**：在测试里临时
> 打印"内容像素的逐行 x 范围"，一次就能看出到底是"被裁"还是"偏心"，
> 打完立刻撤掉（本轮就是这么定位的）。

### 5.6 ★ 裁剪（`tools/CropTool`）：工具只发信号，绝不自己压命令 ★

裁剪是**唯一一个"参数是矩形"的图像级操作**，因此也是唯一一个
**没有对话框**的几何操作（其余六个都是标量 → 输入框即可；矩形是空间信息，
用数字表达要用户做两次坐标换算）。它的三条约束：

**① 工具不得 `new GeometryChangeCommand`，只发 `cropRequested(QRect)`**

几何类命令的内存预检（压缩后仍 >256MB 就不记撤销）**只能有一个入口**
—— `MainWindow::commitGeometryChange()`。工具自己压命令就等于开了第二个
入口，而"漏掉预检"的代价（几百 MB 快照占住内存）要到内存耗尽时才暴露。
方向上也必须如此：`tools → ui` 只能靠信号（同 `requestForegroundColor` /
`requestZoom`），反过来 include `ui/MainWindow.h` 是编译期就会报错的越界。

因此**新增任何图像级操作时，先问一句"它会不会开第二个压命令的地方"**。
主窗口侧的对偶函数是 `MainWindow::applyCropFromTool(QRect)`。

**② 浮点框 → 像素矩形：判据是"像素**中心**落在框内"**

```
i + 0.5 >= left   →  i >= ceil(left - 0.5)
i + 0.5 <  right  →  i <= ceil(right - 0.5) - 1
```

**宽度为整数 w 的框必然给出 w 个像素**，与它落在哪个小数坐标无关。
两种错法实测都会露馅：

| 判据 | left = 20.4、宽 40 的结果 |
| --- | --- |
| 像素中心（正确） | 20..59，40 列 |
| "相交"（`floor(left)` / `ceil(right)-1`） | 20..60，**41 列** |
| `qRound` | 半像素处多算或少算一列 |

这不是理论边角料：**100% 之外的所有缩放级别都会产生非整数坐标**
（33% 下拖 1200 个屏幕像素 = 3636.4 个图像像素）。
症状是**尺寸标签写 40×30、裁出来 41×31** —— 直接伤信任。
守门断言：`crop_test` [9]。

**③ 遮罩必须用"两个子路径 + 奇偶填充"，不能用四个矩形拼**

四个矩形在角上互相重叠，半透明色叠两次比边上深，四个角明显更黑。
`QPainterPath` 加 `bounds` + `m_rect` 两个子路径、`Qt::OddEvenFill`，一次成图。

> ★ 由此得出的一条**测法**教训 ★
> 验证"遮罩画反了"时**不能**靠"把两个子路径对调"来做植入 ——
> 奇偶填充只看穿过次数，谁先谁后结果完全相同，植入后测试**依然全绿**，
> 会被误判成"断言抓不住 bug"。真正有效的植入是**删掉 `bounds` 那一句**
> （只填框内），实测立刻报"框外未被压暗的像素 18385 个"。

## 六、bicubic 重采样（`engine/Resample.*`）

自写，`Resample::Method` 枚举。**a = -0.5 默认**，a = -0.75 作为"更锐"选项。
预览用双线性，确定时用 bicubic。

四条铁律：

1. **必须分离成两次一维卷积**，绝不做二维 4×4
   （复杂度 `O(W1·H1·16)` → `O(W0·H1·4 + W1·H1·4)`）。
2. **权重必须归一化**（`Σw = 1`），否则图像整体变亮/变暗，
   且偏差随缩放比变化。
3. **边缘采样用 clamp**，不是视为透明，否则出现暗边。
4. **在预乘 alpha 空间上加权求和是正确的**（与 LUT 查表不同，那个必须
   转非预乘）。

验证法：纯色图 `(128,128,128)` 放大缩小后应仍是纯色 —— 有偏差就是
归一化漏了。

## 七、测试与自检

- engine / core 层的测试**只链接 Qt5Core + Qt5Gui**，这是分层纪律的守门人：
  往 `engine/` 塞 QtWidgets 依赖会让测试立刻编译失败。
- 界面层测试**按需**开例外（`run_tests.sh` 的 `moc_headers_for` /
  `extra_libs_for`）：`ui_smoke_test` / `view_test` / `crop_test` /
  `mainwin_test` 额外跑 moc 并链接 `Qt5Widgets.lib`（后者要 moc
  **整个应用的头文件**，因为它的 include 面就是 MainWindow 的成员类型）。`geometry_test` 也跑 moc，但**只为 `core/Document.h`**
  （它带 `Q_OBJECT`），**不链接 QtWidgets** —— 它测 engine/core，不该拿到
  界面依赖。
- **读像素必须用扫描线，不能用 `QImage::pixel()`** —— 后者对预乘格式会做
  反预乘转换（把 `(128,128,128,128)` 报成 `(255,255,255,128)`），
  正好把预乘陷阱这个 bug 粉饰掉，拿它写断言等于白测。
- `QImage::setPixel()` 在预乘格式上会**先预乘再写入**，`fill()` 则不会。
  → 测试里要构造确定的像素值时**直接写扫描线**，不要依赖这类隐式转换。
- **带 `Q_OBJECT` 的类必须跑 moc**，否则链接报"无法解析的外部符号
  `...QMetaObject...`"，看起来像"少编译了某个 .cpp"。
- ★ **`.pro` 的 SOURCES/HEADERS 必须与 `src/` 实际文件严格对齐** ★。
  CMake 用 `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)`，新增文件会**自动**
  被收进来，**不暴露遗漏**；qmake 是逐个手写，漏一个 `ImageTypes.cpp`
  只在**链接期**报 `LNK2019: 无法解析的外部符号 resampleMethodName`
  —— 编译全过，很容易误判成"函数没实现"。
  → 实测踩过：`src/core/ImageTypes.cpp` 漏在 SOURCES 外，CMake 全量构建
  0 错 0 警，qmake 全量构建才把它抓出来。**改完 .pro 后应跑一次
  "src 实际文件 ⇄ .pro 列表"的对账**（脚本见 `.buildlog/pro_check.py`）。
- ★ **同一文件不要并行编辑** ★。用多个编辑调用同时改一个文件时，
  后一次会基于**旧内容**写回，**静默覆盖**前一次的改动 —— 不报错、
  结果看起来"只是没生效"。需要在一处文件里批量替换时，**写一次性
  Python 脚本**做替换并**断言匹配唯一**（`replace` 前后 `count` 校验）。
  这跟"double BOM"是同族问题：都是"工具帮你做了一半的隐式转换"。

### ★ 7.1 "定义与使用必须成对"的地方，都要有一条静态对账 ★

有一类错误**编译器永远抓不到**。实测踩过（任意角度旋转对话框）：

```cpp
imageMenu->addAction(m_actionRotateArbitrary);   // ← 菜单里加了
// …而全项目没有一处： m_actionRotateArbitrary = new QAction(…);
```

`QMenu::addAction(nullptr)` 是**合法实参**、静默什么都不做 —— 菜单项凭空消失。
编译 0 错 0 警；`ui_smoke_test` 也测不到（它**根本不链接 `MainWindow`**）；
双构建全绿、全部断言全绿。**只有把程序真正跑起来、点开菜单才看得见** ——
实际是截图工具走真实菜单动作（`actionRotateArbitrary`）时才暴露的。

> 补记：`MainWindow` 这一层现在有 `tests/mainwin_test.cpp` 直接盯着了
> （`./run_tests.sh mainwin`，见 §9）。菜单项缺创建语句这类问题依然要
> 靠静态对账 —— 因为它连"动作对象"都不存在，运行期无从断言。

→ 对账脚本 **`tests/action_check.py`**（`./run_tests.sh actions`，秒回）。
同时检查三件事：

| # | 检查 | 级别 |
| --- | --- | --- |
| ① | 进了菜单的名字必须有 `= new …` 创建语句 | 错误 |
| ② | 创建了的 `QAction` 必须有 `setObjectName()`（自动化靠它定位） | 错误 |
| ③ | `MainWindow.h` 里声明了却从未进任何菜单（写了动作忘挂菜单） | 警告 |

→ **动作"四件套"**：`new` → `setObjectName` → `connect` → `addAction`，
**四处齐全**才算接好。

→ ★ **对账脚本本身必须先证明它抓得住 bug** ★。动手验证时，把出问题的那行
**注释掉**再跑，脚本却报了通过 —— 因为正则把**注释里的赋值**当成了真代码。
**匹配前必须先剥掉注释**（`//` 与 `/* */`）。这是"守门断言必须先验证它抓得住
bug"这条纪律在**静态检查**上的同一形态，与 §7 末尾那条并列。

### ★ 自检脚本绝不能"假绿" ★

`cl` 用 `/Fe:` 指定输出，**只有编译链接成功才会写出 `.exe`**。
若脚本在编译失败后只判断"文件是否存在"，上一次构建遗留的旧 `.exe` 会被
当成这次的结果运行，于是出现：

```
编译失败 → 复用旧二进制 → 打印上一次的「通过 N 项」 → 整套显示全绿
```

而这次改的代码**一行都没编进去**。实测踩过：给 `adjust_test.cpp` 新增
13 条断言后，输出仍是原来的 93 项。

→ **编译前必须 `rm -f` 旧的可执行文件**（moc 的旧产物同理）。
这类问题应视为 **P0**：自检脚本一旦会给"假的好消息"，
它守的每一条断言都失去意义。

## 八、画布视图与呈现管线（`ui/CanvasView.*`）

### 8.1 ★ painter 的坐标系契约：第 3~9 步一律用图像坐标 ★

`paintEvent` 第 2 步执行 `painter.setTransform(m_viewTransform)` 之后，
**第 3~9 步（棋盘格、合成、网格、工具叠加层、蚂蚁线）全部用图像坐标书写**，
不再手工换算。这是整个呈现管线的枢纽。

只有两处例外，它们必须**先 `resetTransform()` 再按屏幕坐标画**：

| 例外 | 原因 |
| --- | --- |
| 第 4 步棋盘格 | 格子大小要恒定于屏幕，不能随缩放变成巨大方块 |
| 第 8.5 步图像边框 | 边框宽度要恒定 1 设备像素 |

**违反这条契约的代价**：`drawComposite()` 曾经把目标矩形手工
`m_viewTransform.mapRect()` 成屏幕坐标后，再交给这个**已被变换过**的
painter —— 视图变换被施加了两遍：

```
T(p) = M(M(p)) = offset·(1 + zoom) + zoom² · p
```

实测（`view_test` 第 7 组把它钉住了）：3840×2160 的照片在 33% 下应画成
1260×709、左上角 `(10, 45.6)`，实际只有 **414×232**、左上角 `(13, 61)`。
`414 / 1260 = 0.3286 = zoom`，`(13, 61) ≈ (10, 45.6) × 1.328` ——
这两个数字就是"变换被乘了两遍"的指纹。

```cpp
// 错：target 是屏幕坐标，painter 还会再映射一次
painter.drawImage(m_viewTransform.mapRect(QRectF(srcAligned)), source, sourceRect);

// 对：target 用图像坐标，交给 painter 映射
painter.drawImage(QRectF(srcAligned), source, sourceRect);
```

**为什么特别难认**：棋盘格与边框都是对的，于是屏幕上是
「正确的取景框 + 里面缩成一小块的图像」，看起来像"图像尺寸算错了"，
会把人引到 `zoom`/`offset` 的数学上去排查。而且 `zoom → 1` 时
`zoom² → zoom`、`offset·(1+zoom) → 2·offset`，**100% 附近几乎看不出来**，
只有明显缩小（适合窗口）时才暴露。

### 8.2 QTransform 的组合语义（右乘 = 后调用的先作用于点）

```
调用顺序  c1, c2, c3   →   M = c1 · c2 · c3
作用于点  p · M = c1 · (c2 · (c3 · p))
                    ↑ 最后调用的 c3 最先作用于点
```

- **`rebuildViewTransform()` 里 `translate` 必须在 `scale` 之前调用**，
  否则 `m_offset` 会被 `zoom` 乘一遍。用一次实测就能确认：
  `t.scale(0.5,0.5); t.translate(10,40)` 的 `map(0,0)` 是 `(5,20)`（平移被缩放），
  而反过来调用是 `(10,40)`（正确）。
- 目标关系固定为 **控件坐标 = zoom · 图像坐标 + offset**。
- **锚点缩放必须在控件空间做**：`M' = M · A`，`A` 是"在控件坐标里
  围绕 anchor 缩放 f 倍"。写成 `A · M` 会把 `anchor` 当成图像坐标，
  画面持续漂移（实测 offset 从 `(-62.5, 7.0)` 变成 `(-14.66, 29.21)`）。
  `X * Y` 表示**先 X 后 Y**。
- 「适合窗口」是一个**模式**，不是一次性动作：`m_userAdjustedView = false`
  表示"视图仍随窗口尺寸自适应"。`resizeEvent` 据此决定是重算 fit 还是
  保持中心。这条专门解决"文档在控件拿到真实尺寸之前就被 `setDocument`"的
  启动场景（否则 3840×2160 会按默认的 640×480 算成 16%）。

### 8.3 验证方式：测渲染结果，不要测喂给渲染器的参数

`view_test` 的坐标换算断言只证明了"数学对"。要证明"用户看到的是对的"，
必须**真的渲染一遍**：`QWidget::grab()` 会走完整 `paintEvent`，
用一张**纯色标记图**（纯红，与背景灰 `(80,80,80)` 三通道都拉开距离）
填入图层，再从结果里取包围盒，就得到**实际的显示尺寸**。

配套注意：

- `grab()` 前必须 `show()` + `resize()` + `processEvents()` ——
  对未显示的控件调 `resize()` **不会派发 `resizeEvent`**，测不出该测的东西。
- 边框的深色描边会压暗图像最外圈，包围盒每边缩进约 1 像素，容差给 3~4 像素。
- `view_test` 也支持传真实图片路径（`./run_tests.sh view -- <图片>`）。
  **中文路径经 Git Bash 传给 MSVC 程序时编码会被破坏**
  （`QString::fromLocal8Bit` 按 GBK 解 UTF-8 字节）→ 加载 0×0 静默回退成
  合成图，测试照样"全绿"。要测真实照片就先把文件复制成 **ASCII 文件名**。

### 8.4 ★ 画布尺寸只有一个取值口径：`effectiveCanvasSize()` ★

预览通道支持"自带画布尺寸"之后（任意角度旋转需要 —— 旋转会把画布撑大），
"画布多大"就不再等于 `m_doc->canvasSize()`。**全类所有用到画布尺寸的地方
都必须走 `effectiveCanvasSize()`**，一处都不能漏：

| 用在哪 | 漏掉会怎样 |
| --- | --- |
| `rebuildViewTransform()` 里翻转/旋转的中心 | 视图围绕**旧画布中心**转，画面与取景框错开 |
| `fitZoom()` / `zoomToFit()` | 缩放按旧尺寸算，新画布装不下（或缩得过小） |
| `paintEvent` / `drawComposite` / `drawGrid` 里的可见区域求交 | 可见区域算错 → 图像被多裁或少画 |
| 棋盘格、图像边框 | 取景框画在旧位置上，看起来"内容跑到框外去了" |
| `drawComposite()` 的源矩形换算 `sx = source.width()/canvasSize.width()` | 预览图被拉伸到错误的尺寸 |

**症状特征是"取景框对、图像偏"或者反过来** —— 而且两者都**只在预览期间
出现**（正常编辑时两个尺寸相等，看不出差别），一取消预览就"自己好了"，
所以极容易被当成偶发问题。

**守门断言**（`view_test` 的 [8] 组）：让预览图自带 200×80 的画布、
而文档只有 100×80，用纯绿标记图 `grab()` 后量绿色包围盒 ——
必须按 200 宽呈现（漏掉时只有 99 宽，报"期望 200.0000 ± 4.0000，
实际 99.0000"）。并且**清除预览后一个预览像素都不能剩**：
`m_previewCanvasSize` 必须与预览图一起清掉，否则画布会继续按大尺寸呈现，
右下角凭空多出一片棋盘格，"适合窗口"也会按错误的尺寸算。

### 8.5 ★ 工具叠加层的屏幕尺寸恒定：靠 `painter.worldTransform()` 自己取缩放 ★

**约定 9**：工具叠加层里凡是有"屏幕尺寸"语义的东西（角柄、尺寸标签、
抓手、锚点等）都必须保持**固定的屏幕像素大小**。9px 的角柄若画在图像坐标下，
25% 缩放下只有 2px（点不中）、800% 下变成 72px（糊住半个画面）。

难点在于：`tools/` 层**不允许 include `ui/CanvasView.h`**（架构铁律 5），
拿不到 `imageToWidget()`。而为此新增一个 `AbstractTool::viewZoom()` 接口
是**不必要的扩张** —— 信息早就在手里：

```cpp
void CropTool::paintOverlay(QPainter &painter, CanvasView *)
{
    // ① 画图像坐标的东西（遮罩、网格）：直接用当前 painter 变换
    // ② 取一次变换，读缩放，然后 resetTransform() 切到控件坐标
    const QTransform t = painter.worldTransform();   // 此刻 == CanvasView 的 m_viewTransform
    const qreal zoom = qMax(0.01, qAbs(t.m11()));    // m11 可能带翻转的负号
    painter.save();
    painter.resetTransform();
    const QRectF rw = t.mapRect(m_rect);             // 用画布自己的矩阵映射，不自算 offset
    ...
}
```

要点：

- **口径必须来自 `painter`，不要自算** —— 视图的 `offset`/`zoom`/旋转/翻转
  组合起来就是 `m_viewTransform`，自己重算等于把 `rebuildViewTransform()`
  再实现一遍，迟早与画布不一致（旋转或翻转后偏移一个像素就是这类 bug）。
- 线宽同理：图像坐标下想画"屏幕上 1 像素"的线，写 `pen.setWidthF(1.0 / zoom)`。
- **`CanvasView` 调用 `paintOverlay` 时必须已经设好 `m_viewTransform`**
  —— 这是本方案成立的前提，已在 `drawToolOverlay` 的契约里（见 8.1 的铁律八）。

**守门断言**（`crop_test` [11]）：同一张离屏图上按 `zoom = 1.0` 与 `0.5`
各渲一遍，量**角柄所在像素**——两档下都必须是 255（整块白）。
若角柄被误画进图像坐标，0.5 档下它会缩成 4.5 像素，"整块白"立刻失败。

## 九、主窗口的装配顺序（`ui/MainWindow.*`）

> 这一章记的两个 bug 有个共同特征：**整体失效，却不报错、不崩溃、菜单还在**。
> 它们不在算法里，而在构造函数里各个 `setup*()` 的**调用次序**上 ——
> 编译器抓不到，其余每一组离线自检也都不建 `MainWindow`，
> 只有把程序真正跑起来、动手点一下才看得见。
> 守门断言是 `tests/mainwin_test.cpp`（`./run_tests.sh mainwin`，见 9.3）。

### 9.1 ★ 工具箱的按钮只能在工具注册完之后建 ★

`buildToolBox()` **必须**在 `ToolManager` 建好且所有 `addTool()` 完成之后调用。

踩过的写法：把它放在 `setupToolBars()` 的末尾。而构造函数里的顺序是

```
setupCanvas();      // 中央控件
setupToolBars();    // ← buildToolBox() 原在此处
setupTools();       // ← ToolManager 在这里才 new
```

于是 `buildToolBox()` 第一行的卫语句 `if (!m_toolsToolBar || !m_toolManager) return;`
直接返回 —— **工具箱一个按钮都没有**。不报错、不崩溃，用户只是找不到工具。

同族的坑：那处代码旁边原本还留着一句**写反了的注释**
（"setupToolBars 在 setupTools 之前被调用吗？不，顺序是 setupTools 之后"），
它让后面读代码的人**不会去核对真实顺序**。
→ 涉及初始化次序的注释，要连同**证据**一起写：
要么指向构造函数里那段顺序说明，要么写清"这里依赖 X 已经存在"。

### 9.2 ★ 信号传不了"现状"：先连接、再触发、最后显式同步一次 ★

`ToolManager` 在**连接建立之前**就已经改过两次活动工具：

1. `addTool()` 把第一个注册的工具设为默认活动工具并 emit 一次；
2. `loadAllOptions()` 恢复 `QSettings` 的 `tools/lastActive` 并 emit 一次。

原代码把 `connect(activeToolChanged, …)` 写在 `loadAllOptions()` **之后**，
两次 emit 全部落进真空 —— `CanvasView::m_activeTool` 停在 `nullptr`。

**症状**：打开程序后画布上**任何鼠标操作都没有反应**。
`CanvasView::shouldDispatchToTool()` 第一行就是 `if (!m_activeTool) return false;`，
而它上面的 `mousePressEvent` 只把事件交给活动工具。

**更麻烦的一点**：这个状态**用 UI 修不回来**。
`ToolManager::setActiveTool()` 发现"已经是这个工具"就 `return`（不发信号），
于是点工具箱里那个**已经选中**的按钮、按它自己的快捷键，全都是空操作。
用户必须先切到**别的**工具、再切回来才恢复正常。

**正确写法**（`setupTools()` 收尾，三步都在）：

```cpp
m_toolManager->loadAllOptions();               // ① 先触发（恢复上次的工具）

buildToolBox();                                // ② 建按钮（依赖工具列表，见 9.1）

connect(m_toolManager, &ToolManager::activeToolChanged,
        this, &MainWindow::applyActiveToolToUi);   // ③ 再连接

applyActiveToolToUi(m_toolManager->activeTool());  // ④ 连接后补一次"现状"推送
```

第 ④ 步不能省：**信号只能传达"变化"，传达不了"连接建立之前已经发生的事"**。
`applyActiveToolToUi()` 是唯一的同步入口（画布 + 选项条 + 工具箱选中态三处），
抽成函数而不是内联进 lambda，就是为了让"信号"与"补推"走同一条路径 ——
否则将来加一项同步只会改到其中一处，出现"启动时少这一项、切一次工具才有"的
诡异差异（而这种差异只有重启程序才观察得到）。

**通用形态**：任何"某个对象在构造期就改过状态、而 UI 要跟着它走"的地方，
都要问一句 —— **连接是在它第一次变更之前建立的吗？**
不是的话，就必须补一次显式同步。

### 9.3 唯一构造 MainWindow 的自检（`tests/mainwin_test.cpp`）

上面两个 bug 的共同点是"整体失效却不报错"，所以断言得这么写：

| 判据 | 为什么这样写 |
| --- | --- |
| 工具箱按钮数 **== ** `ToolManager::tools().size()`，且每个 id 都找得到 | 写死"6 个"的话，Phase 6 加工具就得改测试，最后会被人删掉；恒等式不会 |
| 画布的活动工具 **恒等于** ToolManager 的活动工具、且**非空** | 这是不变量，与"上次用的是哪个工具"无关 |
| 每轮往临时 QSettings 写**不同的** `tools/lastActive` 再构造窗口，检查画布/管理器/按钮三者一致 | 只试一个值只能覆盖一条路径；`move`（默认值，最容易被"早退"漏掉）、`brush`（中间）、`crop`（最后注册）各一条 |
| 弹出「图像」菜单（`aboutToShow`）后读「裁剪」的可用性 | 该项的启用状态**只在菜单弹出那一刻**刷新，不弹就永远读到初值 `true` |

两条工程上的注意事项：

- **QSettings 必须重定向到临时目录**（`QSettings::setDefaultFormat(IniFormat)`
  + `setPath(...)`）。否则测试会写进用户的真实配置，而且会**被用户上次退出时
  留下的 `tools/lastActive` 影响** —— 那种"随使用习惯时红时绿"的假失败最耗人。
  同理，每轮构造前先 `s.clear()`，"这一轮测的是哪个值"不能取决于上一轮。
- **含中文的动态串用 `qUtf8Printable`，不要用 `qPrintable`**。
  后者走 `toLocal8Bit()`，在中文 Windows 上是 GBK 字节；源码字面量却是 UTF-8，
  两者混在同一个日志里就会"一半正常一半乱码"，恰好把出问题那几条糊掉。
  **失败信息读不出来，断言的价值就打了折。**

**植入验证（实测，两条一起植入、分别看签名）**：

| 植入 | 结果 |
| --- | --- |
| 删掉 `setupTools()` 里的 `buildToolBox();` | [1] 组 9 项红，报「工具箱按钮数 == ToolManager 的工具数 期望 6，实际 0」 |
| 删掉连接后那次显式同步 | [2][3][4][5][6] 组 23 项红，报「画布拿到活动工具（非 nullptr）」等 |

合计 15 通过 / **32 失败**。顺带证明了第三条链式依赖：**画布没有活动工具时，
连"拖出选区"都做不到**（事件根本没被派发）——所以 [5][6] 两组也跟着红，
这正是"整体失效"的样子。

## 十、SVG 图标（`resources/` + `ui/IconLibrary.*`）

### 10.0 为什么图标配得上单独一章

图标会以**第三种"静默失效"**的形态出现，而且它比前两种更难看穿：

| 形态 | 编译器 | 自检 | 界面 |
| --- | --- | --- | --- |
| 菜单动作漏 `new`（第九章之前） | 0 错 0 警 | 全绿 | 菜单项凭空消失 |
| 装配顺序错（第九章） | 0 错 0 警 | 全绿 | 整箱为空 / 画布没反应 |
| **图标没加载进来（本章）** | 0 错 0 警 | 全绿 | **按钮上一片空白，或者退化成字母占位** |

前两种至少"东西没了"很显眼；图标失效最坑的地方是**它退化成一个合法但难看的结果**——
按钮还在、能点、功能正常，只是变丑了。如果你没盯着看，它能一路活到发布。

所以本章的每条规则都围绕同一句话：**"图标画出来了没有"必须有断言，
不能靠"我写了 `setIcon` 所以应该有"。**

### 10.1 ★ 关于图标的一切都只有一个来源：`resources/gen_icons.py` ★

```bash
python resources/gen_icons.py     # 生成 resources/icons/*.svg + 重写 resources/resources.qrc
```

`gen_icons.py` 里的 `ICONS` 字典是**唯一真相**（键 = 图标名）。它做三件事：

1. 按字典生成 24×24 的 SVG 文件；
2. **顺手 `ET.fromstring` 校验每个 SVG 是合法 XML** —— SVG 写坏（少个引号、
   标签没闭合）时渲染器只会画出一片空白，不会报错，这个校验是唯一能当场抓住它的地方；
3. 重写 `resources.qrc`。

**`resources.qrc` 和 `resources/icons/` 都是生成物，不要手改。**
手动加一个图标意味着"名字在磁盘上存在、但 qrc 里没有"，
而这类不一致**只有真去跑一次才会暴露**（见 10.5 的对账）。

所有图标共享同一套公共属性（`STROKE="#33393f"`、`stroke-width="1.7"`、
`fill="none"`、圆头圆角），这类属性抽在模板里而不是散在 73 个文件里 ——
否则"哪一张线宽不对"要靠眼睛在图里找。

### 10.2 ★ 必须显式 `QSvgRenderer`，绝不用 `QIcon(":/icons/x.svg")` ★

```cpp
// ✗ 千万不要这么写
QIcon icon(QStringLiteral(":/icons/file_new.svg"));

// ✓ 正确做法（ui/IconLibrary.cpp 里的 icon()）
QSvgRenderer renderer(path);
if (!renderer.isValid()) { /* 记一笔 + 返回空 QIcon，由调用方降级 */ }
```

**为什么 `QIcon(":/...")` 是陷阱**：它内部走 Qt 的图标引擎插件链。
**如果 `qsvg` 插件没被部署**（Release 打包时最容易漏），构造函数不会报错、
不会返回 null，只会给你一个**"合法但永远是空 pixmap"的 QIcon**。
`setIcon()` 兴高采烈地收下它，按钮上什么都没有，0 错 0 警。

显式 `QSvgRenderer` 把这件事变成**可判定的**：`isValid()` 是真是假，当场知道。
`IconLibrary` 因此可以分级降级：

```
icons::iconForTool(id)     → 工具箱首选（工具 id → 图标名是一张静态表）
     ↓ 空
tool->icon()               → 工具自己声明的图标
     ↓ 空
makeLetterIcon(name)       → 字母占位（最后一个兜底，保证按钮不会全空）
```

**降级链条必须真的存在**。只有"首选"而没有兜底，图标一旦失效就是空白按钮 ——
比字母占位更糟：用户连"这是个什么工具"都猜不出来。

### 10.3 ★ qrc 的 `prefix` 与 `<file>` 是"拼接"，不是"替换" ★

```xml
<!-- ✗ 错误：实际资源路径是 :/icons/icons/file_new.svg（多了一层） -->
<qresource prefix="/icons">
  <file>icons/file_new.svg</file>
</qresource>

<!-- ✓ 正确：:/icons/file_new.svg -->
<qresource prefix="/">
  <file>icons/file_new.svg</file>
</qresource>
```

这一条骗过所有人的原因是：**`rcc --list` 只打印 `<file>` 的原文**，
看起来完全正常；写错的 qrc 也能编过、也能链进 exe。
只有真的去问 `QFile(":/icons/file_new.svg").exists()` 才露馅。

首跑 `icon_test` 时 63 个图标**全部报"文件不存在"**就是这个原因。

### 10.4 ★ `.pro` 不能有 UTF-8 BOM —— 与源文件的要求正好相反 ★

| 文件 | BOM | 漏了的症状 |
| --- | --- | --- |
| `*.cpp` / `*.h` / `*.md` | **必须有** | MSVC 把中文源码当 GBK，报一堆莫名的 C4819/C2001 |
| **`.pro`** | **必须没有** | `qmake` 直接拒读：`Cannot read ...: Unexpected UTF-8 BOM` |

同一条"编码约定"在两类文件上要求相反，是因为它们的读者不同：
源文件由 MSVC 读（要 BOM 才认 UTF-8），`.pro` 由 qmake 自己的解析器读
（它不认 BOM）。**用脚本改 `.pro` 时要显式 `encoding='utf-8'`（即不带 BOM）**，
别顺手用会写 BOM 的方式。

### 10.5 ★ 引用 ⇄ 磁盘 ⇄ qrc 三方对账（`tests/action_check.py`）★

图标有三个"名字出现的地方"，它们必须一一对上：

```
MainWindowActions.cpp 里 icons::icon("file_new")     ← 引用侧
IconLibrary.cpp 里 工具 id → 图标名 的静态映射表        ← 引用侧
resources/icons/file_new.svg                          ← 磁盘侧
resources/resources.qrc 里的 <file>icons/file_new.svg</file>  ← 资源侧
```

`./run_tests.sh actions`（**不编译、秒回**）把上面四处扫一遍，输出：

```
引用的图标 73 个 / 磁盘上的图标 73 个 / qrc 里的图标 73 个
```

任何一边多出来或缺失都会报出来。**"磁盘上有、但没人引用"的孤儿图标只是警告不是错误**
——它可能是给下一个阶段预留的（Phase 6 的 8 个工具图标就是这种情况），
所以措辞是提示而非失败。

⚠️ **这条对账的盲区**：它验的是**名字**对得上，**验不出"这个 SVG 画出来是空白"**。
内容层面的问题归 10.6。

### 10.6 ★ 图标质量的量化判据 + 一张给人眼的接触表 ★

`tests/icon_test.cpp` 对**每一个**图标都量四项，阈值是这样定的：

| 判据 | 含义 | 阈值 | 抓的是什么 |
| --- | --- | --- | --- |
| `inkRatio` | alpha > 8 的像素占比 | ≥ 2% | **画出来是空白的**（路径写错、坐标跑到视框外） |
| `inkRatio` 上界 | 同上 | ≤ 72% | **糊成一坨黑块**（填充写错、图形叠满） |
| `inkBounds` | 非透明像素的包围盒 | ≥ 视框的 1/3 | **图标小得像颗沙**（路径尺寸算错） |
| `outerRingClear` | 最外一圈是否全透明 | 必须全透明 | **被裁角**（图形溢出 viewBox） |

外加一条定点核对（不只量比例，直接读具体像素）：`adjust_grayscale` 的右半
`(58, 48)` 必须 `alpha > 240`、左半 `(38, 48)` 必须 `alpha == 0` ——
**"半黑半白"这种语义，比例判据是看不出来的。**

`icon_test` 同时输出 **`tests/build/icons_contact_sheet.png`**：把全部 73 个图标
按 16/20/24/32/48 多档尺寸画在一张图上。

> **为什么量化断言之外还要有一张给人看的图**
> 断言能证明"不空白、不糊块、不触边"，**证明不了"它看起来像它该表示的东西"**。
> 实测抓到过三个只在这一步才露馅的：
> `help_qt` 画成了放大镜（当时是"环 + 斜杠"，和 `view_zoom_in` 撞形）、
> `tool_eraser` 像个菱形、`color_swap` 三个元素挤成一坨。
> 这三个的 `inkRatio` 全部合格。
> **接触表是"人来判断像不像"的唯一手段，别省。**

### 10.7 ★ 断言必须先证明它抓得住 bug（植入验证）★

图标自检本身也做过植入验证 —— 否则它就是一条"永远绿"的摆设：

| 植入 | 期望红 | 实测 |
| --- | --- | --- |
| SVG 内容清空（合法 XML，但无图形） | 空白 | ✓ `inkRatio` 判红 |
| 图形改成 `x=2 y=2 w=24 h=24` 实心（**部分**溢出视框） | 触边 + 糊块 | ✓ 两条同时红 |

⚠️ **第一次植入选错了变体**：写的是 `rect x=-4 y=-4 w=32 h=32` 且 `fill="none"` ——
整个框在视框之外、又没有填充，**画出来真的是空白**，于是报的是"空白"而不是
"触边"。这说明**植入必须朝着你想验证的那条断言去设计**，
不然你验证的是另一条规则。

**主窗口侧的两条图标不变量也各植入了一次**（`.buildlog/implant_mainwin_icons.py`）：

| 植入 | `action_check`（静态对账） | `tests/mainwin_test.cpp` [7] 组 |
| --- | --- | --- |
| **A** 把某菜单动作的图标名改成 `adjust_levels_TYPO` | ✓ 红：`[错误] 代码里用了图标 …_TYPO，但 resources/icons/…_TYPO.svg 不存在`，并额外警告 `adjust_levels.svg` 成了孤儿图标 | ✓ 红：`每个有名字的菜单动作都有图标 —— 缺图标：actionLevels` |
| **B** 丢掉 `iconForTool()`，让工具箱退回字母占位 | ✗ **抓不到**。静态检查看不见"接线"这种东西 —— 这正是这条不变量必须由 mainwin 测试来守的原因 | ✓ 红：`工具箱按钮上的图标就是该工具的专用图标` |

合计 **54 通过 / 2 失败**。最值得注意的是 B：**字母占位是一个合法且非空的 `QIcon`**，
所以"`!action->icon().isNull()`"这种弱断言对它**完全无效** ——
必须比 `QIcon::cacheKey()`（"是不是 `iconForTool(id)` 那张图"）。
凡是"预期值本身可能是某个合法的降级结果"的地方，都不能只判非空。

⚠️ 植入脚本自己也有坑：**必须在替换前断言锚点唯一**（`s.count(old) == 1`），
并且**用 `shutil.copy2` 备份、跑完还原后 `diff` 校验逐字节一致**。
上一轮就踩过"还原脚本逻辑写错、磁盘上的文件其实还是植入态"——
那种情况下你会拿着一份被改坏的源码继续往下做，而且所有测试都在报红，
很容易误判成"我新加的功能有 bug"。**还原也要有断言。**

### 10.8 覆盖范围

| 区域 | 数量 | 说明 |
| --- | --- | --- |
| 工具箱 | 8 个在用 + 6 个预留 | 预留的是 Phase 6 剩余的 `line/rect/ellipse/text/hand/zoom` |
| 菜单 | 48 个条目 | 含 2 个子菜单（`menu_recent` / `menu_panels`）——**子菜单也是 QAction，一样能挂图标** |
| 图层面板 | 15 个 `layer_*` | 8 个底部按钮 + 行内的眼睛/锁（可见/隐藏、锁/解锁两态各一张） |
| 合计生成 | **73 张 SVG** | |

工具 id（`QSettings` 持久化的键）→ 图标名的映射写死在 `IconLibrary.cpp` 的静态表里。
**工具 id 不能为了图标改名** —— 改了用户上次用的工具就丢了。

### 10.9 截图工程（`.buildlog/shot/`）必须带 `svg` 模块

`.buildlog/shot/shot.pro` 的 `QT +=` 里必须有 `svg`：

```qmake
QT += core gui widgets svg
```

漏了会在编译期就报 `C1083: 无法打开包括文件: "QSvgRenderer"` ——
**这其实是好事**：比运行时静默出空图标强得多。
（`ZlPhotoEdit.pro` 里的 `QT += svg` 是早就有的，所以主工程没暴露这个问题。）

另外它必须 `RESOURCES += resources/resources.qrc`。**截图工具不链 qrc 的话，
截出来的界面"看起来没报错"，但工具箱会静默退回字母占位** ——
你会拿着这张图去确认"图标没问题"，结论正好是反的。

截图工具现在有 `menushot` 模式，把 8 个下拉菜单**真的 `popup()` 再 `grab()`**，
逐个打印"带图标 N/M"：

```
  文件(&F) 259×200  带图标 6/7
  编辑(&E) 357×200  带图标 7/7
  ...
```

这是**唯一**能验证"图标不只挂在 QAction 上、而且真的画出来了"的手段
（`!a->icon().isNull()` 在"图标名写对但 qrc 没编进来"时**照样为真**）。

## 十一、图层面板（`ui/LayerPanel.*`）

### 11.0 为什么它要单独一个类、单独一章

面板里的东西**全都是"画出来 / 点上去"的**，而它又自带一整套状态：行序映射、
行内热点、属性控件回填抑制、缩略图节流。这一类状态的共同点是 **编译器一句话
都不会说**：行序反了照样编过，热点点偏了照样编过，缩略图不刷照样编过。

所以规则只有一条，但它要贯彻到每一处：**凡是"看不见的映射"，都抽成不依赖控件
的纯函数，然后给它一条能证伪的断言。**

`LayerPanel.h` 里的 `namespace layerpanel` 就是这些纯函数：行序换算、
`dropRowToTargetIndex()`、`eyeRect/lockRect/nameRect`、`hotspotAt()`。
它们不起窗口、不建 `QApplication`，`tests/layer_panel_test.cpp` 直接断言。

> 另一个理由纯粹是可读性：`MainWindowActions.cpp` 已经一千多行，面板那一整套
> 塞进去会把那个文件的阅读顺序彻底打乱。

### 11.1 ★ 视图行序 ⇄ 文档索引：倒序，全工程只准换算两次 ★

```
Document 索引 0        = 最**底**部图层，索引越大越靠上
面板第 0 行            = 最**顶**部图层
                      → row = count - 1 - index
```

这是本章最容易被写反、写反了又最不容易被发现的一处。忘了倒序的表现是：
**"上移图层"在界面上看着往下走** —— 不报错、不崩溃、逻辑上每一步都"成功"了。

全工程只有 `layerpanel::rowToLayerIndex()` / `layerpanel::layerIndexToRow()`
两个地方允许做这个换算，其余任何地方（含 `MainWindow` 的槽、delegate、
`LayerListWidget::dropdown`）都必须调它们。

**守门断言**（`layer_panel_test` [1] 组）：对 `count = 1..9` 的**每一个**行数，
逐行验证两个函数的**互逆性**，并钉死行 0 ⇄ 索引 `count-1`。

### 11.2 ★ 面板只发信号，绝不改文档 ★（与 §5.6 裁剪同一条纪律）

唯一例外是**活动图层索引** —— 它是纯 UI 状态，不进撤销栈。其余一切改动图层
内容或元数据的操作，面板一律 `emit` 信号出去，由 `MainWindow` 包装成
`LayerCommand` 压栈。这样换来两件事：

1. **撤销/重做只有一条路径**，不可能有"某个入口漏了包装"；
2. 面板可以**在没有 `CommandStack` 的情况下单独构造**（自检正需要这个）。

**反向断言**（`layer_panel_test` [5] 组）：点一下眼睛 →
① `visibilityToggled` 必须**发出**；② `Document` 里那一层的可见性**必须没变**。
只验 ① 的话，"面板自己顺手改了"这种错法照样全绿。

### 11.3 ★ 自绘行的热点：绘制与命中必须共用同一组矩形 ★

行是 `LayerItemDelegate` 自绘的（**不能用 `setItemWidget`** —— 那样项就不能
拖拽排序，`InternalMove` 会在拖动时销毁重建项、子控件随之丢失）。代价是
"眼睛 / 锁点哪儿"要自己算，于是：

- `eyeRect() / lockRect() / nameRect() / thumbnailRect()` 是**纯函数**，
  delegate 的 `paint()` 与 `hotspotAt()` **共用同一套数字**。
  分开写两份的话，改一个忘一个，症状是"眼睛图标画在这里、点了没反应"。
- 三个矩形**两两不重叠**（含边界像素），且 `hotspotAt()` **从右往左判**
  —— 让可点击的小目标（眼睛/锁）优先于大面积的缩略图/名字区。

**守门断言**（`[2]` 组）：对每个矩形取"内缩 1px 的四个角 + 中心"共 5 点验归属，
再专门验"矩形边界上的像素归属唯一"。

### 11.4 ★ 拖拽落点：`QList::move` 的 `to` 是"取出 `from` 之后"的坐标 ★

`dropRowToTargetIndex(srcIndex, dropBeforeRow, layerCount)` 里有两个坑叠在一起：

1. 落点指示线给的是**视图行**，要先按 11.1 换成文档索引；
2. `QList::move(from, to)` 的 `to` 是"**把 `from` 取出来之后**"的坐标 ——
   源项原本在落点**之上**时，插入位置要往前挪一位。

**守门断言**（`[3]` 组）：4 层 × 5 个落点（含两份边界）**每一组都真的调一次
`Document::moveLayer()`**，再对比结果层序与"按落点算出的期望层序"。纯函数
单测这里不够 —— 一定要跟真实的 `moveLayer` 对拍，否则纯函数自洽、整体还是错的。

### 11.5 ★ 缩略图节流：是节流（throttle），不是防抖（debounce）★

画笔每落一笔都会 `contentChanged`。若每次都重渲缩略图，一屏几十行 × 每笔一次
= 明显掉帧。所以用一个 `QTimer`：

```cpp
// 节流：计时器已经跑着就不再 restart，让它自然到期
if (!m_thumbTimer->isActive()) m_thumbTimer->start();
```

写成防抖（`restart()`）的话，**连续画的时候计时器永远不到期**，缩略图在停笔前
一直不刷新 —— 用户看到的是"缩略图卡住了"。

**守门断言**（`[8]` 组）：连打 20 次 `contentChanged`，
`thumbnailRenderCount()` 增量必须 **≤ 1**。并且"连打"之后再等一个窗口，
计数要 +1（证明不是"永远不刷"）。

⚠️ **量这条之前必须先把计时器清干净**：`setThrottleIntervalMs(60000)` 会重排
计时器。第一版断言直接读计数，读到的是**上一次用例的残留**，假绿。

### 11.6 ★ 自绘行必须"量它画出来的像素" ★（与 §8.3 同源）

`grab()` 列表视口 → 数像素。`layer_panel_test` [6] 组四条：

| 判据 | 抓的是什么 |
| --- | --- |
| 第一行缩略图里红色占比 > 60% | 缩略图没画 / 画错行 / 通道串了 |
| 点眼睛前后该行区域**差异像素 ≥ 120** | 眼睛图标没画出来（路径错、qrc 没编进去） |
| 点锁前后该行区域**差异像素 ≥ 120** | 锁图标同上 |
| 隐藏那行的名字区**变淡** | 缺"隐藏态"。**这条需要字体** |

> ★ **offscreen 平台没有字体** ★。Qt 5 起不随包分发字体，离屏渲染时文字被画成
> 一片空白 —— 于是"变淡"的前后两张图**完全一样**，断言莫名其妙地红。修法是给
> `main()` 设 `QT_QPA_FONTDIR=C:/Windows/Fonts`（仅当该目录存在时）。
> 凡是要量**文字**像素的断言，都要先想到这一条。

### 11.7 ★ 面板 ⇄ 文档的同步不能靠"我以为" ★

`[4]` 组：面板行数、行序、活动行、混合模式/不透明度控件的显示值，
必须与 `Document` 逐项一致；**换一份文档**（`setDocument`）后不能串扰
（旧文档的信号不许再改新面板），所以 `bindDocument()` 里要先断旧、再接新。

`[7]` 组：**回填不反改文档** —— 把控件设成某值后，`Document` 必须没变。
`m_syncing` 这个抑制标志一旦漏了，就会出现"程序启动时图层不透明度被悄悄改成
50%"这类**不报错、只改数据**的 bug。

### 11.8 本轮抓住的两个真 bug（都在 `Document`，不在面板）

面板接上之后跑 `mainwin_test`，当场红了两组 —— 都是**面板本身没错、
`Document` 的合并逻辑错了**：

**① `mergeLayerDown()` 方向写反**

```cpp
upper = layer(index + 1);   // ✗ 把"上面那层"当成了当前层
lower = layer(index);
```

正确是 `upper = layer(index)`、`lower = layer(index - 1)`。写反之后
"向下合并"实际是"把下面那层合到上面去"，**画面上看不太出来**（两次合并的
内容差不多），但"哪一层的属性被保留"全错。

顺手修掉一个隐含错误：下层的不透明度原先没被烘进结果 ——
**先把下层按其不透明度合成到透明底上**，结果层回到 100% / Normal。

**② `mergeVisibleLayers()` 的落点算在错误的时刻**

结果层应插在"**原可见层里最靠下的那一层**"的位置上，但原实现是在**删掉所有
可见层之后**才用旧的 `insertAt` 数隐藏层 —— 索引已经偏了。修法是把计数移到
删除**之前**。

> 这两条都符合本章开头那句话：**数学看着对、结果全错，编译器一句话不说。**
> 抓到它们的是 `mainwin_test` 里"合并方向"与"隐藏层不被吃"两条**不变量**式
> 断言（不是写死某个具体层序）。见 §9.3 的断言写法说明。

### 11.9 静态对账的一个盲区修正：图标以"三元字符串字面量"被引用

`LayerPanel.cpp` 里眼睛/锁的图标名是这么写的：

```cpp
const QString name = visible ? QStringLiteral("layer_visible")
                             : QStringLiteral("layer_hidden");
```

`tests/action_check.py` 原来只扫 `icons::icon("…")` 形式的调用，于是这 6 个
（`layer_visible/hidden/lock/unlock/blend/opacity`）被判成**孤儿图标** ——
而"孤儿"的建议动作是"删掉它"。真要照着做，眼睛和锁就会**静默消失**。

修法：把图标引用拆成两档。

| 档 | 扫描范围 | 参与哪条判定 |
| --- | --- | --- |
| `referenced_hard` | `icons::icon/pixmap()` 调用 + `iconForTool()` 静态映射表 | **错误**（"文件不存在"） |
| `referenced_soft` | `src/` 里**全部**字符串字面量匹配图标名 | **警告**（"孤儿"） |

判"文件不存在"必须用 hard（否则字面量里偶然出现的同名词会掩盖错字）；
判"孤儿"要用 soft（否则会误导人去删还在用的图标）。

### 11.10 视觉证据：截图工具的 `layers` 模式

断言能证明"行序没反、图标画上去了"，**证明不了"这一栏排得好不好看、
信息够不够读"** —— 与 §10.6 的接触表同一个道理。所以
`.buildlog/shot/shot_main.cpp` 有一个 `layers` 模式：走用户路径建三层、
每层画一个错开的圆、经面板控件设"正片叠底 + 70%"、再经面板信号锁一层隐藏一层，
最后 grab **面板单张**（`layers_panel.png`）与**整窗**（`layers.png`）各一张。

它自己会打印自证信息（行序、每行文本、按钮图标缺失数）：

```
图层面板：3 行，活动行 = 1
  第 0 行「隐藏的高光」索引 2
  第 1 行「柔光多边形」索引 1
  第 2 行「底色圆」索引 0
面板按钮 8 个，其中没有图标的 0 个
```

> ★ **踩到的坑**：`shot` 是用"mode 名字 → 菜单动作名"的**通用兜底分支**
> 处理对话框类截图的（`levels` → `actionLevels`）。这个兜底写在 `layers`
> 专用分支**之前**，于是 `layers` 被它先吃掉，去找并不存在的
> `actionLayers`，报"找不到动作" —— 而真正的分支就在下面躺着。
> 修法：在兜底分支里维护一张 **保留模式表**（`kReservedModes`），
> **新增专用模式时必须同步这张表**。
> 通用兜底的通用形态是：**它什么都能接，所以必须显式排除专用分支。**

## 十二、绘制工具：油漆桶 / 吸管（`tools/BucketTool` `tools/ColorPickerTool`）

### 12.0 为什么这两个工具值得单独一章

它们**不写新算法**：填充走 `engine/Fill`（扫描线 + 容差 + 覆盖度蒙版），
合成走 `engine/Brush` 的 `composeStroke`（§三），取色就是读一个像素。
真正会错的地方全在**算法之外**，而且全都属于"不报错、只是结果不对"：

| 错法 | 症状 | 怎么发现的 |
| --- | --- | --- |
| 判据取错了图层 | 填出来的形状与看到的边界对不上 | 肉眼，需要刚好有透明层 |
| 描边编号撞号 | 两次点击算一步撤销 | **完全看不见**，只能靠断言 |
| 写回时二次预乘 | 半透明内容整体压暗 | 只在透明画布 / 柔边上露出来 |
| `QColor(qRgba)` 丢 alpha | "不透明度 50%" 变成 100% | **完全看不见**，只能靠断言 |
| 工具箱顺序插错位置 | 用户要跨过两个按钮才能从画笔走到油漆桶 | 肉眼，但没人会去数 |

后两类"完全看不见"的错误正是 `tests/tool_paint_test.cpp` 存在的理由。
它和 `tests/fill_test.cpp` 的分工是：**fill_test 管算法，tool_paint_test 管接线**。

### 12.1 ★★ 撤销粒度：`DrawCommand` 的描边编号必须由调用方显式给出 ★★

这是本轮抓到的最严重的一个 bug，形态非常典型，值得完整记下来。

**背景**：`DrawCommand` 用 `id()` 参与 `QUndoStack` 的合并判定 ——
id 相同的相邻命令会被 `mergeWith()` 合成一条。画笔想用它实现
"一次按住拖动的全部中间状态 = 一步撤销"。

**错法**：构造函数里写的是

```cpp
, m_strokeId(currentStrokeId())      // ← 取"最近一次分配出去的编号"
```

而 `beginStroke()` —— 也就是**唯一会推进编号计数器的函数** ——
全工程**没有任何地方调用过**（`grep` 确认）。于是：

1. 每条 `DrawCommand` 拿到的编号都是同一个常量 `0`；
2. 于是 `id()` 全部相同；
3. 于是 `QUndoStack` 认为"这些是同一次描边"，调用 `mergeWith()` 合并；
4. 于是**连点两下油漆桶，撤销栈里只有一条记录**，`Ctrl+Z` 一次把两处都撤掉；
5. 画笔同理：**画两笔算一步**。

编译 0 错 0 警，其余 1114 项自检全绿，运行期没有任何提示。
**"一次点击 = 一条撤销记录"这句承诺，在代码里其实一天都没有成立过。**

**修法**：把"取新编号"收进一个具名工厂，并让构造函数**必须**接收编号。

```cpp
// DrawCommand.h
DrawCommand(Document *doc, int layerIndex, const QRect &rect, int strokeId, …);

// "一次点击 / 一笔 = 一条撤销记录"的唯一入口
static DrawCommand *standalone(Document *doc, int layerIndex, const QRect &rect,
                               const QImage &before, const QImage &after,
                               const QString &text);
```

`standalone()` 内部调 `beginStroke()` 取一个**新**编号，所以调用点
不需要记得"先开启新描边"。同时**删掉 `currentStrokeId()`** ——
它那副"当前描边号"的长相就是这次事故的全部原因；
留着一个能安静地用错的接口，比没有接口更危险。

> ★ **一般形态** ★
> "某个字段由构造函数自己从一个全局量里推出来"是一种值得警惕的写法：
> 它把一个**调用方必须做的动作**（开启新描边）藏进了对象内部，
> 而调用方看不到这个义务，编译器也不会提醒。
> 判断标准很简单：**这个推导有没有一个明确的、文档写着的调用约定？**
> 有 → 那它就是可以被忘记的，改成显式传参或具名工厂；
> 没有 → 那它推出来的东西本身就没有意义。
> 同类的还有 §5.6（内存预检不能有第二个入口）与 §11.2（撤销只有一条路径）：
> **凡是"必须做且容易忘"的事，都要让它要么只在一个地方发生，要么编译器不允许忘。**

### 12.2 ★★ 合成管线写回的是预乘量：不要再乘一次 alpha ★★

`engine/Blend.cpp` 的单层合成 `compositeLayer()` 里，逐像素算出
`mixR/mixG/mixB` 之后，原先写的是 `mixR * finalA` —— **多乘了一次 alpha**。

推导（非预乘用大写、预乘用小写，均归一化到 0-1）：

```
source-over 的定义：        Co·Ao = Sr·Sa + Dr·Da·(1-Sa)
代码里算的是：       mixR = br·ea + (dr·da)·(1-ea)
                            ↑ dr·da 就是下层的预乘颜色
所以 mixR 已经是"结果的预乘颜色"，直接 ×255 即可。
```

**症状**：只要结果的 alpha 不是 255，颜色就会被压暗到原来的 `outA` 倍。
实测（探针，1 张 4×4 图）：

```
图层位图  raw a=128 r=128     ← 反预乘后是纯红、alpha 128
合成之后  raw a=128 r=64      ← 红被减半了
```

也就是"半透明的纯红"在画面上显示成"半透明的暗红"。

**为什么能潜伏这么久**：目标不透明时 `outA == 255`，这一步退化成乘 1。
只有**透明画布**（新建文档的默认底色）与**柔边笔迹**才会露出来 ——
而这两处的偏差都很容易被当成"就这样"。

> ★ 预乘空间的两条纪律（与 §1.1 的 LUT 侧正好相反）★
> · **合成类**运算在**预乘空间**做：`A·B` 这类公式在预乘下是线性的，
>   不预乘反而要在每个像素上做一次除法（还要特判 alpha 0）。
> · **写完就不要再乘一次 alpha** —— 判断依据是"这一项最终是不是要存进
>   预乘位图"。是 → 别再乘；不是 → 在写回前乘一次，且**只乘一次**。
> · 遇到"半透明内容颜色不对"时，第一个要量的就是
>   **图层位图的原始预乘字节**与**合成结果的原始预乘字节**哪个对不上，
>   不要只盯着合成公式看（那个公式两种写法都"看起来对"）。

### 12.3 ★ 油漆桶的判据取自活动图层，吸管取自合成图 ★

两个工具取的是**相反**的图，这不是不一致，而是它们回答的问题不同：

- **吸管**回答"我看到的这个点是什么颜色" → `Document::composite()`。
  取活动图层的话，在透明处取到 `(0,0,0,0)`，而用户明明看到红色（在下面那层），
  于是"取到的颜色和看到的不一样"，没有任何报错，只是手感不对。
- **油漆桶**回答"在**这一层**上，哪些像素与起点算同一块区域" → 活动图层。
  取合成图的话，区域边界里可能包含"下层内容造成的边界"，
  而上层根本没有那个边界 —— 填出来的色块会**溢出用户看到的图形的边**。

代价（也是正确行为）：在空图层上点油漆桶会填满整层 ——
因为"这一层"确实处处同色，这正是"把这一层填成某个颜色"。

`tests/tool_paint_test.cpp` 的 [4] 组是唯一能一眼区分两者的构造：
**活动层整层透明、下层左右两半不同色**。取自活动层 → 填满整张画布；
取自合成图 → 只填左半边。

### 12.4 ★ 新工具要同步的清单（少一处就静默少做事）★

注册一个工具要动四个地方，**任何一个漏掉都不会编译报错**：

1. `src/ui/MainWindow.cpp` → `setupTools()` 里 `addTool(new XxxTool(...))`。
   **工具箱的按钮顺序 = 注册顺序**（`buildToolBox()` 遍历 `tools()`）。
   绘制类工具要挨着画笔橡皮放，别插到选区后面去。
2. `ZlPhotoEdit.pro` → `SOURCES` + `HEADERS`（qmake 不认通配符；
   漏 `HEADERS` 只在**链接期**报 `LNK2001 metaObject`）。
3. `run_tests.sh` → `mainwin` 分支的**源文件清单**，以及 `moc_headers_for()`
   的 `mainwin_test` 清单。
4. 若新工具自己有测试 → `run_tests.sh` 里的**三处**（见文件头注释）。

另外，`iconForTool()` 里必须有该 id 的映射、`resources/icons/tool_<id>.svg`
必须存在且在 qrc 里 —— 这一条由 `mainwin_test` 的 [7] 组自动盯住
（它比"有没有图标"更严：比的是 `cacheKey()`，能识破工具箱的字母占位图兜底）。

### 12.5 两个实测结论（都反直觉，都值得直接背下来）

```
QImage::fill(const QColor &) 在 ARGB32_Premultiplied 上**不做预乘**。
  fill(QColor(255,0,0,128)) → 位图原始值 (128,0,0,128)
  fill(QColor(128,0,0,128)) → 位图原始值 (128,0,0,128)
两者落下的字节完全一样。测试要精确控制预乘值时，
**直接往 scanLine 里写 qRgba**，不要靠 QColor 猜。

QColor(QRgb) 这个构造函数会把 alpha 丢掉、置成 255。
  QColor(qRgba(1,2,3,128)).alpha() == 255     ← 而 QColor(1,2,3,128).alpha() == 128
所以"取色""填充色"这类地方一律用 QColor(r,g,b,a) 四参构造，
或者 QColor::fromRgba()。这条已经在 fill_test / tool_paint_test / BucketTool /
ColorPickerTool 四处的注释里各钉了一遍。
```

## 十三、形状工具：直线 / 矩形 / 椭圆（`engine/Shape.*` `tools/ShapeTool.*`）

### 13.0 为什么三个工具挤成一个类

`LineTool` / `RectTool` / `EllipseTool` 的交互骨架**逐字相同**：
按下取锚点 → 拖动按 Shift 约束、重算蒙版、重绘预览 → 松手压一条命令。
三个类会把同一个状态机（锚点、上一帧包围盒、拖动快慢节流、取消/提交）
抄三遍，而三份副本一旦分叉就只会在某一个工具上表现异常。
所以落成**一个 `ShapeTool` 承载三个 Kind**，唯一的差异是 `buildMask()`
（直线用 `constrainTo8Directions`，矩形/椭圆用 `rectFromDrag`）。
**判据：如果两个类的成员函数逐个同名、只有一两个函数体不同，它们就该是一个类加一个枚举。**

### 13.1 ★★ 蒙版取 alpha 通道，绝不用 `convertToFormat(Grayscale8)` ★★

形状要参与合成，得先变成一张**覆盖度蒙版**。直觉写法是把抗锯齿渲染到
ARGB32_Premultiplied 临时图，再 `convertToFormat(QImage::Format_Grayscale8)`。
**这会静默地把抗锯齿抹掉**：转灰度时 Qt 可能**先反预乘**，
于是一个"50% 覆盖的白像素"（预乘位图 `a=128 r=128`）反预乘后得到纯白，
灰度化后是 **255** —— 边缘全是实心，抗锯齿消失，而没有任何报错。

正确做法只有一个：**逐像素取 alpha 通道**。alpha 在预乘格式里
**就是覆盖度**，语义唯一、无需换算。

> 这与 §1.1「半透明像素查表要先反预乘」是**同一枚硬币的两面**：
> 那里是"反预乘"该做而漏做，这里是"反预乘"不该做却被动做了。
> 共同的教训是 —— **预乘格式的每一步转换都要问一句"它内部替我做了哪一步"。**

自检里有一条专门的判据：蒙版边缘必须存在 `0 < 值 < 255` 的过渡像素，
而不是非 0 即 255。

### 13.2 ★★ 拖动预览必须幂等：每次都从落笔前的整层快照重算 ★★

形状拖动期间**直接写图层真实像素**做预览（这样用户拖到哪就看见哪，
不需要额外的叠加层）。但**绝不能**在上一帧的结果上继续画 ——
那样每一次 `mouseMove` 都在累积：手在同一位置多抖动几次，
半透明笔迹就会一层层叠深，松手时颜色比预览第一帧深得多。

纪律与画笔完全一致：**落笔时取一份整层浅拷贝（`m_snapshot`）+ 选区快照，
之后每一次重算都从这份快照出发**，只重写"区域"内的像素。于是
"重算 N 次"与"重算 1 次"结果逐位相同。自检里有一条断言专门钉它：
反复对同一段拖动重算 5 次，结果必须一模一样。

### 13.3 ★ 重算区域 = 上一帧包围盒 ∪ 本帧包围盒 ★

形状拖动时"区域"指用户可在其上看到变化的矩形。若只按**本帧**包围盒重算，
用户把矩形从左上拖到右下时，**左上那一块旧框不会被覆盖回去**，留下残影。

所以 `m_prevBounds`（上一帧）必须参与：`region = m_prevBounds.united(mask.bounds)`，
重算后 `m_prevBounds = mask.bounds`。`embedMask()` 负责把局部坐标的蒙版
搬进区域坐标系（其余位置显式清 0 —— 不清就会把区域里别处的像素带进来）。
自检的植入验证 A（区域只取本帧）就是专门证明这条断言抓得住残影。

### 13.4 ★ 同一产品规则要写进每一处它适用的地方 ★

首批油漆桶定过一条产品规则：**"点一下不拖动 = 没有产物"**
（不留痕、不压命令）。矩形与椭圆实现了它（零面积不画），**直线漏了** ——
两点重合时圆头笔帽画出一个实心小圆点，白底上点一下就留个红点，
还压了一条撤销记录。

`rasterizeLine` 因此补上 `|Δx| < 0.5 且 |Δy| < 0.5 → 返回空蒙版`，
与矩形/椭圆对齐。教训：**产品规则不是"每个工具各自实现一遍"，
而是"每一处适用的地方都必须写"——漏一处就是一个只有用户点得出来的 bug**
（自检当初也没覆盖，是补断言时才发现的）。这与 §9 的"新增一个工具要动的清单"
是同一个思路：**规则也要有一张"它应该出现在哪些文件里"的清单。**

### 13.5 新工具同步清单（在 §12.4 之外，本批新增两条）

除 §12.4 的四处（`MainWindow::setupTools()` 注册、`.pro` 的 SOURCES/HEADERS、
`run_tests.sh` 的分支与全量清单、图标映射 + qrc）之外，形状工具还多了两条：

1. **快捷键轮换**：矩形与椭圆共用 `U`，轮换算写在
   `MainWindow::activateToolByShortcut`，与 `M` 键轮换两种选区同构 ——
   注意**必须显式排除 `Line`**，否则它会走"轮换"分支而永远切不到直线
   （见总纲"通用兜底分支必须先排除专用模式"）。
2. **颜色推给工具**：`tools/` 层不依赖 `ui/` 层，所以前景/背景色由
   `CanvasView` 在"工具被激活"与"用户改色"两个时机**推**给工具
   （`setForegroundColor` / `setBackgroundColor`）。形状工具里
   前景色 = 线/描边，背景色 = 填充 —— **别在诊断脚本里绕过主窗口直接设色**
   （§12.7 坑②）。

## 十四、视图导航工具：抓手 / 缩放（`tools/HandTool.*` `tools/ZoomTool.*`）

### 14.0 为什么这两个工具单独成章

它们**不改一个像素**，却比任何绘制工具都难写对 —— 因为它们的输入输出全是
“坐标”，而工程里同时存在**两套坐标系**（图像坐标 / 控件坐标）。
绘制工具错了是“画歪了”，看得见；这两个错了是“拖不动”、“缩放到 2000 倍”、
“点了没反应”，**全都是静默的**，肉眼不一定归因到坐标系。
所以本章的主题只有一个：**哪个量属于哪个空间**。

两个工具都只发信号，实现在 `CanvasView`（`panBy` / `setZoomAt` / `zoomToRect`），
分层与 §5.6 裁剪、§11.2 图层面板同源：**工具表达意图，不实现行为**。

### 14.1 ★★ 请求信号的实参属于哪个坐标空间，必须在名字里写死 ★★

`AbstractTool` 上的三个视图请求信号，各自锁死一个空间：

| 信号 | 实参 | 空间 | 实现 |
| --- | --- | --- | --- |
| `requestPan(QPointF delta)` | 平移增量 | **控件坐标** | `CanvasView::panBy` |
| `requestZoom(qreal factor, QPointF anchor)` | 缩放倍数 + 锚点 | **控件坐标**（锚点 = 鼠标此刻的控件点） | `CanvasView::setZoomAt` |
| `requestZoomToRect(QRectF rect)` | 待铺满的目标 | **图像坐标** | `CanvasView::zoomToRect` |

**三条踩过的坑，全部来自“实参空间没写死”：**

1. `requestZoom` 的第二参数最初叫 `imageAnchor`（图像锚点），照着实现写
   `setZoomAt(factor, imageAnchor)` —— **800% 缩放下锚点完全不对**。
   锚点在物理上只能是“**鼠标此刻在控件里的位置**”，因为放大后要保持
   “鼠标底下那个像素不动”，而鼠标给的就是控件坐标。→ **改名 `anchorWidget`**，
   并在 `AbstractTool.h` / `CanvasView.h` 两边都写注释。
2. `requestPan` 的 delta 若用图像坐标算，`m_offset`（本身就是“图像原点在控件里的位置”）
   是控件量，**两个空间直接相加 = 怎么拖都不动**（高缩放下尤其明显）。
3. `requestZoomToRect` 是唯一**图像坐标**的 —— 因为它的语义是“框住图像的一块区域”，
   与屏幕上显示多大无关。

> ★ **教训**：一个函数的参数叫 `delta` / `anchor` / `rect` 是**不够的**。
> 只要工程里有两种坐标系，**参数名里必须带空间后缀**（`…Widget` / `…Image`），
> 不然下一个人（包括三个月后的自己）一定会拿错的传进去，而且不会报错。

### 14.2 ★ 平移增量 = 本次 − 上一次位置，不是 本次 − 按下点 ★

抓手拖动时，每次 `mouseMove` 发出的必须是**相对上一帧的增量**：

```cpp
const QPointF delta = e.widgetPos - m_lastWidgetPos;   // 增量
m_lastWidgetPos = e.widgetPos;                         // ★ 顺序不能颠倒
emit requestPan(delta);
```

若写成 `e.widgetPos - m_pressPos`（相对按下点），每一次事件的位移都是**累计值**，
而 `panBy` 又把它当增量再累加一次 → **位移平方级加速**，手指一动画面直接冲出屏幕。
这类错误的特征是“**拖一点点就飞了**”，而不是“拖不动”，同样是归因困难。

**且必须用控件坐标算增量**：`widgetPos` 与 `m_offset` 同空间，直接相加即可。
（自检里还专门有一条“抓手与缩放无关”：**改缩放比不改变同一段控件位移对应的平移量**。）

### 14.3 ★ 框选阈值必须用控件坐标；退化必须回落成单击 ★

缩放工具的“点按放大 / 拖框放大”由一个阈值区分，两个坑各占一头：

- **阈值判定用控件坐标**（`qMax(|dx|,|dy|) < 6.0`，`marqueeThreshold()`）。
  用图像坐标判阈值的话，**放大 800% 时“手抖 1 像素”就能触发框选**，
  而缩小到 10% 时“拖半个屏幕”才勉强够 —— 手感随缩放漂移。
- **退化回落**：拖了超过阈值、但图像矩形**宽或高 < 1 像素**时，
  **必须回落成单击放大**，而不是：
  - 发 `requestZoomToRect` —— `zoomToRect` 会算出**几千倍**的缩放（除以近零宽度）；
  - **什么都不做** —— 用户看到的是“点了一下没反应”，像卡死。

```cpp
if (m_marqueeActive && r.width() >= 1.0 && r.height() >= 1.0)
    emit requestZoomToRect(r);
else
    emit requestZoom(zoomsIn(alt) ? kZoomStepFactor : 1.0 / kZoomStepFactor,
                     m_pressWidgetPos);
```

> ★ 这条与“通用兜底分支会吃掉专用分支”（§三类静默失效之三）是**同一族**错误：
> 这里的 `else` 分支如果写成“无脑发框选”，就把专用分支（单击）和退化情形一起吞了。

### 14.4 ★ Alt 反转用 XOR（`base != altDown`）表达四种组合 ★

缩放方向由“**点按还是框选**”×“**是否按 Alt**”两个维度共同决定，共 4 种组合。
写成一串 `if` 极易漏一种（尤其“框选 + Alt = 缩小到框”这条最容易被忘）。
用异或把两个 bool 折叠成一个：

```cpp
bool ZoomTool::zoomsIn(bool altDown) const { return zoomsInByMode != altDown; }
```

`base`（本模式的方向）× `Alt`（是否反转）→ **四种组合自动全覆盖**，加不进人为遗漏。
自检 `testZoomAlt` 对四种组合各钉一条。

### 14.5 ★ 共享步长常量：手感同源的唯一来源 ★

缩放“一格 = 1.25 倍”这个数字，**工具与画布必须同源**，否则会出现
“滚轮一次和点一下缩放走得不一样多”。常量放在 `tools/ToolParams.h`：

```cpp
constexpr qreal kZoomStepFactor = 1.25;
```

`ZoomTool` 与 `CanvasView::zoomIn/zoomOut` 都引它。放 `ToolParams.h`（而非画布头文件）
是为了**零 QtWidgets 依赖**：工具层能引，且符合“共享代码不知放哪层 → 放最下层”（可比 MarchingAnts）。

### 14.6 ★ 光标两态：工具改了光标状态，画布得知道它变了 ★

抓手需要 `OpenHandCursor`（空闲）/ `ClosedHandCursor`（拖动中）两态。
但**光标只在 `CanvasView::refreshCursor()` 里设置**，而工具内部状态变了
**不会自动通知画布**。所以 `mousePressEvent` / `mouseReleaseEvent` 里
**在工具处理完之后补一次 `refreshCursor()`**。

> ★ 这是“**装配顺序**”族（§三类静默失效之一）的变体：不是“连接建晚了”，
> 而是“**状态改了但没人推**”。凡是“工具内部状态 → 影响画布外观”的地方，
> 都要问一句“它靠谁同步”。

### 14.7 ★ 叠加层刻意不 gate 在 `view` 上（为了自检能直接量像素）★

`ZoomTool::paintScreenOverlay` 画框选虚线框（黑白双线，保证在任意底色上都可见）。
**它刻意不写 `if (!view) return;`**（传 `Q_UNUSED(view)`）——
这样自检可以**不建画布**，直接拿一个内存 `QImage` 调它，然后
**量框出来的像素**（§8.3 / §11.6 的“量像素”纪律）。

断言是“**框必须空心**”：框线之间有底色、四角是底色。
若只断言“有黑像素”，把 `drawRect` 写成 `fillRect` 也照样通过。

### 14.8 新工具同步清单（本批新增/确认）

在 §12.4 的基础上，本批额外确认两条：

1. **moc**：`run_tests.sh` 的 `moc_headers_for` 必须给新自检加 `HandTool.h` /
   `ZoomTool.h`（`Q_OBJECT` 类）。漏了 → **链接期** `LNK2001 metaObject`（同 §约定）。

   自检又直接建 `QImage` 量像素，`extra_libs_for` 要给 `hand_zoom_test` 加上。

其余沿用：`MainWindow::setupTools()` 注册、`.pro` 的 SOURCES/HEADERS、
`run_tests.sh` 的全量清单、图标映射与 `resources.qrc`（抓手/缩放两个图标早已在体系内）。

## 十五、文字工具（`engine/Text.*` `tools/TextTool.*` `ui/CanvasView.*` 的浮层）

### 15.0 为什么单独成章

它是 14 个工具里**唯一有“第二份界面”**的一个。

别的工具的全部交互都发生在画布的鼠标事件里；文字多了一个**输入浮层**
（一个浮在画布上的 `QTextEdit`）—— 因为 `QPainter::drawText` 只能“画”，
没法输入中文、没法编辑光标、没法退格。

于是本工具同时踩了三类坑，且**三类都是静默的**：

1. **职责切分**：内容（用户敲了什么）与浮层（一个能输入的控件）分属两层，
   接错了编译器一声不吭；
2. **排版语义**：锚点、对齐、行距、字距全是“差一点点看不出来”的量；
3. **像素落点**：文字最终是一次性写进像素层的，压不压命令、压几条，
   决定了 `Ctrl+Z` 好不好用。

### 15.1 ★★ 内容归工具、浮层归画布 —— 切法只有一种是对的 ★★

```
      内容（用户敲了什么）→ **工具**（它是模型）
      浮层（QTextEdit）    → **画布**（它是界面）
```

**为什么浮层不能归工具**：`QTextEdit` 必须挂在画布上才能定位到“点击处”，
而 `tools/` 层**不允许依赖 `ui/` 层**（`run_tests.sh` 里“工具自检刻意不链 `ui/`”
守着的就是这条边界）。所以浮层只能由画布创建。

**两端怎么牵线**（`AbstractTool` 上的协议，画布**不认识 `TextTool`**）：

| 方向 | 接口 | 说明 |
| --- | --- | --- |
| 工具 → 画布 | `requestTextEditor(anchor, font, color, align, lineHeight)` | 请求开浮层 |
| 画布 → 工具 | `setEditingText(QString)` | 浮层每次 `textChanged` 推回来 |
| 画布 → 工具 | `commit()` / `cancel()` | 确认 / 丢弃 |
| 画布 → 工具 | `hasInlineEditor()` | 决定 Esc / 换工具时要不要收浮层 |

> ★ **不要写成 `static_cast<TextTool*>(m_activeTool)`**。
> 那样 `ui → 具体工具` 的依赖就被焊死了（将来多一个“矢量文字工具”，画布就得改），
> 而且方向与既定的 `ui → tools` 相反。写成基类虚函数，与 `setForegroundColor`
> 的“推”是同一个套路。

**请求里的实参全是“内容”，没有一个是“控件怎么摆”**：`anchor` 是**图像坐标**，
字号该乘 `zoom` 多少、边框怎么去，都是画布的事。但有一个量**必须一起传**：

> ★ **`lineHeight` 必须传，不能只靠 `font`** ★
> `QFont` 里没有“行距”这个概念。漏传的话浮层按 100% 行距显示，
> 用户确定之后行距突然变成 1.8 倍 —— 看到的是“确认之后行跳开了”。
> 凡是“浮层要与最终结果一致”的量，都得在请求里传全（**漏一个就静默不一致**）。
> 植入 C 就是这个 bug，`text_tool_test` 的 `requestTextEditor` 实参断言抓得住。

**浮层的显示字号 = 图像像素字号 × `zoom`**，且每次**从 `m_textEditorFont` 重算**，
不是在上一帧结果上再乘一次（后者会复利放大）。边框全部去掉
（`documentMargin=0` + `NoFrame` + 透明背景），让“浮层位置”与“最终位置”
落在同一个坐标系、同一个点上；摆框用**内容宽度**而不是框宽对齐。

### 15.2 ★★ 锚点 = 文本块**首行顶部** + 水平对齐基准 ★★

全工程唯一一处定义（写在 `engine/Text.h` 顶部）：

```
   左对齐 → 文本块左边缘在 anchor.x
   居中   → 文本块水平中心在 anchor.x
   右对齐 → 文本块右边缘在 anchor.x
   三者的顶边都在 anchor.y
```

**为什么不学 Photoshop 把锚点放在“首行基线”**：基线的位置 = 顶部 + `ascent`，
而 `ascent` 是**字体的属性**。同一个锚点、换一个字体，文字块就会整体上下跳；
用户想让两段不同字体的文字**顶部对齐**时，无法用同一个锚点值。
用“首行顶部”则与字体无关，跨字体可对齐。
（代价：与 Photoshop 的锚点不可直接类比，故在此写明。）

> ★ 对应的实现细节：`QPainter::drawText(QPointF, QString)` 的 y 是**基线**，
> 所以内部必须写 `baseline = top + i * step + fm.ascent()`。
> 漏掉 `ascent` 就是植入 A —— 文字整体下沉一个 ascent，
> 而画面上只是“字比想象中低了一点”。

### 15.3 ★ 对齐只由**框位置**表达，框内一律左对齐 ★

`engine/Text` 算出 `blockLeft(align, anchorX, width)`，然后把**每一行都从
同一个 `left` 起画**。也就是说：**对齐只改变“块在哪”，不改变“行在块里怎么放”**。

反过来做（每行各自按对齐算起点）会把对齐**施加两遍**：
居中的文本再居中到一个已经居中的框里，越偏越多。
植入 B 造的正是这个：`Center` 的位移写成**一个**文本块宽
（等于“居中施加两遍”），`text_tool_test` 用
“居中比左对齐左移**半个**块宽”钉住它。

> ★ 断言这类位移量时，基准必须是**排版宽度（advance）**而不是**墨迹宽度**。
> 墨迹比 advance 窄几个像素（两侧各有一个 side bearing），拿墨迹宽度去核对
> 会凭空多出一条假红 —— 本组第一版就是这么错的。

### 15.4 ★★ 字距由**字体**携带，引擎绝不再设一遍 ★★

`TextOptions::toFont()` 已经把“像素字距”换算成百分比写进了 `QFont`。
所以 `engine/Text` 的参数 `font` 就是**最终字体**，原样使用，不再 `setLetterSpacing`。

> ★ 这是“**同一件事有两处真相**”的典型形态，而且是静默的（只是文字变宽）。
> 植入 D 在 `measureTextBlock` 里又加了一遍字距，宽度增量翻倍 ——
> 断言是“宽度增量在 ≈4×16px 的合理范围内，而不是再翻一倍”。

### 15.5 ★ 不自动换行；换行符必须先归一化 ★

**只按显式的 `\n` 断行**。这是刻意的取舍：自动换行需要一个“折行宽度”，
而点子文字（point text）的锚点语义里并没有这个宽度（Photoshop 的点文字同样
只按回车换行）。编辑浮层也用 `NoWrap` **对齐这一点** —— 否则浮层折行、
落到图层上却不折，用户看到“确定之后行变长了”。

`\r\n` / `\r` 一律先归一成 `\n`。不归一的话，从剪贴板粘进来的两行会被
`split('\n')` 切成 `"第一行\r"` 与 `"第二行"`，而那个残留的 `\r` 在 `drawText` 里
是**不可见的**（不占宽度、不画任何东西）—— 排版看起来完全正常，
而字距 / 宽度测量会莫名其妙地差一点。

### 15.6 ★ 蒙版的像素值**本身就是覆盖度**；但“没有墨”必须单独判 ★

底填黑（0）、白色（255）画字。source-over 在“目标不透明”时退化成
`out = 255 * a` —— 于是**像素值就是覆盖度**，不需要取 alpha 通道
（`Shape` 那份“取 alpha 而不是 `convertToFormat(Grayscale8)`”的说明针对的是
ARGB 绘制目标；这里压根没有 alpha 通道可以取错）。

但**必须单独判“蒙版里有没有墨”**（`maskHasInk`），因为它挡住两种静默空操作：

- 整段都是空格 / 制表符（有 advance、有包围盒，**但没有字形**）；
- 字体缺失导致一个字形都取不到。

不判的话，一次全 0 蒙版会走完整条“落像素 + 压命令”的流程，而 `composeStroke`
面对全 0 蒙版是**原样返回** —— 于是撤销栈里多出一条
“按了 `Ctrl+Z` 什么也没发生”的记录。植入 E 去掉这个判据后，
`纯空白文本不压命令` 与 `1×1 画布不压空命令` 一起变红。

**包围盒另留 `pad = 3`**：抗锯齿会溢出 advance 一个像素左右（斜体尤其明显）、
下划线画在基线**以下**而 `fm.height()` 只覆盖字形本身、`floor/ceil` 取整各让一格。
自检里最强的一条是**与字体无关的不变量**：“墨迹四周都不贴蒙版边缘”。

### 15.7 ★★ 一次输入 = 一条 `DrawCommand::standalone()` ★★

浮层里敲多少字、换多少行都**不产生命令**；只有 `commit()` 那一下压一条。
理由与油漆桶 / 形状相同：让撤销栈里出现“逐字符撤销”会毁掉 `Ctrl+Z` 的语义。

> ★ 用 `standalone()`（取新描边号），**不要**自己 `new` 并传固定编号。
> 撞号会被 `QUndoStack` **静默** `mergeWith` → “写两段，撤一次两段都没了”。
> 植入 H 就是这个 bug，`两次输入是两条撤销记录` 抓得住。

**浮层的 5 条收口路径必须走同一个 `closeTextEditor()`**：
Esc、失焦、`Ctrl+Enter`、换工具、换文档。实现上**先摘指针再 `hide()+deleteLater()`**
（防重入，否则会压两条命令）。

### 15.8 ★ 落像素的完整前置检查（缺一条就是“写了一半”）★

`beginEditAt()` 依次拒绝：无文档 / 图层锁定或隐藏 / 画布尺寸为空 / **没有撤销栈**。
最后一条尤其要紧 —— 没有撤销栈就**干脆不让开始**，
否则用户敲完确认，图层上多了一块**永远撤不掉**的痕迹。
（★ 拒绝的提示必须在**开浮层之前**发，别让用户白敲一场。）

`renderText()` 再挡一次空文本 / 空画布 / 空图层 / 空蒙版 / 空区域，
最后才 `embedMask`（来自 `engine/Shape.h`）→ `composeStroke`（来自 `engine/Brush.h`）
→ `CompositionMode_Source` 写回 → `push(standalone(...))`。
**合成路径全工程仍然只有一份实现**，这是“引擎只产出蒙版”的意义。

`setDocument()` 时按**取消**处理而不是提交：浮层挂在**旧**画布上，
提交会让字写进旧文档、而用户立刻切走了 —— 不可见、不可撤销，最难排查。

### 15.9 新工具同步清单（本批新增 / 确认）

1. **`engine/` 层不许碰 QtWidgets**：`Text.cpp` 只用 `QPainter` + `QFontMetricsF`。
   自检 `text_test` **只链 Qt5Core + Qt5Gui**、且用 `QGuiApplication`
   （不是 `QApplication`，后者会拖进 QtWidgets）；用户参数对象 `TextOptions`
   在 `tools/ToolOptions.cpp` 里、拖着整个 QtWidgets，所以“参数 → 字体 → 排版”
   那条链归 `text_tool_test`。
2. **字体目录**：Qt 5.15 起不带字体，offscreen 平台默认一个字体都找不到
   （症状是“所有蒙版都是空的”而**不是**报错）。两个文本自检都显式

## 十六、跨图导入：「打开为图层」与「粘贴为新图层」

### 16.0 这一章要解决的是什么

用户的原话是：“从第二幅图片中选择一个区域，复制到第一幅图片上。”

这句话里真正缺的从来**不是复制粘贴**（复制走系统剪贴板、粘贴为新图层早就有了），
而是**同时看到两张图**。所以有两条路：

| 方案 | 代价 |
|---|---|
| 多标签页 | 要重构中央控件（`setCentralWidget` → `QTabWidget`），影响面大 |
| **打开为图层** | 零架构改动，多用一步 |

本工程选了后者，于是“跨文档”问题退化成“跨图层”问题 ——
选区、反选、删除、移动这些图层内操作**全部是现成的**。
用户的实际操作变成：`文件 → 打开为图层…` → 在新层上框选 → 反选 → 删除。
多标签页仍然要做，但它是**同一需求的正解**，排在后面单独做（见 `docs/架构规划.md` §3.8）。

> `DocumentManager`（数据层）早就完整了 —— `addDocument` / `openDocument` /
> `closeDocument` / `currentChanged` / `titleAt` / `hasUnsavedChanges` 都在。
> 缺的只是**中央控件那一层 UI 外壳**。这也是“打开为图层”能以零架构改动落地的原因。

### 16.1 ★ “把一张图变成一个新图层”只能有一份实现 ★

两条路径要做的是**同一件事**：

- 「编辑 → 粘贴为新图层」(`Ctrl+V`) —— 像素来自剪贴板
- 「文件 → 打开为图层…」 —— 像素来自文件

所以它们共用 `MainWindow::addImageAsNewLayer(image, pos, name, historyText)`。
把两条约束复制成两份，就会有“改一处忘一处”，而且**第二份没有自检守着**：

- 新图层的位图**必须填满画布**（见 16.2）
- 必须用 `CompositionMode_Source` 而不是 `SourceOver`

这与“合成只有 `composeStroke()` 一处”“尺寸偏移只有 `canvasResizeOffset()` 一处”
是同一条纪律。**新增任何“把一张图变成一层”的入口，都只能去调它，不许另写一份。**

> 契约：只压**一条** `LayerCommand`，**不自己 `beginMacro`** ——
> 撤销粒度由调用方决定（粘贴是一条；导入是“扩画布 + 加图层”两条合成一个宏）。

### 16.2 ★ 新图层必须自己填满画布，绝不能让 `Document::addLayer` 去扩 ★

`Document::addLayer(const Layer &, int)` 在图层尺寸**大于画布**时会静默调用
`setCanvasSizeInternal()` 去扩大画布 —— 而那条路径**不压任何命令**，
撤销时画布尺寸回不去。

所以 `addImageAsNewLayer()` 先开一张**画布大小**的位图、再把图像画进 `pos`，
“图层尺寸恒等于画布尺寸”这条不变量就守住了，那条静默路径永远踩不到。

> **★ 断言必须用“比画布大”的图才测得出来 ★**
> 自检里第一段用的是 40×24 的小图。就算有人把新图层开成图片尺寸，
> `addLayer` 也只会把它重排到左上角（因为比画布小），画布尺寸照样不变 ——
> **小图上这条断言根本测不出问题**。所以必须有第二段：粘贴一张比画布大的图。

### 16.3 ★ 尺寸决策必须问用户；而“没人可问”不能默认成裁剪 ★

导入图**比画布大**时必须做决定：扩大画布（不丢图，但改了画布尺寸）
还是裁剪（保住画布，但丢了图的一部分）。两个都不是能替用户默认做的事。

于是 `importImageAsLayer()` 的第二个参数是 `GrowPolicy`：

```
Ask    —— 弹三选一框问用户（openAsLayer() 用这个，= 产品默认）
Grow   —— 直接扩大画布以容纳（自动化用）
Crop   —— 保持画布尺寸，超出部分裁掉（自动化用）
```

**绝不把“没人回答”默认为 `Crop`** —— 那是在无人值守时静默丢掉用户图片的一部分。

判定用 `engine/Geometry` 的两个纯函数，而不是在 `MainWindow` 里重写一遍：

```cpp
QSize unionSize(const QSize &a, const QSize &b);        // 逐维取大
QPoint centeredOffset(const QSize &canvas, const QSize &item);  // 居中偏移
```

抽成纯函数的价值：**“扩到多大”“放在哪里”成了可以被断言的数学事实**，
而不是只能靠人眼看截图。`canvasResizeOffset()` 是同一个理由（见 §5.1）。

> ★ `unionSize` **不能**写成 `qMax(面积)` 或“取较大的那一张” ★
> 只有**逐维**取大才既装得下原画布、又装得下导入图。
> 植入验证里 A 就是这一条。
>
> ★ `centeredOffset` **不能**加 `qMax(0, …)` 钳位 ★
> 看似是防御性编程，实际把“调用方把尺寸算错了”这个错误藏了起来：
> 内容会悄悄贴到左上角，而不是暴露成负数。植入验证里 C 就是这一条。

> ★ **放不下时的放置规则，粘贴与导入是刻意不同的** ★
> `pasteFromClipboard()` 放不下时用 `(0,0)`（贴左上角），
> 而「打开为图层」**一律用居中偏移**（放不下时 `centeredOffset` 会算出负数，
> 于是超出部分被**两侧对称裁掉**）。
> 理由：粘贴的内容通常来自“某个已知位置”（同文档时甚至原位粘贴），
> 放不下时保持左上角是与源一致的退化；而导入的是一整幅图片，
> 它没有“画布坐标”可言，**居中是唯一自然的锚点**。
> 两处的差异是**有意的**，但也是**容易被后人当成 bug 顺手“修掉”的** ——
> 所以记在这里。别再改回去：贴左上角会让用户看不到导入图的主体，
> 屏幕上只剩一个角。
> 两者共用的是**建层**（`addImageAsNewLayer`），不是**放置** ——
> 放置规则由各自的调用方决定。

### 16.4 ★ 几何变更只能走 `commitGeometryChange`；宏的顺序不能反 ★

“扩画布”是几何变更，因此**只能**走 `MainWindow::commitGeometryChange()`
—— 那是**内存预检唯一的一道防线**（见 §5.6 与 `MainWindow.h` 的说明）。
绝不能在这里自己 `new GeometryChangeCommand`。

**顺序不能反**：`GeometryChangeCommand` 的前后快照是
**整份图层列表 + 画布尺寸**。若先加图层再扩画布，快照里就会带上那个新图层，
撤销“扩画布”时会连图层一起动 —— 两层命令的职责就串了。

```
beginMacro("打开为图层")
  ├─ resizeCanvas(union, Center, transparent, smart)   ← 先扩（此时图层列表还是原样）
  │    └─ commitGeometryChange(before, ResizeCanvas, "扩大画布")
  └─ addImageAsNewLayer(…)                             ← 再加层
endMacro()
```

**`beginMacro` 与 `endMacro` 必须成对，失败路径也要 `endMacro`** ——
不配对会让撤销栈永久停在“宏内”状态，接下来所有命令都被吞进这个宏，
症状是“按一次 `Ctrl+Z` 把好几步一起撤销了”，非常难查。

**扩画布之前要检查图层锁定**：画布尺寸变更会逐图层重排到新尺寸，
锁定的图层必须在这里被挡住（与 `openCanvasSize()` 的检查同款）。
“加一层”本身不需要这个检查（它不碰现有图层）。

### 16.5 ★★ 带对话框的功能，必须把“干活的那半”做成公开入口 ★★

这是本章最可复用的一条，也是这一章能写出来的原因。

`openAsLayer()` 的第一件事是 `QFileDialog::getOpenFileName`（模态）。
在**无人的自动化环境**里，模态框会让进程**永久挂死** ——
截图工具就会挂死在这一行。同理，三选一询问框、“图像过大”的确认框、
甚至连“读不出这个文件”的警告框都会。

于是把函数拆成两半：

```
openAsLayer()            ← 只负责“选文件”，选完就交棒
    └─ importImageAsLayer(path, policy)   ← public，真正干活的那一半
```

拆开之后立刻得到三样东西：

1. **截图工具能驱动它**（`.buildlog/shot/shot_main.cpp` 的 `openaslayer` 模式），
   于是这条路径有了人眼可看的两张图；
2. **自检能断言它**（`tests/mainwin_test.cpp`），
   于是三种策略、撤销粒度、失败不动文档全部被钉住；
3. **“不弹任何模态框”成了一个结构性保证**，而不是靠每处记得判断 ——
   失败汇报统一走一个 lambda：

```cpp
const auto reportFailure = [this, policy](const QString &title, const QString &text) {
    if (policy == GrowPolicy::Ask)
        QMessageBox::warning(this, title, text);      // 交互：用户必须看见
    else if (m_statusBar)
        m_statusBar->showMessage(text, 6000);          // 自动化：弹框会把脚本挂死
};
```

> 这不是新发明 —— `TextTool::placeText()` 与 `tools/TextTool` 的浮层是同一个套路：
> **把“有对话框”和“真正干活”分开，干活的那半必须能脱离 UI 被调用。**
> 推而广之：**本工程凡是带对话框的功能都该长成这样**，
> 否则它就永远只能靠人眼验证，而没有断言守着。

> ★ 截图工具拿撤销栈踩过的坑（值得单记一句）★
> `win.findChild<CommandStack*>()` 拿到的是**第一个**子对象 ——
> 也就是那个已关闭的初始空文档留下的栈，于是“撤销记录数”永远是 0，
> 三条断言集体误报成“粒度不对 / 宏没生效”，而产品代码完全正常。
> 根因在 `MainWindow::setupDocumentManager()`：**每个文档配一个 `CommandStack`**
> （命令内部持有 `Document*`，共用一个会在文档 B 里撤销掉文档 A 的操作），
> 换文档时把旧的 `deleteLater()` 掉。
> **当前文档的栈只有 `ToolManager` 手里有**，只能从那里拿。
> 同一条纪律写进了 `.buildlog/shot/shot_main.cpp` 的注释里。

### 16.6 断言与证据

**引擎侧**（`tests/geometry_test.cpp`，`unionSize` / `centeredOffset` 组）：
逐维取大、**对空/零尺寸不做特判**（留了“墓碑断言”挡将来的死代码）、
偶数差值的对称性、以及“导入图完全落在画布内”的组合不变量。

**装配与行为**（`tests/mainwin_test.cpp`）：

- `testOpenAsLayerAssembly()` —— 动作存在、**有真图标**、
  **确实挂在「文件」菜单里且紧跟在「打开」之后**、与「打开」是两个独立动作。
  （`addAction(nullptr)` 是**合法且静默**的，所以“动作对象存在”完全证明不了“菜单里有它”。）
- `testImportImageAsLayerPolicies()` —— 三种策略 + 失败路径：
  ① 放得下（`Ask`）：图层 +1、**画布一个像素都没变**、新图层位图 == 画布、
  内容落在 `(canvas-img)/2` 处且**左邻一格仍透明**（差一像素也抓得住）、图层名 == 文件名、
  **一次导入 = 一条撤销**；
  ② `Crop`：图层 +1 但**画布不变**（这是选 `Crop` 的全部意义）；
  ③ `Grow`：画布扩到 `unionSize`，且**只宽不高时高度必须原封不动**
  （这条才区分得出“逐维取大”和“整体取导入图的尺寸”）、
  撤销一次**扩画布与加图层一起回退**；
  ④ 有锁定图层时 `Grow` **被拒绝且没做出“半件事”**；
  ⑤ 读不出的文件返回 `false` 且**文档完全没被动过**（若改成弹框，本段会卡死而不是报错）。
- `testPasteAsNewLayerRegression()` —— 抽出共用实现之后，粘贴那条路
  **行为一点没变**：一条撤销、新图层填满画布、居中、左上角透明，
  并含“粘贴比画布大的图”第二段（见 16.2 的方框）。

**植入验证**（`.buildlog/implant_openaslayer.py`，**十条**）：

## 十七、多标签页（`ui/DocumentTabs.*` + `ui/MainWindow.*`）

> 设计背景与七步改造表见 `docs/架构规划.md` §3.8 / §3.8.3。
> 本章只记**动手时必须遵守的**东西，以及这次踩到的三个真 bug。

### 17.1 模型：一页 = 三件套，「当前页」= 三个指针

```cpp
struct DocumentTab {
    Document     *doc;      // 借用（所有权在 DocumentManager）
    CommandStack *stack;    // 本控件持有（QObject parent = DocumentTabs）
    CanvasView   *canvas;   // 本控件持有（同时是 QTabWidget 的一页）
};
```

`MainWindow` 仍然只有 `m_doc` / `m_commandStack` / `m_canvas` 三个成员，
但它们从“唯一的那一份”变成“**当前页**的那一份”，由 `activateTab(index)` 重指。

★★ **这是本次改造能一次做完的根本原因** ★★
全工程几百处 `m_doc->xxx()` / `m_canvas->xxx()` **一行都没改**。
一旦改成 `m_tabs[i]->doc->xxx()` 或引入 `currentDocument()` 访问器，
每一处调用点都要动 —— 而且动错的地方编译器未必拦得住。

★ **代价必须说清楚**：这三个指针是**派生状态**，
真相在 `m_tabs->currentTab()`。所以它们只允许在 `activateTab()` 里被写。
任何地方自己写 `m_doc = ...` 都会制造出"指针与标签页不一致"的中间态 ——
而且不报错，只是操作落到了别的文档上。

### 17.2 撤销栈与画布都必须**每页一份**

**撤销栈**：`Command` 内部持有 `Document*`。全工程共用一个栈的后果是：
在 B 页按 Ctrl+Z 撤销掉的是 **A 页**的操作 —— 而 A 页画面不会跟着变，
用户看到的是"撤销了但什么都没发生"。

**画布**：视图状态（缩放 / 平移 / 蚂蚁线）是用户对**这一张图**的设置。
共用的切页会把上一页的缩放宽高带过去：一张 200×200 的图标和一张 6000×4000 的
照片用同一个缩放比，前者小得看不清、后者只看得见一个色块。

★ 顺带一条：**工具是跨页共享的**（`ToolManager` 只有一份，工具不随页重建），
所以"正在画的那一笔"是工具内部的状态。切页前必须 `commitActiveTool()`，
否则在 A 页画到一半切到 B 页，松手时这一笔会落在 **B 页**的图层上。
（旧实现里这条保护藏在 `CanvasView::setDocument()` 的 "工具正忙就 cancel()" 里，
一页一块画布之后切页不再经过 `setDocument`，那条保护就消失了 —— 必须补在
`activateTab()` 的第一行。）

### 17.3 `activateTab()` —— “当前页变化”的唯一入口

```cpp
activateTab(index):
  ① m_toolManager->commitActiveTool()        // 结算上一页未完成的一笔
  ② 三个指针 ← m_tabs->tabAt(index)（index<0 → 全 nullptr）
  ③ m_docManager->setCurrentIndex(indexOf(m_doc))
  ④ applyDocumentToPanels(m_doc)             // 面板重绑（约定 7 的唯一入口）
  ⑤ syncUndoRedoActions(m_commandStack)      // 显式补推
  ⑥ updateWindowTitle()
```

★★ **传 -1 是"空状态"，也是一种合法的"当前页变化"** ★★
关掉最后一页、`closeEvent` 拆完全部页之后，都要走 `activateTab(-1)`。
它把三件套置空**并推给所有面板** —— 这一步不能省，理由见 17.4.2。

★★ **`closeDocumentTab` 的三步顺序不能换** ★★

```
㈠ removeDocumentTab(index)     // 画布 + 撤销栈随页销毁
㈡ activateTab(剩下的某一页)     // 先把界面切到还活着的文档
㈢ m_docManager->closeDocument(docIndex)   // 最后才 delete 文档
```

反过来的话，中间会出现"工具 / 面板 / 状态栏都还指着那份已经被 `delete`
的文档"的窗口期，而任何一次重绘或析构都可能碰到它。

★ 这三步要用 `QScopedValueRollback<bool>` 把 `m_switchingTabs` 置位 ——
让外界看不到"标签序号与文档序号不一致"的中间态。
用 RAII 而不是手写 `set(true)/set(false)`：下面有七八处 `return`，
漏掉一条的症状是"那次操作之后切页再也不工作了"（标志位永久为真）。

★ `docIndex` 必须从**文档指针反查**（`DocumentManager::indexOf`），
不要直接用 index —— "标签序号 == 文档序号"是当前的巧合，不是可依赖的性质。

### 17.4 ★★ 三个真 bug：全在"销毁与重绑的顺序"上 ★★

#### 17.4.1 「栈马上就要没了」必须有信号 —— `aboutToRemoveTab`

**症状**：关掉一个标签页 → **段错误**。0 错误 0 警告。

**原因**：`removeDocumentTab()` 会 `delete` 这一页的 `CommandStack`，
而 **`QUndoView`（历史面板）的内部模型里存的是裸 `QUndoStack*`**；
紧接着 `applyDocumentToPanels()` 调 `m_undoView->setStack(新栈)`，
而它做的第一件事就是对**旧栈** `disconnect()` —— 旧栈刚刚被 `delete`。

**修法（结构性）**：`DocumentTabs` 增加一个信号

```cpp
signals:
    void aboutToRemoveTab(int index);   // 在 removeDocumentTab() 的第一行发出
```

发出时机是**栈、画布、文档都还活着**的那一刻。`MainWindow` 连它，
调 `detachStackConsumers(栈)` 把历史面板 / 状态栏 / 工具管理器一起解开。

★ 为什么不做成"调用方记得先解绑"：那样"销毁栈"就多了一条**隐藏前置条件**。
将来任何一个新调用点（"关闭其他标签页"、"关闭所有"…）忘了它，
症状都是随机段错误 —— 而且**只在被销毁的恰好是当前页时才出现**。
做成信号，前置条件就变成了结构性的。

★ `detachStackConsumers` 必须**只解开确实指向这一份栈的**消费者：
销毁后台页的栈时把当前页的绑定也一起打断的话，`clearAllTabs` 那条路径上
**没有后续的重新绑定**。（例外是析构：传 `nullptr` = "全部解开"。）

★ 同类消费者不止历史面板：`StatusBarWidget` 也存了 `CommandStack*`，
而 `refreshDocumentInfo()` 会读 `m_stack->estimatedMemoryUsage()`，
它挂在 `Document` 的 `contentChanged` 上 —— **任何一次内容变化都可能回调到它**。

#### 17.4.2 `closeEvent` 拆完页之后必须走 `activateTab(-1)`

**症状**：关窗口之后再销毁窗口 → 段错误。
（真实程序里进程紧接着就退出了，所以这颗雷一直没响；自动化测试是"关完之后还有代码跑"的那种程序。）

**原因**：`clearAllTabs()` 拆的只是**页**（画布与撤销栈随页消失），
而面板（图层面板 / 状态栏 / 工具管理器）手里还攥着各页的 `Document*`
—— 它们要等 `applyDocumentToPanels(nullptr)` 才会松手。
于是 `closeAll()` 一执行，面板全指着已释放的内存，本窗口随后那一轮完整析构
（面板换绑时都会 `disconnect(m_doc, …)`）随时会踩空。

**修法**：`closeEvent` 里，在 `clearAllTabs()` 之后、`closeAll()` 之前
调 **`activateTab(-1)`**。不要手写三行 `m_doc = nullptr;` ——
那只能把 `MainWindow` 自己的指针置空，**面板那一侧照样攥着**，正是要修的东西漏掉了。

#### 17.4.3 切页要**显式补推**状态栏的缩放比

**症状**：在 1200×800 的页上状态栏写着「99.9%」，切到 3840×2160 的页
仍然是「99.9%」（真实值 31.6%）。而**窗口标题是对的**。

**原因**：`CanvasView::viewChanged` 只在缩放**变化**时发，而切页时新画布的
缩放本来就是它自己的值 —— `applyDocumentToPanels` 里那句 `setDocument()`
因此早退，**一个信号都不发**。

**修法**：在 `applyDocumentToPanels` 里显式 `m_statusBar->setZoom(m_canvas->zoom())`。
（`StatusBarWidget::setZoom` 内部有 `m_updatingZoomCombo` 守卫，程序化设置不会
反过来触发 `onZoomComboChanged` 把缩放再改一遍。）

★★ **这条最值得记** ★★
它不是断言先发现的，是**看截图**看出来的（`.buildlog/multitab.png`）。
补断言时用两页**尺寸差得够远**的画布才验得出来 —— 两个 1200×800 的页
彼此缩放相同，拿它们对比时"跟不跟着走"完全看不出来。
植入验证：关掉那一句，**恰好一条**断言变红。

#### 17.4.4 两条规律（值得单独背下来）

> **① 信号只传达"变化"，传达不了"现状"。**
> 凡是"对象构造期就改过状态、或状态在别处已经改好"的，
> 界面侧都要**显式补推**一次。本项目已踩过四次：
> 活动工具（`applyActiveToolToUi`）、撤销/重做动作（`syncUndoRedoActions`）、
> 新画布的工具与颜色（`applyDocumentToPanels`）、状态栏缩放比（本条）。
>
> **② 销毁一个对象之前，必须先让所有指向它的人松手。**
> 谁指着它？这个问题**只能由"知道销毁时机"的那一方发起通知**
> （在这里就是 `DocumentTabs::aboutToRemoveTab`），
> 靠"调用方记得"迟早会漏。

### 17.5 `DocumentTabs` 的纪律：只管容器，不碰业务

与 `LayerPanel` 完全同一条纪律：

- **只报告**：用户点了某一页的 ×，它发 `closeTabRequested(index)`，然后**什么都不做**。
  "关闭一页"要问用户、要调保存、要处理取消 —— 那些都是 `MainWindow` 的事。
- 不 `delete Document`（所有权在 `DocumentManager`），不压任何命令。
- ★ 好处：**"关闭一页"全工程只有一条路径**，不会出现"点 × 关"与"菜单关"行为不同
  （例如一条记得问保存、另一条忘了）。
- ★ `tabCloseRequested` 要**转发一次**而不是让外部直接连 `QTabWidget::tabCloseRequested`：
  将来本控件换实现（自绘标签栏、加"全部关闭"按钮…）会打断外面的连接，
  而打断是**静默**的 —— 症状是"点 × 没反应"。

### 17.6 `QSignalBlocker` 只屏蔽需要屏蔽的那一段

**在 `addDocumentTab` / `removeDocumentTab` 里屏蔽**：`QTabWidget` 在
"这是第一页"／"摘掉当前页"时会**自己**挑一个当前页并同步发 `currentChanged`，
而那一刻调用方还没把这一页的撤销栈接好、三个指针也还没重绑 ——
外界收到的是一个**半成品当前页**。所以 `addTab` / `removeTab` 那一小段要屏蔽，
切页由调用方在准备好之后**显式**做。

★★ **但不要"整体兜底屏蔽"** ★★
`clearAllTabs()` 原先在循环外整体屏蔽了自己的信号（理由写的是同上）。
多标签落地后它变成了**有害的**：它把 `aboutToRemoveTab` 也一起挡掉了 ——
于是"逐页销毁撤销栈"外界完全看不到，历史面板留下悬垂指针，退出时踩空。

> **教训**：一个图省事的兜底屏蔽，会吃掉**后来新增**的信号，
> 而报错信息一个字都不会提它。屏蔽的责任要下放到唯一需要它的那一段。
> 判据：**"连续摘很多页"与"用户连点很多次 ×"在信号层面必须完全一样**
> —— 后者是有实测覆盖的（关到一页不剩那组断言）。

### 17.7 判据只有一份：`needsSave(doc, stack)`

"这个文档改了没保存"要在三处被问到：① 关一页；② 关窗口（逐页）；
③ 标签上要不要画 `*`。三处各写一遍，迟早出现"标签带着 `*`，但关闭时不问保存"
—— 而用户只有真的丢了东西才会发现。

判据取**撤销栈的 `clean` 状态优先**（`!stack->isClean()`）而不是
`doc->isModified()`：前者是 `QUndoStack` **自动跟踪**的 ——
用户撤销回到保存点时它会自己变回 clean；后者只是个手动维护的标志位。
场景：画了一笔（modified=true）→ 按 Ctrl+Z 撤销回去 ——
此时内容与保存时完全一致，不该再提示保存，用 `isModified` 会误提示。

### 17.8 「新建 / 打开」不再需要未保存确认

单文档时代它们是"用新图替换掉当前这张"，所以要问。
多标签之后**只是多开一页**，原文档原封不动 —— 没有任何东西会丢，
弹一句"要保存吗"就是纯粹的打扰。

★ 于是需要确认的只剩两处：**关一页、关窗口**。审查起来清楚得多。
★ 但这也意味着"重复打开同一个文件"要有明确行为：**切过去，不新开一页**。
多开一份会让"在两个标签里各改一遍、保存时后者覆盖前者"成真 ——
而用户在保存前完全不会意识到自己有两份。

### 17.9 自检：覆盖什么，以及**刻意不覆盖**什么

- `tests/document_tabs_test.cpp`（85 项）：账本 / 三件套绑定 / 每页状态独立 /
  标题与 `*` / 摘页只销毁自己的东西 / **只报告不关闭**（真的发出
  `tabCloseRequested` 之后断言页数一个都没少）/ `clearAllTabs` / `indexOf`。
- `tests/mainwin_test.cpp` 阶段八两组：多标签装配 + 命令行参数（见 [自检与验证.md](自检与验证.md)）。
- ★★ **刻意不测** ★★：关闭**有未保存修改**的页（会弹模态确认框）。
  离屏环境下没人点它，自检会**永久挂死** —— 比失败更糟。
  能钉住的只有它的**判据**（标签上的 `*`，与模态框共用 `needsSave`），
  其余靠人眼。
- ★ 关窗口那条路径（`clearAllTabs`）**必须单独测**：它与"一页一页点 ×"
  **不是同一段代码**，而 17.4.2 那个 bug 只有它会踩到。
  离屏下它不会弹框（前提是每一页都干净 —— 测试里要先撤销回原点）。

### 17.10 视觉证据

`shot.exe <图> .buildlog/multitab.png multitab` → 两张整窗图：

- `multitab.png`：5 个标签，其中一个标题带 `*`；状态栏显示当前页的
  尺寸 / 内存 / 缩放比；
- `multitab_switched.png`：切到另一页 —— 标签高亮、尺寸、缩放比、图层数、
  撤销步数全跟着换。

自证打出：页数 / 撤销栈个数（应相等）/ 每页的标题·文档尺寸·画布缩放·栈步数 /
**当前可见的画布数（应恒为 1）**。最后一条同时证明了两件事：
页真的被换掉了、而且每页各有一块画布。

> ★ 造 4 页时要**故意让尺寸差得够远**（1200×800 / 3840×2160 / 600×400 /
> 260×900 / 1400×300）：尺寸一样的话，每页的缩放比也一样，
> "每页一块画布""切页要补推缩放比"这两件事在截图上都看不出来。

### 17.11 手法：段错误怎么定位

Qt 的信号槽 + 裸指针项目里，段错误的**位置信息为零**。
这次用的办法，性价比最高：

**把每条断言写进 `stderr`（MSVC CRT 下 stderr 是
无缓冲的），崩溃点就是最后一行。**

```cpp
static int g_seq = 0;
static void trace(const char *what)
{
    std::fprintf(stderr, "<%d> %s\n", ++g_seq, what);
    std::fflush(stderr);
}
// 在 check()/checkEqInt()/checkStr() 的第一行调它（临时插桩，查完即删）
```

★ 为什么不能用 `stdout`：重定向到管道/文件时它是**全缓冲**的，
进程一崩，最后那几十行还在缓冲区里，一个字都看不到。
`beginGroup()` 之所以能看见，只是因为它自己 `fflush` 了。

★ 定位到"哪个 `trigger()` 崩的"之后，再往被测代码里插桩就很快了。
本次两轮就把范围收成了一个函数。

★ 插桩要**临时**：这次的 `trace()` 在修复验证通过后立刻删掉
（它会让 17 个测试程序都多打几百行）。

## 十八、标尺与参考线（`engine/RulerMetrics.*` + `ui/RulerWidget.*` + `ui/CanvasView.*`）

> 设计背景见 `docs/架构规划.md` §3.9 / 阶段七。
> 本章只记**动手时必须遵守的**东西，以及这次踩到的两个真 bug ——
> 两个都是**同一个根因**，而且第一个只在"显示窗口的那一瞬间"才崩。

### 18.1 定位：视图辅助 vs 图像内容，靠**结构**分开而不是靠 `if`

标尺与参考线是**辅助**,不是图。判据只有一条：**它们绝不能进 `Document::composite()`**。

★ 这条不能靠"在合成时判断一下要不要画"实现 ★
写 `if (!isViewAid) { ... }` 的话，任何一条新增的合成路径（导出、另存、缩略图、
复制到剪贴板、合并图层…）都要各自记得判断一次，漏一处就"导出的图上有根蓝线"。
**结构上分开**则无从漏：参考线根本不在 `Document` 里，它在 `CanvasView` 里。

```cpp
// CanvasView.h
struct Guide { Qt::Orientation orientation; int position; bool locked; };
QVector<Guide> m_guides;         // ★ 每页一份的**视图状态**，不进 Document
```

于是"参考线不进导出"是**编译器保证**的，不是纪律保证的。
自检里仍有一条逐像素断言守着它（`composite()` 前后完全相等），
因为**将来有人可能"顺手"把它挪进 Document** —— 那条断言就是拦住这一手的。

### 18.2 刻度换算必须是**纯函数**，且判据用**屏幕像素**不用图像像素

`engine/RulerMetrics.*` 全是无副作用纯函数（与 `engine/Geometry.*` 同一层原则）：

| 函数 | 职责 |
|---|---|
| `unitAt(i)` / `unitIndex(u)` | **单位顺序的单一协议**。菜单顺序、`QSettings` 存的下标、枚举值三者同源 |
| `pixelsPerUnit(u, dpi)` | inch = dpi、cm = dpi/2.54、mm = dpi/25.4、pt = dpi/72；**dpi ≤ 0 回落 96** |
| `niceStep(x)` | 把任意步长吸附到 1/2/5×10ⁿ。`x ≤ 0` / NaN → 返回 1.0 |
| `chooseTicks(zoom, u, dpi, minLabelSpacingPx)` | 选主/次刻度，见下 |
| `formatLabel(v, u, major)` | 数字文本 |

★★ **"主刻度之间留多宽"必须按屏幕像素判，不能按图像像素判** ★★
同一张图在 10% 与 800% 缩放下，屏幕上能放的刻度数差 80 倍。
按图像像素判 → 缩小到 5% 时数字叠成一坨黑。所以 `chooseTicks` 收的是 `zoom`，
内部先把"最小标签间距(屏幕px)"折算成图像距离再吸附。

★★ **数字的小数位要从"步长本身"推，不能按量级拍脑袋** ★★
一开始写的是"`major < 1` → 1 位小数、`< 0.1` → 2 位…"，于是
**英寸的 ¼ 英寸主刻度**（`major = 0.25`）落到"1 位小数" → 印出来是 `1.3`
（`1.25` 被四舍五入），量出来的刻度是错的。
现在改成从步长自身推导：把 `major` 逐次 ×10 直到它成为整数，小数位 = 乘的次数。
`0.25 → 2 位`（`1.25` 正确），`200 → 0 位`（`400` 而非 `400.0`）。
**这条是引擎自检里唯一一个"一开始写错"的断言**（`ruler` 自检 51 项）。

★ 单位切换只在**两把尺子**上生效，判据是 `m_unit` 一份 —— 不存在"水平尺厘米、
垂直尺像素"这种状态（`setRulerUnit` 一处同时设两把）。

### 18.3 ★★ 真 bug ①：`mapTo(parent, …)` 的 parent 必须是**祖先** ★★

标尺要知道"画布左上角在我的坐标系里是哪儿"，才能把刻度画在正确的位置。
第一版写的是：

```cpp
return m_view->mapTo(this, QPoint(0, 0));   // ✗ 崩
```

`QWidget::mapTo(parent, pos)` 的实现是"**从自己沿父链往上走，直到撞见 parent**"。
而**标尺与画布是兄弟**：两者都挂在中央网格宿主上（画布在标签容器里）。
父链从画布往上走到根也撞不见标尺，于是 `w` 变成 `nullptr`，
紧接着 `w->mapToParent(p)` **解引用空指针 → 进程当场段错误**。

正确写法 —— **经全局坐标中转，与层级无关**：

```cpp
return mapFromGlobal(m_view->mapToGlobal(QPoint(0, 0)));   // ✓ 兄弟/堂兄弟都成立
```

★★ **为什么这个 bug 特别值得记：它的症状极具误导性** ★★

```
MainWindow 构造完成     ← 一切正常
resize 完成             ← 一切正常
show 完成               ← 一切正常
Segmentation fault      ← 崩在 show() 之后的第一次重绘里
```

构造、装配、菜单、图标、自检的**全部数学断言**都是绿的 ——
因为崩的是"把换算结果画到屏幕上"这一步。第一眼看上去像"画布或布局坏了"。

★ 定位手法（与 17.11 同一套，但这次要跨"进程边界"）★
自检开头就崩在 `[1]`，看不出崩在哪。往 `newWindow()` 里插 `fprintf(stderr,…)` 后，
**最后一行是 `show 完成`** → 锁定"崩在 `processEvents()` 的重绘里"；
再往 `RulerWidget::paintEvent` 里分段插桩，最后一行停在"有文档" →
范围收成 `canvasSize() / canvasOrigin() / zoom()` 三行，一眼就是它。
两轮插桩定位完毕，验完即删。

### 18.4 ★★ 真 bug ②：**测试里**犯了同一个错 ★★

修复 18.3 之后自检反而"走得更远才崩"（从 `[1]` 变成 `[15]`）——
因为我刚写的测试里有一行：

```cpp
const QPoint originInRuler = cv2->mapTo(hr, QPoint(0, 0));   // ✗ 同一个错
```

`hr`（标尺）不是 `cv2`（画布）的祖先 —— 同样是兄弟。改成：

```cpp
const QPoint originInRuler = hr->mapFromGlobal(cv2->mapToGlobal(QPoint(0, 0)));
```

★★ **规律**：`mapTo/mapFrom` 这一族在"自绘控件 + 网格宿主"的工程里是**高频雷区**，
因为"谁是祖先"这件事在改写布局时会变（标尺从浮动改成网格、标签容器插进来…），
而写成兄弟时的失败**不在编译期、不在构造期，而在第一次重绘**。
凡是要在两个**兄弟控件**之间换算坐标，一律走 `mapToGlobal` + `mapFromGlobal`。

★ 顺带：`MainWindow::setupCanvas()` 把标尺从"浮动在画布上"改成"网格宿主里的一格"，
这个改动使**每一次**"标尺 ⇄ 画布"的换算都从"父子"变成了"兄弟" ——
所以这类重构之后，**所有**跨控件坐标换算都要重新过一遍。

### 18.5 拖出方向语义：**参考线方向 == 尺子方向，位置取自垂直位移**

从**顶部**尺子往下拖 → 得到一条**水平**参考线，它的位置是 **y**。
容易写反，而且写反之后**画面看起来完全正常**（线照样画、能拖能删），
只是"尺子上量到的那一格"与"线落在的那一行"差了一个坐标轴。

```cpp
// RulerWidget::perpendicularImagePos() —— 名字里的 perpendicular 就是这条纪律
// 水平尺 → 读 pos.y() → 水平线的位置(y)
// 垂直尺 → 读 pos.x() → 竖直线的位置(x)
```

★ 自检里专门有一条"位置语义"断言：用**画布坐标**反算期望值
（`cv->widgetToImage(...)`），而不是拿尺子上的那一点去比 ——
后者会因为"两边都算错、恰好抵消"而假绿。

### 18.6 松手判定靠 Qt 的**隐式鼠标抓取**

交互语义：按下 = 开始拖一根新线；**松在尺子上 = 放弃，松到画布那边 = 落线**。

```cpp
const bool commit = !rect().contains(zl::eventPos(event).toPoint());
```

★ 这一判定能成立的前提是 **Qt 在按下时做了隐式鼠标抓取** ——
即使光标早已移出尺子（尺子只有 18px 厚），本控件**仍然**收到 move/release。
不抓取的话"松在画布上"这个事件根本送不到尺子，判定就无从谈起。
（这也是为什么"新建从尺子拖出"可以做，而"移动/删除在画布侧"必须分开：
尺子上没有可抓的东西。）

★ 分工是刻意的，别合并：**新建 → 标尺**（`RulerWidget` 只发信号，
不改任何状态，与"面板只读文档 + 只发信号"同律）；**移动/删除 → 画布**
（`guideAtWidget` + `m_draggingGuide`）。合并的话标尺就得知道参考线列表，
而参考线是**每页**的 —— 标尺却是跨页共享的两个控件。

★★ **命中容差必须在控件坐标里（`kGuideGrabPx = 5.0`）** ★★
写成图像坐标的容差会随缩放失真：放大到 800% 时 5 图像像素 = 40 屏幕像素，
"离得老远也抓得住"（于是正常落笔被抢走）；缩小到 10% 时又变成抓不住。
与形状工具的阈值纪律同一条（见第十三章）。

★ 锁定的两层：`Guide::locked`（单根）与 `m_guidesLocked`（全部）。
锁定只影响**命中**，不影响**绘制** —— 线还在，只是拖不动。

### 18.7 参考线是**每页一份的视图状态** → `activateTab()` 里重指

标尺只有两根（跨页共享），参考线每页一份 —— 这个不对称是本章最容易写错的地方。

```
activateTab(index):
  ...
  ⑦ if (m_hruler) m_hruler->setView(m_canvas);
     if (m_vruler) m_vruler->setView(m_canvas);
```

★★ **不重指也能"正常显示"** ★★ 刻度照画、数字照印 ——
只是刻度与图像**对不上**（尺子还在读上一页的缩放/平移）。
属于"看起来对、其实全错"，人眼几乎发现不了，所以自检里把它单列为
本组最重要的一条（切页后断言 `hr->view() == 新画布`）。

★ `RulerWidget::setView()` 里必接一条 `QObject::destroyed` →
把 `m_view` 置空。标尺活得比某一块画布久（标签页关掉了），
而它手里是**裸指针** —— 与"销毁裸指针消费者前先松手"同律（第十七章）。
`setView()` 同时要 `disconnect(m_view, nullptr, this, nullptr)` 断干净旧画布。

★ 三个"应用级偏好"存 `QSettings`（显示标尺 / 显示参考线 / 锁定参考线 + 单位下标），
但**参考线本身不存** —— 它是每页的临时视图状态，关掉就没了。
"清除参考线"作用在**当前页**，其余三项作用在**全局**。

★ `QSettings` 里的单位下标**读回来要先夹到合法范围**：存档可能是旧版本写的、
或被人手改过。越界下标会让 5 个单选项**一个都不选中**（菜单上一片空白），
而 `setRulerUnit()` 又会静默拒绝 —— 用户看到的是"单位菜单坏了"，且全程零报错。
自检里用"写坏 QSettings 再构造窗口"专门照这一条。

### 18.8 菜单口径

- 「标尺单位」子菜单的 5 个单选项**刻意不设 `objectName`**：对账脚本有一条
  "有名字的菜单动作必须有图标"的规则，把它们牵连进来就得给 5 个单选项各配一张图标
  （纯噪音）。定位它们靠**子菜单本身**（`menuRulerUnit` 有 `objectName`）+ `unitAt(下标)`。
- 子菜单**自己**带图标（`view_ruler`），单选项不带。
- 于是自检里**不能直接调 `setRulerUnit()`**（它是普通私有成员函数，不是槽，
  `QMetaObject::invokeMethod` 也找不到 —— 这些槽走的是**函数指针连接**）。
  必须 `menuRulerUnit->actions().at(i)->trigger()`：这样顺带把
  `菜单第 i 项 ⇄ unitAt(i)` 这根线也钉住了（加一个单位、改一次顺序就错位，
  而直接调槽是照不到这个的）。

### 18.9 自检：覆盖什么

| 组 | 内容 |
|---|---|
| ① 装配 | 正好 2 把尺子、方向没写反、厚度 == `kThickness`、父控件是中央宿主（不是浮在画布上） |

| ⑥ ★ 量像素 | `grab()` 前后逐像素比，差异必须集中在 **1~3 行**且**出现青色** —— 防"数学全绿而画面不对" |

## 十九、另存为 ICO 图标（`engine/IcoWriter.*` + `ui/MainWindow::exportIcon`）

> 本章记两件事：**"自己外写一个二进制格式"该怎么验**，以及
> **"Qt 自带插件明明能写，为什么还要自己写"** —— 后者是实测出来的，不是猜的。

### 19.1 上限 512 是**产品定案**；超限要"拒绝"而不是"默默缩小"

用户口径：**边长超过 512 就不许存 ICO**（Windows 官方口径是 256，512 是各图示
工具的通行扩展上限）。`ico::kMaxIconEdge = 512`，`canEncode()` 判"宽高都 >0 且 ≤512"。

★ **超限必须拒绝，不能默默缩到 512** ★
默默缩小的后果是"导出成功了"，用户回头才发现图被改小 ——
这是最难查的一类问题（文件在、能打开、就是内容不对）。
拒绝时给的话必须带**实际尺寸 + 上限 + 怎么办**（见 19.5）。

★ 判据是 `>` 不是 `>=` ★ 恰好 512×512 要放行。
差一像素写反是这里最容易犯的错，自检里有专门一条钉它（植入 D）。

### 19.2 为什么不用 `QImageWriter`（qico 插件）—— ★ 实测结论 ★

本工程**能**用 `QImageWriter(path, "ico")` 写：实测
`QImageWriter::supportedImageFormats()` 里有 `ico`，写 300×300 返回成功。
但**写出来的是 256×256**（270398 字节 ＝ 256 尺寸的 BMP 条目），
而且 `errorString()` 还是 `"Unknown error"` —— 也就是"成功"。

★★ 它会把超过 256 的图**静默缩到 256**，程序一声不响 ★★
所以"另存为 ICO"如果交给插件，用户存 512×512 会拿到 256×256，
**没有任何提示**。这一条是实测出来的（`.buildlog` 里那次一次性探针），
不是照着文档猜的 —— 写注释时"我猜 Qt 会……"是最容易留下错误依据的写法。

另外两条理由：

- **512 上限没法表达**。插件只负责编，不会替我们判断"该不该编"。
- **`qico.dll` 是要单独部署的插件**（`imageformats` 目录）。漏打一个 dll 的症状是
  "PNG 能存、ICO 存不了"，而且要到**运行期**才发现。自写编码器没有这个依赖
  （PNG 是 QtGui 内置格式，不是插件 —— 所以 PNG 条目那条路也稳）。

### 19.3 两种条目：≤256 走 BMP，257~512 走 PNG

目录项 `ICONDIRENTRY` 里的宽/高**各只占 1 个字节**，而且**其中 0 表示 256**：

| 尺寸 | 条目 | 理由 |
|---|---|---|
| 1~255 | BMP | 字节能原样表达 |
| 256 | BMP | 用 0 表达（0 ⇔ 256） |
| 257~512 | **PNG** | 1 个字节**结构上就装不下** 256 以上 |

BMP 条目 = 40 字节 `BITMAPINFOHEADER` + 自下而上的 32bpp BGRA + 自下而上的 1bpp AND 掩码。
PNG 条目 = 整段 PNG 直接塞进去（Vista 之后的官方扩展）；此时目录项的宽高写 0，
**真实尺寸以 PNG 头为准**（Windows 与 Qt 都是这么读的）。

★ 于是**别写"目录项宽高总是等于图像尺寸"这种断言** —— 257 以上它必然不等。
自检里按条目类型分开断言：BMP 条目对拍尺寸，PNG 条目断言"字节是 0"、
再由**往返**（读回来的宽高必须等于原尺寸）来钉真尺寸。

★★ 一条最强的**整体不变量**：`dwImageOffset + dwBytesInRes == 文件总长` ★★
它一次就覆盖"条目里记的长度"与"实际写出去的字节数"是否一致 ——
不成立就意味着文件里有缺口或冗余，任何读图程序都会读错位。
比逐个字段对拍更能抓住"某处算错了一个字节"。

### 19.4 三个"写进去就错、但肉眼看不出来"的坑

① **`biHeight` 记的是 XOR 图 + AND 掩码的合计高度（＝ 2 × h）**
   漏乘 2 的后果：读图程序把像素数据的前一半当图像、后一半当掩码，
   症状是"图标上下错位、下半张变成黑白噪点"。

② **AND 掩码的位语义：置 1 ＝ 全透明**，且**最高位对应最左边的像素**。
   写反了老读图程序会把不透明像素从背景里"挖掉"。
   ★ 只对 `alpha == 0` 置位，半透明**不置位** ★（半透明还是有墨，置位等于把它挖空）。

③ **预乘数据必须先还原成非预乘**
   `qRed()`/`qBlue()` 直接读 `Format_ARGB32_Premultiplied` 拿到的是"乘过 alpha"的值，
   写出去半透明区域明显偏暗。不透明像素完全正常 —— 只有带透明边缘的图才会暴露。
   转换**放在编码器内部**（`ico::encode` 自己转），不散给调用方：
   散出去就必然出现"这条路径转了、那条路径忘了"。

★ 掩码**自己按位拼**，不要 `Format_Mono` + `createAlphaMask()` + `invertPixels()` ★
`createAlphaMask()` 的阈值语义与"要不要盖住背景"并不等价，而 `invertPixels()`
在 1bpp 上到底改颜色表还是改位，跨 Qt 版本口径不一。一个字节一个字节写最短、最没歧义。

### 19.5 验证法：**字节级结构 + 用别人的读取器往返**

自写二进制格式，"本程序能写"毫无意义（本程序根本不读它）。所以两路夹：

1. **字节级结构**：手写小端 `putU8/putU16/putU32`（不用 `QDataStream` ——
   它默认大端，漏设 `setByteOrder()` 的话产出文件"看着完全正常"但谁也打不开；
   手写没有"忘记设"这个失败模式），逐字段对拍 + 那条整体不变量。
2. **往返**：写出去之后用 **Qt 自带的 ico 读取器**读回来逐像素比。
   两套独立实现互相印证，这条最像"用户真的能打开吗"。

★ 覆盖尺寸要**跨过 256 这条分界线**：16 / 32 / 48 / 256（BMP）与 300 / 512（PNG）。
★ 测试图要**四种 alpha 各一份**（不透明 / 半透明 / 全透明 / 另一种不透明），
  否则"透明通道被丢掉"根本测不出来。

### 19.6 ★★ 分流点只此一处：`MainWindow::writeImage` ★★

```cpp

    QString err;
```

★ **`saveDocument()`（Ctrl+S 到已有 .ico）与 `saveDocumentAs()`（另存为）都经过
`writeImage`** ★ 所以在这里分流 = 两条路自动覆盖，不可能出现
"另存为能存 ICO、Ctrl+S 又走回插件"这种不一致。

★ 自检怎么钉住"真的走了自写分支" ★
判据必须**能区分两套实现**：我们的编码器 >256 写 PNG 条目、尺寸原样保留；
qico 插件 >256 静默缩到 256。于是断言是
**"打开一张 300×300 的 ico → 触发「保存」→ 读回来仍是 300×300"**，
外加"图像数据仍以 PNG 魔数开头"。
"文件存出来了"这种弱判据**根本抓不住**（插件也会写出一个合法 ico）。
★ 这一条在植入验证里是 H 号：关掉分流后它立刻红。

★ 触发要用**菜单动作**（`findChild<QAction*>("actionSave")->trigger()`），
不要直接调 `saveDocument()` —— 它是 private，而动作那条正是用户走的路。
★ 触发前**先把文件删掉**：不删的话"保存失败"与"保存成功但内容没变"分不开，
文件还在，断言照样绿（典型假绿）。删掉之后"文件重新出现"本身就是写入发生了的证据。

### 19.9 这次"测试自己写错"的三处（都值得记）

1. **`pixelColor()` 会按格式还原，`pixel()` 不会**
   `ARGB32_Premultiplied` 的图上，`pixelColor(0,0).red()` 会把预乘除回去，
   于是"断言前提：预乘数据的红已经不是 255"永远不成立。要读内存原值用 `pixel()`。
2. **PNG 条目的目录项字节本来就装不下 257 以上**
   第一版 `validateStructure()` 一律断言"目录项宽高 == 图像尺寸"，
   于是 257/300/512 全红。**是断言写错了，不是代码错了** ——
   发现"多个尺寸报同一种错"时要先怀疑断言，而不是急着改实现。
3. **窄字符串字面量里嵌 ASCII 引号会直接断编译**
   `"……不是"超过""` 这种写法（`"` 是全角/半角混着敲出来的）会提前终止字面量。
   本轮在 `ico_test.cpp` 里一次踩了四处，改成 `【】` 收尾。
   ★ 这一条与 `ruler_test.cpp` 那次是同一个坑，第二次踩了。
