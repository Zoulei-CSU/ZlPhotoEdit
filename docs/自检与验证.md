# 离线自检与验证

> 怎么在没有显示器的环境里测一个 Qt 桌面程序，以及自检脚本本身最容易犯的错。
> 构建见 [构建与运行.md](构建与运行.md)；实现约束见 [实现铁律.md](实现铁律.md)。

## 离线自检

`tests/` 下是**不依赖界面**的算法自检程序。它们不属于应用工程
（两套构建配置都只收集 `src/` 下的文件），独立编译运行。

```bash
source build_env.sh     # 构造 MSVC 环境
./run_tests.sh          # 编译并运行 tests/ 下的全部自检（含一条不编译的静态对账）
./run_tests.sh actions  # 只跑静态对账：主窗口菜单动作 + 图标三方对账，秒回
./run_tests.sh icon     # 只跑图标自检（依赖极轻：只有 IconLibrary 自己）
./run_tests.sh layer_panel  # 只跑图层面板自检（纯函数 + 自绘像素，刻意不链 commands/）
./run_tests.sh magicwand    # 只跑魔术棒（判据取哪张图 / 容差边界 / 四种运算 / 羽化顺序）
```

> `tests/action_check.py` 是**静态对账**，不编译、不链接，所以秒回，
> 但它守的是**编译器永远抓不到**的错误 —— 见下表最后两行。

### 为什么值得单独写这些测试

画笔的颜色数学（预乘 alpha 空间的 source-over、擦除、选区乘算）是
"编译通过、运行不报错、但结果悄悄错误"的重灾区。典型症状 ——
半透明边缘发灰、橡皮擦不干净、选区外缘一圈淡影 —— 在界面上都不明显，
靠肉眼几乎发现不了，只有逐像素断言才靠得住。

调整/曲线这一层同理，而且它的错误更"安静"：一张 50% 透明的白色像素
在预乘格式里存的是 `(128,128,128,128)`。如果实现里漏了"先反预乘再查表"，
这个像素会拿着 128 去查表 —— 于是半透明区域被当成中间灰处理，颜色明显
不对，但因为只有半透明像素受影响，在照片上很容易被当成"原图就这样"。
`adjust_test.cpp` 里有一条**精确到个位数**的断言来钉死它：
把 `255 → 100、128 → 7` 这条表作用上去，正确结果必须是 **50**
（反预乘得 255 → 查表得 100 → 乘回 alpha），漏了反预乘就会得到 **7**。

> 读像素时必须用扫描线而不是 `QImage::pixel()`：后者对预乘格式会做
> 反预乘转换（把 `(128,128,128,128)` 报成 `(255,255,255,128)`），
> 正好把这个 bug 粉饰掉，拿它写断言等于白测。

#### 通道广播：一个"灰度测试图完全测不出来"的真实 bug

`applyLuts()` 里有一条按单表优化的分支。它的判据是
`ChannelLuts::isMonochrome()`，含义是**三条曲线长得一样**：

```
lutR(x) == lutG(x) == lutB(x)      对任意 x
```

但实现时被误解成了"**像素的 R/G/B 三个分量一样**"，于是写成：

```cpp
if (mono) { const int v = lutR[ir]; r = g = b = v; }   // 只查红通道再广播
```

这两件事毫无关系。任何 `R≠G≠B` 的像素，其 G/B 都会被红通道的查表结果
覆盖 —— 用户拉一下亮度滑块，彩色照片就会整体变成"用红通道值渲染"的
单色版本。

它之所以能潜藏很久，是因为两个巧合叠在一起：

1. `applyLutRgb()` 构造出的 `ChannelLuts` **天然**满足 `isMonochrome()`，
   于是这条错误分支覆盖了**亮度 / 对比度 / RGB 主曲线的全部调用**；
2. 之前所有 LUT 断言用的都是**灰度像素**（`R == G == B`）。
   灰度图上"各查各的"与"查一个再广播"结果**完全相同**，测不出来。

真正抓到它的是 `ui_smoke_test.cpp` —— 它用的源图是一个彩色像素
`(128, 96, 64)`，默认参数下 `apply()` 返回的却是 `(128, 128, 128)`。
修法是把判断**提到循环外**，只让 `lutG`/`lutB` 指向同一张表（省的是
256 字节表的 cache 占用，不是查表次数），三个通道始终用各自的输入值查表。
`adjust_test.cpp` 里补了 1.7 节共 13 条彩色像素断言来守住它。

> 教训：**测试数据的取值范围要覆盖实现的假设边界**。
> 只用灰度像素测 LUT，等于默认"通道之间可以互换"，而这恰恰是被测代码
> 内部做的一个隐含假设 —— 用同样的假设去测它，等于没测。

另外，曲线那部分的判据是"**整个 256 项输出方向一致**"而不是"必须递增"：
内置的「反相」预设就是一条递减直线，它完全正确；真正危险的是
**段内回勾**（曲线在小段里先升后降），那会在图像上压出色带、
让高光里冒出反相噪点 —— 这正是选用 Fritsch–Carlson 单调样条而非
Catmull-Rom 的原因。

选区这套代码有两个更隐蔽的坑，都是靠这套断言才揪出来的：

1. **静默失效**：`Selection::setFromPath()` 内部需要一份"尺寸参考"蒙版，
   新文档上蒙版为空时它会**直接 return，一个标志位都不改**。表现是
   "用户拖着画了半天框，松手后什么都没有"，而且没有任何报错、没有日志。
   `tests/selection_test.cpp` 里专门有一段在**固化这个错误行为**
   （不调 `prepareCanvas` 就必须失败），这样将来谁改了这段逻辑都会立刻可见。
2. **羽化半径的口径**：三次盒式模糊是串联的，总扩散 ≈ 3 × 单趟半径。
   历史实现把用户给的 `radius` 直接当作单趟半径，实际羽化范围是标称值的
   **3 倍** —— 用户填"羽化 4 像素"得到 12 像素的模糊，选区硬边彻底消失。
   测试里用"距边界 3 像素处应被染到、距边界 8 像素处应仍为 0"两条断言
   把这个口径钉死，改回去就会失败。

另外，`run_tests.sh` **只链接 Qt5Core 与 Qt5Gui**。这顺带成了分层纪律的
守门人：哪天有人往 `engine/` 里加了 QtWidgets 依赖，这个测试会立刻
编译失败，而不是等到某天有人抱怨"engine 层编译变慢"才被发现。

界面层的测试是**按需**开例外（`moc_headers_for` / `extra_libs_for`
两个函数按测试名返回 extras）：只有 `ui_smoke_test`、`view_test`、
`crop_test`、`layer_panel_test` 与 `mainwin_test` 会额外跑 moc 并链接
`Qt5Widgets.lib`。`geometry_test` 也要跑 moc，但只为
`core/Document.h`（它带 `Q_OBJECT`，构造 `Document` 就需要
`metaObject()`/`qt_metacall()`），**不链接 QtWidgets** —— 它测的是
engine 与 core，不该、也拿不到界面依赖。这样 engine/core 的纪律仍然被守住。

> `layer_panel_test` 还额外守了一条**边界**：它**刻意不链 `commands/`**。
> 面板本来就该在"没有 `CommandStack`"的情况下可用（它只发信号，
> 压命令是 `MainWindow` 的事），所以真链上 `commands/` 反倒掩盖了这条约束。

#### 渲染占位：一个"数学全对、画面还是错"的真实 bug

`view_test` 的前六组断言算的都是"矩阵把图像映射到了哪"，它们是**关于数学**
的断言。但用户看到的是**像素**，中间还隔着 `paintEvent` 的十步呈现管线。
这两件事可以完全脱节 —— 实际就脱节了：

用户报告「打开照片后显示的尺寸完全不对，滚轮缩放也异常」。矩阵那一层
（`rebuildViewTransform` 的平移被缩放、`setZoomAt` 的锚点漂移）确实有两个
真 bug，修完数学断言全绿。但补上第 7 组**渲染占位**断言后立刻失败：

```
期望图像矩形 x= 10.0 y= 45.6 w=1260.0 h=708.8
实测红色包围盒 x= 13   y= 61   w= 414   h= 232
```

`414 / 1260 = 0.3286`，正好是缩放比；`(13, 61) ≈ (10, 45.6) × 1.328`。
这两个数字指向 `T(p) = M(M(p)) = offset·(1+zoom) + zoom²·p` ——
**视图变换被施加了两遍**。

根因在 `CanvasView::drawComposite()`。`paintEvent` 第 2 步已经把 painter 的
变换设成 `m_viewTransform`，并明确约定「第 3~9 步全部用**图像坐标**书写」。
但 `drawComposite` 先把目标矩形手工 `m_viewTransform.mapRect()` 成屏幕坐标，
再交给这个已被变换过的 painter —— 于是矩阵乘了两次：

```cpp
// 错：target 是屏幕坐标，但 painter 还会再映射一次
const QRectF dstRect = m_viewTransform.mapRect(QRectF(srcAligned));
painter.drawImage(dstRect, source, sourceRect);

// 对：target 用图像坐标，交给 painter 去映射（与第 3~9 步的约定一致）
painter.drawImage(QRectF(srcAligned), source, sourceRect);
```

症状之所以难认，是因为**棋盘格与图像边框是对的**：它们都先
`resetTransform()` 再按屏幕坐标画。于是屏幕上出现的是
「正确的取景框 + 里面缩成一小块的图像」，看起来像"图像尺寸算错了"，
非常容易把人引到 `zoom`/`offset` 的数学上去排查。
而且 `zoom → 1` 时 `zoom² → zoom`、`offset·(1+zoom) → 2·offset`，
**100% 附近几乎看不出异常**，只有缩放/居中时才明显。

> 教训：**测量渲染结果，而不是测量你喂给渲染器的参数。**
> `grab()` 会把控件真的渲染一遍（走完整 `paintEvent`），
> 用一张纯色标记图（这里用纯红，与背景灰 `(80,80,80)` 三通道都拉开距离）
> 再取包围盒，就能得到**用户实际看到的尺寸**。
> 只断言 `imageToWidget()` 的返回值，等于在测"我的数学"，而不是"用户的屏幕"。

#### 示意图的坐标契约：同一个坑的第二次现形

画布大小对话框左侧会画一张示意图：**实线**＝新画布、**虚线**＝原画布范围、
**蓝色块**＝内容、**深红块**＝会被裁掉的内容。它自己有一套绘制管线 ——
把四个**图像坐标**矩形等比映射到控件坐标后再画。

这条管线里唯一容易出错的地方是"漏掉映射"。实测就这么错了：

```cpp
const QPainterPath contentPath = rectPath(contentInNew);      // ✗ 图像坐标
const QPainterPath contentPath = rectPath(m(contentInNew));   // ✓ 映射到控件坐标
```

一幅 3840×2160 的照片，漏映射后"内容路径"就是一个 3840×2160 的矩形
直接铺在两百多像素宽的控件上，于是：

- `内容 ∩ 画布` 退化成**整块画布** → 蓝色铺满，新扩出来的透明区看不见了
- `内容 − 画布` 退化成**画布以外的全部区域** → 红块从画布四周溢出
- 而虚线用的是映射后的值，**看起来还是对的**

结果画面上是"红底上一个蓝框"，与真实情况（蓝块只占旧画布范围）完全不符。
**不崩、不报错、信息面板文案全对**，`contentOffset()` 的数学对账也全绿。

守门断言（`ui_smoke_test`，同 `view_test` 的"渲染占位"思路）：

| 断言 | 为什么它抓得住 |
| --- | --- |
| 放大时**没有任何深红像素** | 放大不可能裁内容，是纯逻辑必然，容差可以开到 0 |
| 内容色块右/下边缘与画布边框**有空白** | 漏映射时间距会从几十 px 塌到 1~2 px |
| 虚线**可见像素数可观** | 内容包围盒常等于整幅旧画布，虚线若画在内容之前会被整条埋掉（实测只剩 3 px） |

顺带定死了绘制顺序：底色 → 旧画布"将被移除"区 → 内容 → **原画布虚线** → 新画布边框。
虚线必须在内容之后（否则被埋），边框必须最后（压在一切之上）。

> 教训：**同一个"数学对了、画面错了"的坑，会在每一条自绘管线里各出现一次。**
> 每写一个自绘控件，就要有一个"量它画出来的像素"的断言。

#### 单位只是显示方式：一个「拨一下开关就把图改掉」的陷阱

尺寸类对话框的输入框现在有**像素 / 百分比**两种单位，画布大小那侧还能与
「相对」叠加，于是同一个目标尺寸有四种写法：

| 单位 | 绝对（目标） | 相对（增量） |
| --- | --- | --- |
| 像素 | 新宽 = `n` px | 新宽 = 原宽 + `n` px |
| 百分比 | 新宽 = 原宽 × `n`% | 新宽 = 原宽 × (100 + `n`)% |

它们在实现上是**同一个东西**：`m_target`（`QSize`，像素）永远是唯一真相，
单位、相对模式、长宽比锁定都只是它的**视图**。这条边界一旦被越过，就会
写出这样的代码：

```cpp
// ✗ 切换单位时"顺手换算一下"
m_unit = unit;
m_target.setWidth(inputToTarget(m_width->value(), m_original.width()));
```

用户只是拨了一个显示开关，图却被真的改了 —— 而且撤销栈里会多出一条
几百 MB 的、他自己都不明白怎么来的记录。正确做法与切换「相对」完全一致：
**先松范围、再回写显示、`m_target` 一个像素都不动**。

边界情况都在「按各维度算输入框区间」里收口（`inputRangeFor`）：

| 决定 | 理由 |
| --- | --- |
| 上限 `(20000 × 100) / 原尺寸`，**向下取整** | 4000 宽的图上 500% 恰好到 20000，501% 就越界。向上取整会让滑块"拨不到头"（拨到头反而被改写成更小的数） |
| 上下限**按宽、高分别算** | 4000×3000 的图上，宽的上限 500%、高的上限 666%。共用一个区间必有一边永远拨不到顶 |
| 下限 `max(1%, 最接近 1 像素的整数百分比)` | 百分比是整数尺子，1% 已是最细一格；要精确到像素就切回像素单位 |
| 取整**四舍五入（.5 远离零）**，不截断 | 截断会让"缩到 50% 再放回 100%"每次少一像素，用户来回拉几下图就真的变小了 |

换算本身放在引擎层（`geometry::percentToPixels` / `pixelsToPercent`），
与 `canvasResizeOffset()` 同理：**一个算法只能有一处实现**，
否则"输入 33% 却显示 34%"这种只在特定尺寸下复现的怪相迟早出现。

> 守门断言也走"先证明它抓得住 bug"这一步：把上面那段 ✗ 的写法临时植入，
> `ui_smoke_test` 立刻从 0 失败变成 **8 项失败**（两个对话框都报
> 「切换单位不改变目标尺寸」失败），随即撤掉。没有这一步，"断言全绿"
> 只说明代码没变，说明不了断言有没有盯着东西。

**裁剪工具（`crop_test`）的三次植入验证**（每次都先跑红、再撤销）：

| 植入的改动 | 结果 |
| --- | --- |
| 浮点框→像素的判据退化成"相交"（`floor(left)` / `ceil(right)-1`） | 报「宽 40.0 的框给出 40 列像素 期望 40，实际 41」，4 项变红 |
| 遮罩只填框内（删掉 `bounds` 子路径） | 报「框外未被压暗的像素 18385 个，首个在 (0,0)」+「框内被压暗 3311 个」，9 项变红 |
| 去掉「框 == 整幅画布时框内按下算拉新框」这条特例 | 首拖无反应 → 后续全线崩塌，20 项变红 |

> ★ 一条反面教训 ★
> 最初写的植入方案是"把遮罩两个子路径对调"。那是**错的** ——
> 奇偶填充只看穿过次数，谁先谁后结果完全相同，照那个方案做会看到
> 测试**依然全绿**，然后误判成"断言抓不住 bug"，进而把一条本来有效的
> 断言删掉。**植入必须是真正能改变行为的那种改动**，改完先确认
> "这个改动会让程序出错吗"，再去看断言有没有红。

**主窗口装配（`mainwin_test`）的植入验证**（两条 bug 一起植入，看各自的失败签名）：

| 植入的改动 | 结果 |
| --- | --- |
| 删掉 `setupTools()` 里的 `buildToolBox();` | 第 [1] 组 9 项变红：「工具箱按钮数 == ToolManager 的工具数 期望 6，实际 0」 |
| 删掉连接之后那次显式同步 | 第 [2]~[6] 组 23 项变红：「画布拿到活动工具（非 nullptr）」等 |

合计 **15 通过 / 32 失败**。第二条还顺带证明了链式依赖：**画布没有活动工具时，连"拖出选区"都做不到**（事件根本没被派发），所以后面两组也跟着红 —— 这正是"整体失效"的样子，也是它必须由一条**不变量**而不是"某个按钮存在"来钉住的原因。

> ★ 这两个 bug 的形态值得单独记一笔 ★
> 它们都不在算法里，而在构造函数里各个 `setup*()` 的**调用次序**上：
> 工具箱的按钮**只能**在工具注册完之后建；而"信号只能传达变化、传达不了现状"——
> 对象在连接建立之前就改过状态时，连接之后必须**显式补推一次**当前状态。
> 详见 `docs/实现铁律.md` 第九章。

### 界面代码怎么在没有显示器的环境里测

Qt 自带 `qoffscreen` 平台插件。设 `QT_QPA_PLATFORM=offscreen` 后，窗口
不显示，但控件会被真实地创建、布局，`QWidget::grab()` 会真的走一遍
`paintEvent` 把内容渲染到离屏缓冲。于是"构造函数里空指针 / 绘制代码里
除零 / 信号断链"这类崩溃都能在 CI 里被抓出来 —— 比"启动主窗口看看
进程还活着"强得多。前面那个通道广播 bug 就是这么浮出水面的。

> **截图的文字会是空的？** offscreen 平台用的是极简字体库，默认找不到字体，
> 于是 `grab()` 出来的对话框**所有文字都不渲染**（只画控件框），
> 启动时会打印 `QFontDatabase: Cannot find font directory ...`。
> 断言不受影响（像素比较用的是颜色不是文字），但想拿截图给人看就要
> 指一个字体目录：`QT_QPA_FONTDIR=C:/Windows/Fonts`（见
> `.buildlog/shot/` 下那个一次性截图工具）。

### ★ 自检脚本本身最危险的 bug：假绿 ★

`cl` 用 `/Fe:` 指定输出，**只有编译链接成功才会写出 `.exe`**。如果脚本
在编译失败后只判断"文件是否存在"，那么上一次构建留下的旧 `.exe` 会被
当成这次的结果运行，于是：

```
编译失败 → 复用旧二进制 → 打印上一次的「通过 93 项」 → 整套显示全绿
```

而这次改的代码其实**一行都没编进去**。实测踩过：给 `adjust_test.cpp`
新增 13 条断言后，输出仍是原来的 93 项。

修法很简单但必须做：**编译前先 `rm -f` 掉旧的可执行文件**（moc 的旧产物
同理）。自检脚本一旦会给出"假的好消息"，它守的每一条断言都失去意义 ——
所以这类问题应当当成 P0，而不是"顺手改改"。


### ★ 编译器抓不到的错误：菜单动作对账 ★

有一类错误**编译器永远抓不到**，因为它的每个实参都是合法的：

```cpp
imageMenu->addAction(m_actionRotateArbitrary);   // ← 菜单里加了
// …而全项目没有一处： m_actionRotateArbitrary = new QAction(…);
```

`m_actionRotateArbitrary` 是 `nullptr`，而 `QMenu::addAction(nullptr)` 只是
**静默什么都不做** —— 菜单项凭空消失。后果是：

- 编译 **0 错 0 警**（`nullptr` 是合法实参）；
- `ui_smoke_test` **测不到**（它根本不链接 `MainWindow`，只测对话框）；
- 双构建全绿、全部断言全绿、**只有把程序真正跑起来点开菜单才看得见**。

实测踩过：任意角度旋转对话框做完后，是截图工具去走**真实菜单动作**
（`findChild<QAction*>("actionRotateArbitrary")` 返回空）时才暴露的。

→ 补上 **`tests/action_check.py`**（`./run_tests.sh actions`）。它同时检查：

| # | 检查 | 级别 |
| --- | --- | --- |
| ① | 进了菜单的名字必须有 `= new …` 创建语句 | 错误 |
| ② | 创建了的 `QAction` 必须有 `setObjectName()`（自动化靠它定位） | 错误 |
| ③ | `MainWindow.h` 里声明了却从未进任何菜单 | 警告 |
| ④ | 代码里引用的图标名 ⇄ `resources/icons/*.svg` 必须存在 | 错误 |
| ⑤ | `resources.qrc` ⇄ `resources/icons/` 目录必须一一对应 | 错误 |
| ⑥ | 磁盘上有、却没有任何地方引用的图标（下一阶段的预留） | 警告 |

**动作"四件套"：`new` → `setObjectName` → `connect` → `addAction`，四处齐全。**

> ★ **对账脚本本身也要先证明它抓得住 bug** ★
> 动手验证时，把出问题的那行**注释掉**再跑，脚本却报了通过 —— 因为正则
> 把**注释里的赋值**当成了真代码。→ **匹配前必须先剥掉注释**（`//` 与
> `/* */`）。这是上文「守门断言必须先验证它抓得住 bug」在**静态检查**上的
> 同一形态。
