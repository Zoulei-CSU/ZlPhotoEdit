# 构建与运行

> 把 ZlPhotoEdit 从零跑起来：环境要求 → 两种构建方式 → 踩过的构建坑 → 发布打包 → 目录结构。
> 功能一览见 [../README.md](../README.md)；自检见 [自检与验证.md](自检与验证.md)。

## 环境要求

| 项目 | 版本 |
| --- | --- |
| Qt | 5.15.16 (MSVC 2022 64-bit) |
| 编译器 | MSVC 14.4x（Visual Studio 2022） |
| 构建 | qmake 或 CMake |
| C++ | C++17 |

本机已确认安装路径：

- Qt：`C:\Qt\5.15.16-VS2022-rel`
- Qt Creator：`C:\Qt\QtCreator-8`
- VS 2022：`C:\Program Files\Microsoft Visual Studio\2022\Professional`

> 注意：本机 Qt 为 Release-only 构建（目录名带 `-rel`），**只能编译 Release 配置**，Debug 会链接失败。

## 构建

工程提供**两套等价的构建配置**，任选其一即可。两套都同时兼容
Qt 5.15 与 Qt 6.x，切换 Qt 版本时不需要改任何文件。

> **关于"等价"的程度**：两套配置编译同一份源码、用同样的 `/utf-8` 与
> C++17 设置，功能完全一致。但**产物不是字节相同的** —— 两边的链接顺序
> 不同（qmake 按 `.pro` 里手写的顺序，CMake 按 `GLOB` 的字母序），
> 链接器据此排布代码段，产物会差几百字节。这是正常的，不代表配置有差异。
> 要判断两边是否真的等价，应该比较"编译了哪些源文件"而不是文件大小。

### 方式一：qmake（与 Qt Creator 一致）

在 VS 2022 x64 Native Tools 命令提示符中：

```bat
call "C:\Program Files\Microsoft Visual Studio\2022\Professional\VC\Auxiliary\Build\vcvars64.bat"
set PATH=C:\Qt\5.15.16-VS2022-rel\bin;%PATH%

qmake ZlPhotoEdit.pro
nmake release
```

产物：`release\ZlPhotoEdit.exe`

也可以用 Qt Creator 8 直接打开 `ZlPhotoEdit.pro`，选择
`Desktop Qt 5.15.16 MSVC2022 64bit` 套件构建。

### 方式二：CMake + Ninja

`cmake` 与 `ninja` 不需要单独安装 —— 它们随 VS 2022 的
「使用 C++ 的桌面开发」工作负载一起发布，位于
`<VS>\Common7\IDE\CommonExtensions\Microsoft\CMake\`。

```bat
call "C:\Program Files\Microsoft Visual Studio\2022\Professional\VC\Auxiliary\Build\vcvars64.bat"

cmake -S . -B build_cmake -G Ninja -DCMAKE_BUILD_TYPE=Release ^
      -DCMAKE_PREFIX_PATH=C:\Qt\5.15.16-VS2022-rel
cmake --build build_cmake
```

产物：`build_cmake\bin\ZlPhotoEdit.exe`

> **建议**：日常开发用 qmake（增量构建快、与 Qt Creator 无缝）；
> 提交前用 CMake 做一次 `--clean-first` 全量构建。
> 原因见下方「构建陷阱」第 3 条。

### 在 Git Bash 中构建

本机默认 shell 是 Git Bash，而 `vcvars64.bat` 是批处理脚本，在 bash 里
`call` 它**不会把环境变量导出到当前 shell**（子进程的环境不回流）。
因此仓库提供了一个辅助脚本 `build_env.sh`，它手工拼出 `cl.exe` 需要的
`PATH` / `INCLUDE` / `LIB`：

```bash
source build_env.sh          # 构造 MSVC 环境（会打印探测结果）
cmake --build build_cmake    # 或 qmake + nmake
```

该脚本也把 `cmake` 与 `ninja` 的目录加进 `PATH`（它们不在系统 PATH 里，
不加会报 `cmake: command not found`）。

## 构建陷阱（踩过的坑，改配置前请先读）

这些问题的报错信息与实际原因相距很远，记录在此避免重复排查。

1. **必须显式加 `/utf-8`，且对 CMake 要用 `target_compile_options`。**
   MSVC 默认按本地代码页（GBK）解释源文件。本工程是 UTF-8 中文注释 +
   中文字符串常量，若不加 `/utf-8`，某个中文字符的第 3 个字节可能恰好是
   `0x5C`（反斜杠），把行尾的引号或换行「吃掉」，编译器随即报出一大串
   看似无关的错误 —— 例如 `C2001: 常量中有换行符`、
   `C3646: 未知重写说明符`，甚至污染到 Qt 自己的头文件
   （`qvariant.h` / `qimagereader.h`）。这些报错位置全是「错误现场的
   邻居」，不是真正的病灶，很容易误判成源码有语法错误。

   另外 `add_compile_options()` **只对它在文件中之后定义的 target 生效**。
   本工程 `add_executable()` 写在前，因此必须用
   `target_compile_options(ZlPhotoEdit PRIVATE /utf-8)` 才能可靠生效。

2. **`INCLUDE` / `LIB` 必须用 Windows 路径形式。**
   在 Git Bash 里设置时要用 `C:/Program Files/...`，不能用 MSYS 的
   `/c/Program Files/...`。后者会让 `cl.exe` 报
   `fatal error C1083: 无法打开包括文件 type_traits` ——
   看起来像「缺了标准库」，实际只是路径形式不对。同理 `rc.exe` 在
   Windows SDK 的 `bin/<ver>/x64` 下，必须单独加进 `PATH`，否则链接阶段
   报 `LNK1158: 无法运行 rc.exe`。这些都在 `build_env.sh` 里处理好了。

   **同一条规则也适用于传给 `cl.exe` 的源文件路径与 `/Fo` `/Fe` 输出路径。**
   `cl /I /d/Code/.../src ...` 会把整个路径当成命令行选项，报出极具
   误导性的两条消息：

   ```
   cl: 命令行 warning D9002 :忽略未知选项"/d/Code/.../Brush.cpp"
   cl: 命令行 error D8003 :缺少源文件名
   ```

   看起来像"忘了给源文件"，实际又是路径形式不对。`run_tests.sh` 里的
   `to_win()` 就是干这个的（`cygpath -m` 转成 `D:/Code/...` 混合形式）。

3. **qmake 增量构建会掩盖错误，CMake 全量构建不会。**
   `nmake release` 只重编改动过的文件。如果某个 `.cpp` 的 `.obj` 是本轮
   之前就已存在的，它里面的错误不会被发现 —— 直到某次全量重建才突然
   冒出来。这是本项目实际踩到的坑：一批 `QList` / 头文件包含的问题在
   qmake 下潜伏了很久，换成 CMake `--clean-first` 后一次性全暴露。
   **所以两者都要能编过，才算真正编过。**

4. **Qt5 的 `QList<T>` 与 `QVector<T>` 不等价。**
   Qt5 的 `QList` 是「指针数组 + 内联存储」的混合结构：没有 `resize()`、
   没有 `(size, value)` 构造函数、没有 `data()`/`constData()`（不保证
   连续内存）。凡需要「预分配长度 + 按下标随机访问 + 连续内存」的场合
   必须用 `QVector`（Qt6 里 `QVector` 是 `QList` 的别名，所以写 `QVector`
   两版都能编）。本项目 `engine/` 层的像素缓冲全部用 `QVector`。

5. **Qt5/Qt6 差异只允许出现在 `src/compat/QtCompat.h`。**
   典型差异：`QMouseEvent::localPos()`（Qt5）vs `position()`（Qt6）；
   `QImage::mirrored()`（Qt5）vs `flipped()`（Qt6，且一次只能翻一个方向）；
   `QWheelEvent` 需要用 `pos()`（Qt5）vs `position()`（Qt6），
   **且 `QWheelEvent` 从来没有 `localPos()`**。
   需要新写版本判断时，请加进兼容层，不要在业务代码里散落 `#if QT_VERSION`。

6. **源码保存为 UTF-8 with BOM。**
   三重保险里的第一重（另外两重是上面的 `/utf-8`，以及 `.pro` 里的
   `msvc { QMAKE_CXXFLAGS += /utf-8 }`）。校验方式：

   ```bash
   head -c 3 src/main.cpp | od -An -tx1     # 应为 ef bb bf
   ```

7. **lambda 里调用基类成员函数，即使写了类名限定也仍然要捕获 `this`。**
   MSVC 对"在未捕获 `this` 的 lambda 里调用基类成员"一律报 `C4573`
   （"要求编译器捕获 this，但当前默认捕获模式不允许"）——
   **写成 `QObject::connect(...)` 这种静态调用形式也没用**，
   它只认捕获列表。

   本项目实际踩过：`MainWindowActions.cpp` 里一个只捕获了
   `[list, rebuildList]` 的 lambda 内调用了 `QObject::disconnect` /
   `QObject::connect`，加限定符后警告照旧，最后靠补上 `this` 捕获解决。

## 目录结构

```
src/
├── main.cpp    程序入口（高 DPI / UTF-8 编码设置 / 启动日志）
├── compat/     Qt5 ↔ Qt6 兼容层（唯一允许出现版本判断的地方）
├── core/       数据模型（Layer / LayerList / Document / Selection / ClipboardData）
├── engine/     图像算法（纯函数，无 UI 依赖）
├── commands/   撤销重做命令（QUndoCommand 子类）
├── tools/      交互工具（策略模式）
└── ui/         界面控件

resources/      图标（生成物，勿手改）
├── gen_icons.py    ★ 唯一真相：生成 78 张 .svg 并重写 resources.qrc
├── icons/*.svg     24×24 单色 SVG
└── resources.qrc   Qt 资源清单（prefix="/"，所以路径是 :/icons/xxx.svg）

tests/          离线自检（不属于应用工程，见「离线自检」一节）
                brush / fill / selection / adjust / ui_smoke / geometry / ruler /
                ico / view / crop / tool_paint / shape / text / text_tool /
                hand_zoom / layer_panel / tabs / icon / mainwin
                + action_check.py（静态对账，不编译，秒回）
```

依赖方向严格单向：`ui → tools → commands → core → engine`

> 有一个类刻意"逆流"放置：`tools/MarchingAnts.h` 是选区边界的绘制函数。
> 它被 `ui/CanvasView`（画已有选区）与 `tools/SelectionTool`（画拖动预览）
> 同时使用。放进 `ui/` 则工具层无法复用，放进 `engine/` 又违反"engine 不碰
> QPainter"。放在 `tools/` 是唯一让两个调用方都能用、且不破坏依赖方向的位置。

其中 `engine/` 是**无副作用的纯函数层**：输入 `QImage` + 参数 → 输出新
`QImage`，不持有状态、不弹窗、不碰 `QUndoStack`。这一层因此可以脱离 UI
单独做单元测试，也便于将来并行化。

> `engine/Brush.h` 里 `stampTipInPlace()` 是这一层唯一的例外（原地修改
> 传入的蒙版缓冲），原因与边界都写在那个函数的注释里 —— 累积蒙版是
> 画布尺寸的，若按纯函数风格每次落笔都返回新蒙版，内存带宽会成为瓶颈。

调整类功能的一份代码拆在两层，边界很清楚：

```
engine/Histogram.h     直方图统计（纯函数：QImage → 256 项计数）
engine/Adjust.h        亮度/对比度/色相/饱和度/明度/色阶（都是烘焙 LUT）
engine/Curves.h        控制点 → LUT（Fritsch–Carlson 单调样条）
engine/Lut.h           查表应用（唯一处理"预乘往返"的地方）

ui/AdjustmentDialog.h  调整对话框基类：apply() 纯函数接口 + 确定/取消/复位
ui/BrightnessContrastDialog.h / HueSaturationDialog.h / CurvesDialog.h
ui/CurveEditor.h       曲线控件（内部状态是 0..255 整数，边界处与 engine 互转）
ui/LevelsDialog.h      色阶对话框（数值框 + 自动；apply() 就是一条 levelsLut）
ui/LevelsWidget.h      色阶控件（直方图 + 五枚手柄；灰点位置由烘焙表反查）
```

对话框**不认识 `Document`**：它只有一个
`virtual QImage apply(const QImage &src) const = 0`。把它接到文档、撤销栈、
画布上的是 `MainWindow::runAdjustment()` —— 这样对话框既能脱离界面
单独测试，将来也能直接拿去做批处理。

根目录辅助文件：

| 文件 | 用途 |
