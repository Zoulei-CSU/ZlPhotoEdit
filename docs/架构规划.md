### 1.1 Qt5 / Qt6 双版本兼容约定

工程需**同时支持 Qt 5.15 与 Qt 6.x**。这不是"以后再说"的事 —— 它决定了写代码时的每一个 API 选择。约定如下：

**（1）工程配置双份**

| 文件 | 用途 |
| --- | --- |
| `ZlPhotoEdit.pro` | qmake（本机 Qt5 主力构建方式） |
| `CMakeLists.txt` | CMake（Qt5 与 Qt6 都能用，`find_package(QT NAMES Qt6 Qt5)` 自动探测） |

CMake 用 `Qt${QT_VERSION_MAJOR}` 变量化目标名，这样同一份 `CMakeLists.txt` 在 Qt5 和 Qt6 下都能工作：

```cmake
find_package(QT NAMES Qt6 Qt5 REQUIRED COMPONENTS Core Gui Widgets)
find_package(Qt${QT_VERSION_MAJOR} REQUIRED COMPONENTS Core Gui Widgets)
target_link_libraries(ZlPhotoEdit PRIVATE
    Qt${QT_VERSION_MAJOR}::Core Qt${QT_VERSION_MAJOR}::Gui Qt${QT_VERSION_MAJOR}::Widgets)
```

**（2）API 差异与统一写法**

以下差异会实际影响本项目，全部按"兼容写法"实现，**不散落 `#if`，而是集中在 `src/compat/` 里包一层**：

| 差异点 | Qt 5.15 | Qt 6 | 统一写法 |
| --- | --- | --- | --- |
| 鼠标事件坐标 | `event->localPos()` / `pos()` | `position()`（`localPos` 已删） | `src/compat/QtCompat.h` 内联函数 `zl::eventPos(e)` |
| 滚轮事件坐标 | `event->pos()` / `position()` 均有 | 仅 `position()` | `zl::wheelPos(e)` |
| 滚轮滚动量 | `angleDelta()` / `delta()` | 仅 `angleDelta()` | 只用 `angleDelta()`（两版都有） |
| 图像镜像 | `QImage::mirrored()` | `QImage::flipped()` | `zl::mirrorImage()` 包装 |
| 全局坐标 | `QMouseEvent::globalPos()` | `globalPosition()` | `zl::eventGlobalPos(e)` |
| 高 DPI 缩放 | 必须 `AA_EnableHighDpiScaling` | **默认开启**，该枚举已废弃 | `#if QT_VERSION < QT_VERSION_CHECK(6,0,0)` 显式设置 |
| 高 DPI 位图 | 必须 `AA_UseHighDpiPixmaps` | 默认开启 | 同上 |
| 字符串与容器 | `QString::split` 返回 `QStringList` | 有行为差异（`QStringView`） | 不依赖具体返回类型，用 `auto` |
| `QRegExp` | 可用 | **已移除** | **一律用 `QRegularExpression`** |
| `QLinkedList` / `QVector` | 均可用 | `QLinkedList` 已移除；`QVector` 是 `QList` 别名 | 一律用 `QList`，**不用 `QVector` 也不用 `QLinkedList`** |
| `foreach` 宏 | 可用 | 已移除，须用范围 for | **一律用范围 for**，不用 `foreach` |
| `QTextStream` 编码 | `setCodec("UTF-8")` | `setEncoding(QStringConverter::Utf8)` | `zl::setUtf8(stream)` 包装 |
| `QImage::Format_` | 枚举在 `QImage::` 下 | 移到 `QImage::Format` 枚举类（值不变） | 直接引用 `QImage::Format_ARGB32` 两侧都对 |
| `QPainter::drawText` 返回 | `void` | 返回 `QRectF`（有重载歧义风险） | 不依赖返回值 |
| `qSort` / `qSwap` | 可用 | 已移除 | 用 `std::sort` / `std::swap` |
| `QPainter::HighQualityAntialiasing` | 已废弃但仍存在 | 已移除 | 不用，只用 `Antialiasing` / `SmoothPixmapTransform` |
| `QDesktopWidget` | 可用 | 已移除 | 用 `QScreen` / `QGuiApplication::screens()` |

**（3）从第一天就遵守的硬性规矩**（写代码时对照）

1. **不用 `QVector`** —— 用 `QList`（Qt6 中 `QVector` 就是 `QList` 的别名，但显式写 `QList` 两版一致）
2. **不用 `foreach`** —— 用范围 for
3. **不用 `QRegExp` / `qSort` / `qSwap` / `QLinkedList` / `QDesktopWidget`** —— 全部是 Qt6 已删除项
4. **不用 `QMouseEvent::pos()` / `localPos()` 直接写** —— 走 `zl::eventPos()`
5. **不想 `#if QT_VERSION` 散落各处** —— 版本判断只允许出现在 `src/compat/` 与 `main.cpp` 两处
6. **`QString` 与 `const char*` 的隐式转换** —— Qt6 默认关闭，一律显式 `QStringLiteral()` 或 `tr()`

> **第 5 条是这套兼容方案能长期维护的关键**：如果 `#if QT_VERSION` 散布在 20 个 `.cpp` 里，将来升级 Qt 会变成考古工作。集中到 `src/compat/` 后，升级时只需改这一个目录。

**（4）本机验证方式**

本机只有 Qt 5.15.16，**Qt6 兼容性靠"规矩"保证而非编译验证**。CI 或另一台机器上可用 Qt6 编译同一份 CMake 工程验证。写代码时如果拿不准某个 API 在 Qt6 里是否还有，**查 Qt 文档确认，而不是猜**。

## 2. 总体架构

采用经典的**分层 + MVC 变体**结构。核心思路是：**文档模型只管数据，画布只管呈现，工具只管交互**，三者通过信号槽解耦。

### 设计原则

1. **Document 持有全部像素数据，CanvasView 不持有**。画布每次重绘都从 Document 取合成结果（带缓存），保证数据单一来源。
2. **工具不改数据，只产生 Command**。所有对像素/图层结构的修改都封装成 `QUndoCommand`，压入 `QUndoStack`。这样撤销重做零成本接入，且天然支持脚本化。
3. **滤镜在单独的 QImage 副本上运算，完成后再提交为 Command**。避免长耗时操作锁死 UI。
4. **ImageEngine 全部是无副作用纯函数**：输入 `QImage` + 参数，输出新 `QImage`。便于单元测试，也便于后续接多线程。

**合成算法**（`composite` 的核心）：

```
result = 空白透明图 (ARGB32_Premultiplied)
for layer in layers:                       // 从底到顶
    if (!layer.isVisible() || layer.opacity() == 0) continue
    result = blend(result, layer.image(),
                   layer.blendMode(), layer.opacity())
```

`blend()` 的通用公式（考虑 alpha 与不透明度）：

```
设 底 s、顶 d（均为预乘 alpha，通道值 ∈ [0,1]）
不透明度 α = layer.opacity
混合函数 f(s, d) 由 BlendMode 决定

对每个通道：
    d' = (1 - α) * d + α * ( (1 - d_alpha) * s + d_alpha * f(s, d) )

即：图层不透明度与像素自身 alpha 相乘后，作为插值权重叠加。
```

**优化策略**：如果顶层图层是 `Normal` 且 `opacity == 1.0` 且不透明区域覆盖了剩余全部，可以直接短路返回该图层——这是最常见的情况，能省掉整轮循环。

### 3.2 Selection —— 选区

用 **8 位灰度蒙版（`QImage::Format_Alpha8` 或 `Format_Grayscale8`）** 表示选区，而不是 `QRegion`。

理由：`QRegion` 只能表达矩形并集，无法支持羽化、抗锯齿边缘、魔棒的多连通区域。灰度蒙版一切通吃，且可直接作为画笔的 alpha 蒙版参与运算。

```cpp
class Selection {
public:
    bool  isEmpty() const;
    QRect bounds() const;          // 选区的紧包围盒
    uchar alphaAt(int x, int y) const;   // 0 = 未选中, 255 = 全选中
    void  setRect(const QRect&);         // 矩形选区
    void  setEllipse(const QRect&);      // 椭圆选区
    void  invert();                      // 反选
    void  selectAll();                   // 全选
    void  clear();                       // 取消选择
    void  feather(int radius);           // 羽化（盒式模糊近似）
private:
    QImage m_mask;    // Format_Grayscale8
};
```

**与工具的关系**：所有写入像素的操作，都要先经过选区约束：

```cpp
// 在画笔落笔前，把笔刷蒙版与选区蒙版求交
QImage mask = brushMask & selection.mask();
```

这样"只在选区内绘制"这个语义就自然实现了，不需要每个工具各自判断。

### 3.3 CanvasView —— 画布控件

这是整个程序交互的心脏。职责有三块：**视图变换**、**输入派发**、**呈现**。

```cpp
class CanvasView : public QWidget {
    Q_OBJECT
public:
    explicit CanvasView(Document* doc, QWidget* parent = nullptr);

    // ── 视图变换 ──
    // 内部统一用 QTransform 建模，不用 zoom + offset 两个标量。
    // 理由：标量只能表达缩放+平移，无法支持"旋转查看画布"。而一旦按标量
    // 写完全部坐标换算，后续加旋转会让所有工具返工。详见 功能覆盖审计.md 3.4 节。
    QTransform viewTransform() const;              // 图像坐标 → 控件坐标
    void       setViewTransform(const QTransform&);

    // 便捷访问器（从矩阵中提取 / 反向构造）
    qreal  zoom() const;                           // 矩阵的缩放分量
    void   setZoom(qreal factor, const QPoint& anchor = QPoint());
    QPoint offset() const;
    void   setOffset(const QPoint&);

    // 视图旋转与翻转（只改显示，不动图像数据）
    void   setViewRotation(qreal degrees);
    void   setViewFlipped(bool horizontal, bool vertical);

    void   zoomIn() / zoomOut() / zoomToFit() / zoomToActualSize();
    void   zoomToRect(const QRect& imageRect);     // 缩放到指定图像区域
    void   setZoomLevel(qreal level);              // 对齐到预设级别（25/50/100/200%）

    // 可视区域（图像坐标），导航器与滚动条用
    QRect  visibleImageRect() const;

    // ── 坐标转换（工具所有鼠标事件都要用）──
    QPoint widgetToImage(const QPoint& widgetPt) const;
    QPoint imageToWidget(const QPoint& imagePt) const;
    QRect  widgetToImage(const QRect& widgetRect) const;

    // ── 交互 ──
    void   setActiveTool(AbstractTool* tool);
    void   setForegroundColor(const QColor&);
    void   setBackgroundColor(const QColor&);

    // ── 辅助显示 ──
    void   setRulerVisible(bool);
    void   setGridVisible(bool);
    void   setGuidesVisible(bool);
    QPoint cursorImagePos() const;                 // 供状态栏显示

signals:
    void viewChanged();                            // 缩放/平移/旋转变化，状态栏与导航器同步
    void cursorMoved(const QPoint& imagePos);      // 光标位置变化
    void panned();                                 // 视口平移（滚动条同步用）

protected:
    void paintEvent(QPaintEvent*) override;
    void mousePressEvent(QMouseEvent*) override;
    void mouseMoveEvent(QMouseEvent*) override;
    void mouseReleaseEvent(QMouseEvent*) override;
    void wheelEvent(QWheelEvent*) override;
    void resizeEvent(QResizeEvent*) override;
    void keyPressEvent(QKeyEvent*) override;
    void contextMenuEvent(QContextMenuEvent*) override;   // 画布右键菜单
    void dragEnterEvent(QDragEnterEvent*) override;       // 拖文件进窗口
    void dropEvent(QDropEvent*) override;

private:
    Document*     m_doc;
    AbstractTool* m_activeTool = nullptr;
    QTransform    m_viewTransform;    // 唯一视图状态源：图像坐标 → 控件坐标
    QImage        m_compositeCache;   // 合成结果缓存
    QRect         m_cachedRect;       // 缓存对应的图像区域
    QPoint        m_lastMouseImagePos;
    bool          m_spacePanning = false;  // 按住空格临时平移

    // 自动滚动（拖拽到边缘时）
    QTimer*       m_autoScrollTimer = nullptr;
    QPoint        m_autoScrollDir;
};
```

**呈现管线**（`paintEvent`）：

```
1. 用 QPainter 填充背景（棋盘格或中性灰）
2. painter.setTransform(m_viewTransform) —— 之后一律用图像坐标绘制
3. 计算可视区域对应的图像矩形（由矩阵逆映射控件矩形得到）
4. 绘制棋盘格底纹（表示透明区域）—— 只在图像矩形范围内
5. 绘制合成结果：
   painter.setRenderHint(SmoothPixmapTransform, zoom < 1.0)
   painter.drawImage(imageRect, m_compositeCache, sourceRect)
6. 绘制网格（若开启）—— 纯视图辅助，不参与合成
7. 绘制参考线（若开启）—— 同上
8. 让当前工具叠加临时图形（如拖动中的选区框、裁剪框、橡皮筋）
   m_activeTool->paintOverlay(painter, this)
9. 绘制选区边界的"蚂蚁线"
10. 结束时 painter.resetTransform()，再绘制不随视图变换的叠加层
    （笔刷轮廓、裁剪框的角柄、尺寸标签 —— 它们应保持屏幕尺寸恒定）
```

> **第 2 步是视图矩阵化的核心收益**：变换一次 `QPainter`，之后所有绘制（网格、参考线、工具叠加、蚂蚁线）都用图像坐标写，不需要各自换算。**但笔刷轮廓、角柄这类需要"屏幕尺寸恒定"的装饰必须在 `resetTransform()` 之后画** —— 否则放大到 800% 时笔刷轮廓会被放大成一个巨大的圈。

**坐标换算**（工具与界面层的唯一入口）：

```cpp
QPoint CanvasView::widgetToImage(const QPoint& p) const
{
    return m_viewTransform.inverted().map(p);
}
QPoint CanvasView::imageToWidget(const QPoint& p) const
{
    return m_viewTransform.map(p);
}
```

**缩放策略**：以鼠标位置为锚点缩放，视觉上更自然。

```
对任意锚点 a（控件坐标），希望缩放后 a 对应的图像点不动：
    T' = T * S(scaleAround)   // 在图像空间围绕 a 的逆映射点缩放
等价实现（用矩阵表达，比标量公式更通用，缩放/旋转/翻转同一套代码）：
    QTransform inv = m_viewTransform.inverted();
    QPointF imgPt = inv.map(a);
    m_viewTransform *= QTransform().translate(imgPt.x(), imgPt.y())
                                   .scale(f, f)
                                   .translate(-imgPt.x(), -imgPt.y());
```

**渲染质量**：放大用 `Qt::FastTransformation`（保持像素锐利，方便看清像素）；缩小用 `Qt::SmoothTransformation`（避免摩尔纹）。

**性能要点**：
- 缓存合成结果。`Document::contentChanged(dirtyRect)` 到达时，只重算脏矩形区域，用 `QPainter` 把新区域画回缓存的对应位置。
- 缩放/平移时不重算合成，只改变 `drawImage` 的目标矩形。
- 若图像超过阈值（比如 4000x4000），在缩小显示时缓存一份降采样版本用于绘制。

### 3.4 AbstractTool —— 工具接口

用**策略模式**统一所有工具，新增工具只需实现一个子类，不改画布代码。

**工具参数体系**：12 个工具各有自己的参数（画笔大小、容差、线宽、字体…），但**不要每个工具各写一套 UI**。统一用"工具选项条 + 参数对象"的机制：

```cpp
/// 工具参数的基类。每个工具持有一个自己的参数对象
class ToolOptions {
public:
    virtual ~ToolOptions() = default;

    /// 由工具实现：创建选项条控件并绑定到自身参数
    virtual QWidget* createWidget(QWidget* parent) = 0;

    /// 参数变化时发出，工具据此更新内部状态（如重建笔刷蒙版）
    /// 用信号槽而非直接调用，避免工具与控件耦合
    virtual void load(const QSettings&) = 0;   // 持久化
    virtual void save(QSettings&) const = 0;
};
```

**关键设计**：

- 每个工具持有 `std::unique_ptr<ToolOptions>`，`ToolOptionsBar` 在工具切换时取出它并调用 `createWidget()` 重建选项条。
- **参数持久化用 `QSettings`** —— 用户上次用的画笔大小、容差、字号，下次启动应保留。
- **参数变化用信号通知**，不要让工具直接持有控件指针（否则工具的 UI 依赖侵入 engine 层）。

各工具的参数字段：

| 工具 | 参数 |
| --- | --- |
| 画笔 / 橡皮 | 大小(1-500)、硬度(0-100%)、不透明度(0-100%)、流量、颜色 |
| 油漆桶 | 容差(0-255)、抗锯齿、连续/非连续、不透明度、混合模式 |
| 吸管 | 取样范围(点/3×3/5×5 平均) |
| 直线 | 线宽、线型、颜色、抗锯齿 |
| 矩形 / 椭圆 | 线宽、描边/填充/两者、填充色、圆角半径（矩形） |
| 文字 | 字体、字号、颜色、粗体/斜体/下划线、对齐、行距、字间距 |
| 选区 | 模式（新建/添加/减去/交集）、羽化半径、抗锯齿 |
| 移动 | 是否自动选择图层、是否显示变换框 |
| 裁剪 | 预设比例、是否删除裁剪区域外的像素、网格叠加 |
| 抓手 / 缩放 | 无（缩放工具有"放大/缩小"切换） |

### 3.5 CommandStack —— 撤销重做

直接用 Qt 的 `QUndoStack` / `QUndoCommand`，不自己造轮子。

```cpp
// CommandStack 是对 QUndoStack 的薄封装，额外提供信号转发
class CommandStack : public QObject {
    Q_OBJECT
public:
    QUndoStack* stack();

};
```

`HistoryPanel` 可以直接用 `QUndoView` 挂到 `QUndoStack` 上，几行代码就得到一个可点击跳转的历史列表。

#### 各类 Command 设计

| Command 类 | 记录内容 | undo 实现 |
| --- | --- | --- |
| `DrawCommand` | 目标图层、目标矩形、绘制前像素、绘制后像素 | 把绘制前的像素写回 |
| `LayerAddCommand` | 图层对象、插入位置 | 从列表中移除 |
| `LayerRemoveCommand` | 图层对象、原位置 | 插回原位置 |
| `LayerMoveCommand` | from / to 索引 | 反向移动 |
| `LayerPropertyCommand` | 属性名、旧值、新值 | 写回旧值 |
| `SelectionCommand` | 旧选区蒙版、新选区蒙版 | 写回旧蒙版 |
| `ImageAdjustCommand` | 目标图层、整层旧像素、整层新像素 | 写回旧像素 |
| `GeometryChangeCommand` | 新旧画布尺寸、**所有图层**的新旧位图、选区新旧蒙版 | 整体恢复旧尺寸与旧位图 |
| `LayerMergeCommand` | 参与合并的图层、合并结果图层、原位置 | 拆回原图层 |

**尺寸类 Command 的内存问题**：这是最耗内存的一类 —— 要存所有图层的前后两份位图。4 图层 × 4000×3000 就是 384MB/步。必须用 `qCompress` 压缩存储（级别 3 是速度快慢与压缩率的平衡点），并对这类 Command 单独限制步数。详见 [画布与文件操作设计.md](画布与文件操作设计.md) 第 2 节。

**关键权衡：像素级撤销的粒度用什么？**

两种方案，按操作类型分别采用：

- **脏矩形方案**（适合 `DrawCommand`）：只保存被改动的那一块像素。画笔一笔画过去可能覆盖大片区域，但相比整层仍然省很多。用一个 `QRect` 追踪本次拖动累计影响的区域。
- **整层快照方案**（适合滤镜/调整/变换）：这类操作本来就作用于全图，逐像素记录反而更费。直接存前后两份 `QImage`。

**内存上限控制**：给 `QUndoStack` 设 `setUndoLimit(30)`，超出后自动丢弃最早的历史。一张 4000x3000 的 ARGB 图层约 48MB，30 步整层快照理论上能到 1.4GB —— 所以整层快照的 Command 要谨慎使用，优先在可能的情况下走脏矩形。可以考虑对整层快照做 `qCompress` 压缩存储来降内存。

### 3.6 ImageEngine —— 图像算法库

全部为无状态自由函数，不依赖 Qt Widgets，可独立测试。

#### blend.cpp —— 混合模式

对 **22** 种混合模式，逐通道计算（★ 数量以 `src/core/ImageTypes.h` 的 `BlendMode` 枚举与 `allBlendModes()`
为准 —— 该枚举的**注释**至今还写着"与 Photoshop 的 16 种常用模式对齐"，是过期注释，别照抄）。核心是定义一组混合函数 `f(backdrop, source) -> result`：

| 模式 | 公式（归一化到 [0,1]） |
| --- | --- |
| Normal | `f = s` |
| Multiply | `f = s * d` |
| Screen | `f = s + d - s * d` |
| Overlay | `f = d <= 0.5 ? 2*s*d : 1 - 2*(1-s)*(1-d)` |
| Darken | `f = min(s, d)` |
| Lighten | `f = max(s, d)` |
| ColorDodge | `f = d == 0 ? 0 : (s == 1 ? 1 : min(1, d / (1 - s)))` |
| ColorBurn | `f = d == 1 ? 1 : (s == 0 ? 0 : 1 - min(1, (1 - d) / s))` |
| HardLight | `f = s <= 0.5 ? 2*s*d : 1 - 2*(1-s)*(1-d)` |
| SoftLight | 见 W3C 标准公式（分段多项式） |
| Difference | `f = abs(s - d)` |
| Exclusion | `f = s + d - 2*s*d` |
| Hue / Saturation / Color / Luminosity | 在 HSL 空间按分量替换（W3C 定义） |

> **实现建议**：`Hue` / `Saturation` / `Color` / `Luminosity` 这四种需要 RGB↔HSL 转换，逐像素做浮点转换很慢。可以预先建 256 项的查找表（LUT）加速；或者第一版先只做前 12 种，这四种留作后续增强。

**并行化**：对整层合成，按行分块用 `QtConcurrent::blockingMap` 并行处理，多核机器上能有接近线性的加速。注意每个线程只写自己负责的行，避免数据竞争。

#### adjust.cpp —— 调整

| 功能 | 算法 |
| --- | --- |
| 亮度 | `v' = clamp(v + delta)`，delta ∈ [-255, 255] |
| 对比度 | `v' = clamp((v - 128) * k + 128)`，k 由参数映射到 [0, 4] |
| 色相 | RGB→HSL，`h' = (h + delta) mod 360`，HSL→RGB |
| 饱和度 | HSL 空间 `s' = clamp(s * k)` |
| 明度 | HSL 空间 `l' = clamp(l * k)` |
| 锐化 | 3x3 卷积核 `[0,-1,0; -1,5,-1; 0,-1,0]`，或 unsharp mask |
| 高斯模糊 | 分离式高斯（先横后纵），半径小用直接卷积，半径大用三次盒式模糊近似 |
| 去色 | 按亮度权重 `gray = 0.299R + 0.587G + 0.114B` |
| 反色 | `v' = 255 - v` |
| 阈值 | `v' = v > t ? 255 : 0`（按亮度判定） |
| 浮雕 | 方向性卷积 `[-2,-1,0; -1,1,1; 0,1,2]` |
| 怀旧/棕褐 | 色调映射矩阵 |
| **曲线** | **控制点 → 单调三次样条 → 256 项 LUT。详见 [曲线调整设计.md](曲线调整设计.md)** |

#### curves.cpp / lut.cpp —— 曲线与查找表

曲线是调整类功能里表达力最强的一个：亮度、对比度、色阶都只是它的特例（一条直线或分段直线）。它不参与逐像素数学运算，而是**先把控制点烘焙成 256 项查找表（LUT），再逐像素查表**。

```
控制点列表 (x, y)  ──bakeLut()──→  256 项 LUT  ──applyToRgb()──→  新 QImage
```

插值必须使用 **Fritsch–Carlson 单调三次样条**。普通 Catmull-Rom 样条在陡峭段会产生过冲（回勾），映射到图像上就是暗部反转、色带和噪点 —— 这是曲线实现的经典坑。

**查找表优化（全调整模块通用）**：亮度、对比度、反色、阈值、去色、曲线这类逐通道独立运算，统一走 `Lut::applyToRgb()` 这条流水线，预先烘焙 LUT 后一次遍历完成。

```cpp
// 以亮度为例
quint8 lut[256];
for (int i = 0; i < 256; ++i)
    lut[i] = qBound(0, i + delta, 255);

// 然后对每个像素直接查表
```

> 亮度/对比度对话框可以复用曲线的 LUT 烘焙流水线（把滑块参数换算成控制点），省掉一套映射代码。

**预乘格式陷阱**：`ARGB32_Premultiplied` 存储的是已乘过 alpha 的值，直接查表会导致半透明区域色偏。正确做法是在 `applyToRgb()` 内部先转 `Format_ARGB32`（非预乘）运算，结束后再转回预乘。详见曲线设计文档第 3.2 节。

> 注意：**这条规则只适用于逐通道独立运算的调整**。混合模式（`Blend.cpp`）和重采样（`Resample.cpp`）的运算本来就定义在预乘空间上，反而应该保持预乘格式，不要做这个转换。

#### transform.cpp —— 几何变换

`transform.cpp` 里的函数都是**图层级**的（作用于单个 QImage）。**图像级**的旋转/翻转（作用于全部图层 + 画布尺寸跟着变）由 `Document` 层组织调用这些函数，详见 [画布与文件操作设计.md](画布与文件操作设计.md)。

| 功能 | Qt 实现 |
| --- | --- |
| 旋转 90°/180°/270° | `QTransform::rotate(90)` + `QImage::transformed`，走整数变换，无插值损失 |
| 任意角度旋转 | `QTransform::rotate(angle)`，配合 `SmoothTransformation` |
| 水平/垂直翻转 | `QImage::mirrored(true, false)` |
| 裁剪 | `QImage::copy(rect)` |
| 缩放 | `QImage::scaled(size, aspectMode, mode)` —— 但仅用于邻近/双线性；**默认走自实现的 bicubic**，见 [画布与文件操作设计.md](画布与文件操作设计.md) 第 8.4 节 |
| 画布扩边/裁切 | 新建目标尺寸的透明图 + `QPainter::drawImage` 按锚点偏移绘制 |

旋转后画布尺寸要跟着变（用 `QTransform::mapRect` 计算新的包围盒），并把所有图层的位图都做同样变换。

> **90° 整数倍必须走无损路径**：虽然数学上等价于任意角度旋转，但走插值路径会引入不必要的重采样损失。判断时用容差比较（`fmod` 的结果可能是 89.999999），不要用 `==`。

#### Resample.cpp —— 高质量重采样

Qt 只提供邻近（`FastTransformation`）和双线性（`SmoothTransformation`）。本项目**自实现 bicubic**，对照片的放大与二次缩小有可见的画质提升。

| 方法 | 实现 | 适用 |
| --- | --- | --- |
| 邻近 | `QImage::scaled(..., Qt::FastTransformation)` | 像素画、需要硬边缘 |
| 双线性 | `QImage::scaled(..., Qt::SmoothTransformation)` | 预览、快速运算 |
| **两次立方（默认）** | **自实现，Keys 三次卷积 a = -0.5** | 照片缩放 |
| 两次立方（更锐） | 自实现，a = -0.75 | 需要更锐利时 |

**两个必须遵守的实现要点**：

1. **分离式两遍一维卷积**，绝不做二维 4×4 卷积。复杂度从 `O(W1·H1·16)` 降到 `O(W0·H1·4 + W1·H1·4)`。
2. **权重必须归一化**（`Σw[j] = 1`）。三次卷积核在非整数偏移处求和不为 1，不归一化会导致图像整体变亮或变暗 —— 这是实现 bicubic 最容易漏的一步。

完整算法与性能预算见 [画布与文件操作设计.md](画布与文件操作设计.md) 第 8.4 节。

| 功能 | 算法 |
| --- | --- |
| 去色 | 按亮度权重 `gray = 0.299R + 0.587G + 0.114B` |
| 反色 | `v' = 255 - v` |
| 阈值 | `v' = v > t ? 255 : 0`（按亮度判定） |
| 浮雕 | 方向性卷积 `[-2,-1,0; -1,1,1; 0,1,2]` |
| 怀旧/棕褐 | 色调映射矩阵 |
| 油漆桶填充 | 见下方专节 |

#### 油漆桶的容差算法

原规划只有一句"扫描线种子填充，支持容差"，以下把算法定清楚。

**容差比较用欧氏距离**，不要用逐通道差值（会让某些颜色组合被误判为相近）：

```cpp
/// 返回 0-255 的色差，三通道等权重
static inline int colorDistance(QRgb a, QRgb b)
{
    const int dr = qRed(a)   - qRed(b);
    const int dg = qGreen(a) - qGreen(b);
    const int db = qBlue(a)  - qBlue(b);
    return qRound(std::sqrt(qreal(dr*dr + dg*dg + db*db) / 3.0));
}
```

> 除以 3 再开方是为把结果归一化到 0-255，让容差滑块的范围符合直觉（容差 30 大致表示"肉眼能看出的轻微差异"）。

**用扫描线填充**，不要用逐点四邻域递归（慢且会爆栈）：

```
1. 取起始点颜色 seedColor
2. 用栈保存待处理线段，初始压入起始行
3. 循环取出一行 (y, xLeft, xRight)：
   a. 向左右扩展直到颜色超出容差
   b. 标记这些像素已填充
   c. 检查上下两行中与当前线段重叠的部分：
      若存在未填充且颜色在容差内的连续段，压入栈
4. 直到栈空
```

**必须维护一个"已填充"标记**（`QBitArray` 或单独 `Grayscale8` 蒙版），否则相邻线段会重复压栈导致死循环 —— 这是扫描线填充最常见的 bug。

**连续 / 非连续**：

- **连续**（默认）：只填充与起始点连通的区域，即上面的扫描线算法
- **非连续**：填充全图中所有容差内的像素，不管连通性。实现简单（一次全图遍历）

**抗锯齿边界**：直接填硬边缘会有明显锯齿。正确做法是对边界**部分填充** —— 超出容差但在"容差 + 软化带"内的像素，按距离线性插值混合：

```cpp
const int dist = colorDistance(pixel, seedColor);
if (dist <= tolerance) {
    out = fillColor;                                  // 完全填充
} else if (dist <= tolerance + softBand) {
    const qreal t = qreal(dist - tolerance) / softBand;
    out = blendColors(pixel, fillColor, 1.0 - t);      // 过渡带
}
```

**与选区求交**：填充范围先与选区蒙版求交，只在选区内生效（与其他工具一致）。

### 3.8 DocumentManager —— 文档管理抽象

`MainWindow` **不直接持有 `Document*`**，而是通过管理器。这样从单文档扩到多标签时，上层业务代码不用改。

```cpp
class DocumentManager : public QObject {
    Q_OBJECT
public:
    Document* currentDocument() const;
    int       documentCount() const;
    Document* documentAt(int index) const;

    Document* createDocument(const QSize& size, const QColor& fill);
    Document* openDocument(const QString& path);
    bool      closeDocument(int index);        // 返回 false 表示用户取消
    bool      closeAll();

    bool      saveCurrent();
    bool      saveCurrentAs(const QString& path);

    /// 剪贴板粘贴的智能定位需要判断"是否同一文档"
    bool      isOwnerOf(const Document* doc) const;

signals:
    void currentChanged(Document* doc);
    void documentAdded(int index);
    void documentRemoved(int index);

private:
    QList<Document*> m_docs;
    QList<QString>   m_titles;      // 标签标题（含 * 标记）
    int m_currentIndex = -1;
};
```

**第一版只支持单个文档**（`m_docs` 最多一个元素），但接口按多文档设计。收益：

- `MainWindow` 里所有 `m_doc->xxx()` 变成 `m_docs->currentDocument()->xxx()`
- 后面接 `QTabWidget` 时只需改 `MainWindow` 的布局部分
- 剪贴板的"同文档原位粘贴"逻辑天然依赖 `isOwnerOf()`

#### 升级到多标签的改造步骤

抽象已经做了，真正接 `QTabWidget` 时按以下步骤（**都不是大改**）：

| 步骤 | 内容 |
| --- | --- |
| 1 | `MainWindow` 中央控件从单个 `CanvasView` 换成 `QTabWidget`，`QTabWidget::setTabsClosable(true)` |
| 2 | 每个标签页持有一个 `CanvasView` + 一个 `Document` + 一个 `QUndoStack`，用一个 `struct DocumentTab` 打包 |
| 3 | `DocumentManager::currentChanged(Document*)` 到达时，把所有面板（图层面板、历史面板、导航器、状态栏）**重新绑定**到新文档。这是改造的关键点 —— 面板必须支持 `setDocument()` 而不是构造时绑定 |
| 4 | 关闭标签触发 `closeDocument(index)`，内部走未保存确认；用户取消则 `return false` 且**不关标签**（与 `closeEvent` 的 `e->ignore()` 同理） |
| 5 | `MainWindow::closeEvent` 改为遍历所有文档询问，任一取消则整体取消 |
| 6 | 命令行参数支持多个文件路径，逐个 `openDocument()`；无参数时新建空白文档 |
| 7 | 视图状态（缩放/平移）、参考线、当前工具**按标签独立保存**，切换标签时整体换掉 |

> **第 3 步是最容易返工的地方**：如果面板在构造时就绑定文档指针，多标签化时每个面板都要改。**从一开始就让所有面板提供 `setDocument(Document*)`**，即使第一版只会被调用一次。这条要求已写入阶段一的目录结构与验收标准。

#### 3.8.1 现状：数据层已完成，缺的只是中央控件那一层

**`DocumentManager` 本身已经全部实现**（`addDocument` / `openDocument`（用 `indexOfPath` 挡重复打开） /
`closeDocument(index)`（内含当前索引修正）/ `setCurrentIndex`（发 `currentChanged`） /
`titleAt` / `allTitles` / `hasUnsavedChanges` / `unsavedDocumentNames` 都在）。
`MainWindow::applyDocumentToPanels(doc)` 也已经是文档切换的**唯一入口**
（重绑画布 / 状态栏 / 图层面板 / `ToolManager` / 撤销栈 —— 遵守约定 7）。

**唯一缺的是中央控件那一层 UI 外壳**：`setCentralWidget(m_canvas)` 目前是单个 `CanvasView`，
`openDocumentFromPath()` 走的是 `closeDocument(旧索引)` —— 也就是严格的单文档体验。
换成 `QTabWidget` 就是上表那七步。

> **（2026-09 更新）这一层外壳已经补上了** —— 见下面的 §3.8.3。

#### 3.8.2 多标签之前，「打开为图层」是同一需求的正解

用户提出的第一个真正跨文档的需求是：

> 从第二幅图片中选择一个区域，复制到第一幅图片上。

这句话里缺的**不是复制粘贴**（复制走系统剪贴板、粘贴为新图层早已实现），
而是**同时看到两张图**。两个可选方案：

| 方案 | 代价 |
| --- | --- |
| 多标签页（3.8 上表七步） | 要重构中央控件，影响面大 |
| **「文件 → 打开为图层…」** | **零架构改动**，多用一步 |

**已按后者落地**：把图 B 整幅变成一个图层，于是“跨文档”问题退化成“跨图层”问题 ——
选区、反选、删除、移动这些图层内操作全部是现成的。
用户的操作变成：`文件 → 打开为图层…` → 在新层上框选 → 反选 → 删除。

两者的关系不是替代而是**先后**：多标签页是同一需求的正解，排在后面单独做；
届时“打开为图层”仍然有用（它就是“导入一张图”这项能力本身）。

实现要点（完整规格见 `docs/实现铁律.md` 第十六章）：

- 「粘贴为新图层」与「打开为图层」共用 `MainWindow::addImageAsNewLayer()`
  —— **“把一张图变成一个新图层”只有一份实现**；
- 新图层位图**必须自己填满画布**，否则会踩到 `Document::addLayer` 那条
  **静默扩画布且不压命令**的路径；
- 导入图比画布大时必须问“扩大画布 / 裁剪到画布”，
  且**绝不把“没人可问”默认为裁剪**（那会静默丢掉用户图片的一部分）；
- 尺寸决策抽成纯函数 `engine/Geometry::unionSize()` / `centeredOffset()`，
  使“扩到多大、放在哪里”成为可断言的事实；
- 扩大画布走 `commitGeometryChange()` 的唯一入口，且**必须先扩画布、后加图层**
  （几何快照含整份图层列表），两件事合成**一条**撤销。

#### 3.8.3 已落地：上表那七步是怎么走的（2026-09，阶段八）

七步**全部完成**，且做到了一件当初没敢指望的事：**业务代码一行没改**。
关键就在下面第 2 条的"三件套仍叫 `m_doc` / `m_commandStack` / `m_canvas`"。

| 步骤 | 落地方式 |
| --- | --- |
| 1 | 中央控件改为 `ui/DocumentTabs`（`QTabWidget` 子类），`setTabsClosable(true)` + `setMovable(true)` |
| 2 | ★ **`struct DocumentTab { Document*; CommandStack*; CanvasView*; }` 打包，但 `MainWindow` 的成员名不改** ★ —— `m_doc`/`m_commandStack`/`m_canvas` 从"唯一的那一份"变成"**当前页**的那一份"，由 `activateTab(index)` 重指。全工程几百处 `m_doc->xxx()` / `m_canvas->xxx()` 因此一行未动 |
| 3 | 面板重绑仍然只有 `applyDocumentToPanels(doc)` 一个入口，只是调用者从"`DocumentManager::currentChanged` 信号"换成 `activateTab()`。同步方向变成**单向**：标签页是真相，`activateTab` 把结果推给 `DocumentManager`（`setCurrentIndex`）与所有面板 |
| 4 | `MainWindow::closeDocumentTab(index)`：先把该页切到前面（未保存确认与保存都作用在"当前页"上，复用同一套 `maybeSave`/`saveDocument`，不写吃 `Document*` 的重载），再走 **摘页 → 重绑 → 销毁文档** 的三步顺序 |
| 5 | `closeEvent` 走 `maybeSaveAll()`：逐页问过去，**任何一页被取消就整体取消**（询问前先把那一页切到前面，用户看到的才是被问到的那张图） |
| 6 | `main()` 把 `app.arguments()` 交给构造函数；`openDocumentPaths()` 收敛"命令行多参数"与"拖入多个文件"两条入口 |
| 7 | 视图状态天然按页独立（一页一块 `CanvasView`）；活动工具与前景/背景色是**应用级**状态，切页时由 `applyDocumentToPanels` **显式推给新画布** |

**这次改造回出的两个真 bug 都在"销毁与重绑的顺序"上 —— 而且都是 `use-after-free`：**

1. **关掉一个标签页 → 段错误**。`removeDocumentTab()` 会 `delete` 掉这一页的
   `CommandStack`，而历史面板（`QUndoView`）的内部模型里存的是**裸**
   `QUndoStack*`；紧接着的 `applyDocumentToPanels()` 会调
   `setStack(新栈)`，而它做的第一件事就是对**旧栈** `disconnect()` ——
   那个旧栈刚刚被 `delete`。
   → 修法是**结构性**的：给 `DocumentTabs` 加 `aboutToRemoveTab(int)` 信号，
   在"栈还活着、但马上要没"的那一刻通知外界松手（`MainWindow::detachStackConsumers`）。
   不做成"调用方记得先解绑"—— 那样"销毁栈"就多了一条隐藏前置条件，
   将来任何一个新调用点忘了它，症状都是随机段错误。

2. **`closeEvent` 逐页销毁文档，却没有让面板松手**。
   `clearAllTabs()` 拆的只是"页"，而图层面板 / 状态栏 / 工具管理器手里还攥着
   各页的 `Document*` —— 它们要等 `applyDocumentToPanels(nullptr)` 才会松。
   于是 `closeAll()` 之后面板全指着已释放的内存，本窗口随后那一轮完整析构
   （面板换绑时都会 `disconnect(m_doc, …)`）随时会踩空。
   → 修法是在 `closeEvent` 里走 **`activateTab(-1)`**：
   "当前页变化"全工程只有这一个入口，**空状态也是它的一种**。

**顺带回出第三个（轻的）**：切页后状态栏的缩放比不跟着换 ——
`CanvasView::viewChanged` 只在**变化**时发，而切页时新画布的缩放本来就是
它自己的值（`setDocument()` 因此早退，一个信号都不发）。
症状是在 1200×800 的页上看到「99.9%」，切到 3840×2160 的页仍然是「99.9%」
（真实值 31.6%），而窗口标题是对的（它直接读 `m_canvas->zoom()`）。
这条是**看截图看出来的**，不是断言先发现的 —— 补断言时顺手做了植入验证
（关掉那一句 → 恰好一条断言变红）。

> 三个 bug 的共同形状：**信号只传达"变化"，传不了"现状"**；
> **销毁一个对象之前，必须先让所有指向它的人松手**。
> 这两条已写进 `docs/实现铁律.md` 第十七章。

### 3.9 视图辅助 —— 标尺 / 参考线 / 网格

这三项都依赖 `CanvasView` 的坐标变换，应放在视图矩阵化之后做。

> **状态：标尺 / 参考线 / 网格三项均已实现**（阶段七）。
> 下面是**落地后**的接口 —— 与最初草图的差异在末尾"实现时的三处修正"里说明。

```cpp
// engine/RulerMetrics.h —— 刻度换算，全是**无副作用纯函数**，不链 QtWidgets
namespace rulermetrics {

enum class Unit { Pixel, Centimeter, Millimeter, Inch, Point };
constexpr int kUnitCount = 5;

Unit  unitAt(int index);            // ★ 单位顺序的**单一协议**：
int   unitIndex(Unit u);            //   菜单顺序 / QSettings 下标 / 枚举值同源
qreal pixelsPerUnit(Unit u, int dpi);   // inch=dpi, cm=dpi/2.54, …；dpi≤0 回落 96
qreal niceStep(qreal x);            // 吸附到 1/2/5×10ⁿ；x≤0 / NaN → 1.0

struct Ticks { qreal major; qreal minor; };
Ticks chooseTicks(qreal zoom, Unit u, int dpi, qreal minLabelSpacingPx);

QString formatLabel(qreal valueInUnits, Unit u, qreal major);
}

// ui/RulerWidget.h —— 上边 / 左边各一个实例
class RulerWidget : public QWidget {
    Q_OBJECT
public:
    static constexpr int kThickness = 18;

    explicit RulerWidget(Qt::Orientation orientation, QWidget *parent = nullptr);

    CanvasView *view() const;
    Qt::Orientation orientation() const;

    void setUnit(rulermetrics::Unit u);
    void setDpi(int dpi);                    // 物理单位的换算基准

signals:
    void guideDragMoved(Qt::Orientation, int posImage);      // 拖拽中
    void guideDragFinished(Qt::Orientation, bool commit);    // 松手；false = 放弃
};

// ui/CanvasView.h —— 参考线归**画布**（每页一份的视图状态）
struct Guide { Qt::Orientation orientation; int position; bool locked; };

// ui/CanvasView.h —— 网格：显示与吸附是**两个独立开关**
void setGridVisible(bool);   void setGridSize(int);   void setGridColor(const QColor &);

bool snapToGrid() const;     void setSnapToGrid(bool);

qreal snapToleranceScreenPx() const;   void setSnapToleranceScreenPx(qreal);

// engine/GridMetrics.h —— 吸附数学，**纯函数**、零 QtWidgets（与 RulerMetrics 同规格）
namespace gridmetrics {
inline bool  isUsable(int gridSize) { return gridSize > 0; }

qreal   nearestLine(qreal v, int gridSize);                  // qRound(v/g)*g
qreal   snapValue(qreal v, int gridSize, qreal tolPx);       // 超容差 → 原值
QPointF snapPoint(qreal x, qreal y, int gridSize, qreal tolPx);
QPoint  snapOffsetForRect(const QRect &rect, int gridSize, qreal tolPx);
}
```

**要点**：

- **参考线从标尺拖出** —— 两者必须一起实现，不能先做标尺再做参考线。
- **单位换算需要 DPI**：`cm`/`mm`/`inch` 基于图像的物理尺寸，而图像本身没有 DPI 概念，
  需从元数据读或用户设定（见 3.10），默认 96 DPI。
- **刻度间隔随缩放变化**：放大到 800% 应显示到像素级，缩小到 10% 应显示到 100px 级。
  判据是**屏幕像素**（`minLabelSpacingPx`），不是图像像素。
- **参考线不进导出**：它们是视图辅助，不是图像内容。
  ★ 落地做法是**结构隔离**——参考线根本不在 `Document` 里（在 `CanvasView` 里），
  所以"导出的图上没有蓝线"是编译期保证的，不需要在合成管线里写 `if`。
- **网格**：可设间距（预设 8/16/32/64/128/256 + 自定义 4~2000）、可设线色、
  可显示、可对齐吸附。★ **"显示"与"吸附"是两个独立开关**（想看着手工对齐、
  或开着吸附不显示网格，都是合理用法）；★ 吸附是**应用级偏好**（存 QSettings），
  但载体是画布（每页一块）→ 切页/新页必须由 `applyDocumentToPanels()` 补推。
  ★ 吸附口径是"**临近才吸**"：离网格线的距离超过容差就不动，容差是**屏幕**
  像素（默认 8px），在 `CanvasView::makeToolEvent()` 里折算成图像像素后塞进
  `ToolEvent`（与 `viewZoom` 同一条路，工具因此不必 include `ui/`）。

**实现时的三处修正**（相对最初草图）：

1. `RulerWidget` 的构造**不收 `CanvasView*`**，改成构造后再 `setView()`。
   原因：标尺是**跨页共享**的两个控件，而画布每页一块 ——
   构造时给的画布在切页后就过期了。`setView()` 是唯一的重指入口。
2. 参考线**不放在 `RulerWidget` 里**，改放 `CanvasView`。
   标尺只"新建"，移动/删除在画布侧（`guideAtWidget`）——
   否则标尺就得知道参考线列表，而列表是**每页**的、标尺却是**全局**的。
3. "画布左上角在本尺子坐标系里的位置"**必须经全局坐标求**
   （`mapFromGlobal(view->mapToGlobal(0,0))`），**不能写 `view->mapTo(this, 0)`**：
   标尺与画布是**兄弟**，而 `mapTo(parent,…)` 的 `parent` 必须是**祖先** ——
   传兄弟进去会沿父链走到 `nullptr` 然后段错误，且崩点在 `show()` 之后的重绘里。
   详见 `docs/实现铁律.md` 第十八章。

### 3.10 元数据 —— EXIF 与 DPI

```cpp
namespace ImageMeta {

struct ExifInfo {
    QImageIOHandler::Transformations orientation;   // 拍照方向
    QString   cameraMake, cameraModel;
    QDateTime dateTime;
    int       dpiX = 96, dpiY = 96;
    QString   colorSpace;                            // "sRGB" 等
};

ExifInfo read(const QString& filePath);

/// 是否需要在打开时自动应用旋转
bool needsAutoRotate(const ExifInfo& info);

}
```

**自动应用旋转**（投入产出比最高的补充之一）：

```cpp
QImageReader reader(path);
const auto tf = reader.transformation();   // Qt 5.5+ 直接支持，无需自己解析 EXIF
QImage img = reader.read();
if (tf & QImageIOHandler::TransformationRotate90)
    img = img.transformed(QTransform().rotate(90));
// ... 处理其余三个变换标志
```

> 手机拍的照片大多带 Orientation 标记。不处理的话用户打开照片发现是躺倒的，还得手动转 —— 而手动转会真的重采样、损失画质。自动处理则是在**无损的整数变换**下完成。

**DPI 元数据**：图像本身只是像素矩阵，没有物理尺寸概念；DPI 是元数据，用于打印和标尺换算。

```cpp
// 写
img.setDotsPerMeterX(qRound(dpiX / 0.0254));
img.setDotsPerMeterY(qRound(dpiY / 0.0254));

// 读
const int dpiX = qRound(img.dotsPerMeterX() * 0.0254);
```

**色彩空间**：文档已明确不做 ICC 管理，但至少要**识别 `QColorSpace` 标记并在导出时保持不变** —— 否则原图是 sRGB、导出后被标成未知，某些软件里会显示偏色。

### 3.11 错误处理与内存降级

现有设计对失败路径考虑不足。以下场景都需要明确的降级行为：

| 场景 | 处理 |
| --- | --- |
| **打开文件失败** | `QImageReader::errorString()` 转可读提示，不崩溃 |
| **打开超大图** | 先读 `reader.size()` 预检。超过阈值（如 1 亿像素）时询问是否继续，并提示可能的内存占用 |
| **`QImage` 分配失败** | 所有构造后检查 `isNull()`，失败则中止操作并提示 |
| **`qCompress` 失败（内存不足）** | 撤销记录降级：跳过压缩存原始数据；若原始也失败，**放弃该步历史但仍执行操作**，提示"内存不足，此操作无法撤销" |
| **`qUncompress` 失败（数据损坏）** | 撤销时不要崩溃，提示历史已损坏并清空栈 |
| **滤镜运算内存不足** | 分块处理降低峰值内存；仍失败则中止并恢复原图 |
| **剪贴板内容超大** | 超过画布面积若干倍时提示 |

**统一原则**：**任何一步失败都不能让程序崩溃或丢失用户已有数据**。宁可不执行，也不要执行到一半留下损坏状态。

实现上所有可能失败的函数返回 `bool` 或用 `std::optional`，不依赖异常（Qt 代码风格如此）。关键路径加 `Q_ASSERT` 与 `qWarning()` 日志。

> **撤销栈的降级路径特别值得注意**：`GeometryChangeCommand` 这类要存几百 MB 快照的操作，在小内存机器上很可能压缩失败。如果它崩溃，用户的整个编辑会话就毁了 —— 而正确行为只是"这一步不能撤销"。

### 3.12 导出扩展 —— ICO 图标（`engine/IcoWriter.*`）

「另存为」的格式列表里早就有 `ICO 图标 (*.ico)`，但**不能交给 `QImageWriter`**。
实测（Qt 5.15.16 / MSVC）：

```
QImageWriter(path, "ico").write(300×300 的图)  →  返回 true
                                                写出的却是 256×256（270398 字节）
                                                errorString() = "Unknown error"
```

★ **它会把超过 256 的图静默缩到 256，程序一声不响** ★
用户存一张 512×512 会拿到 256×256，而且没有任何提示 —— 属于"看起来成功了"的失败。
另有两处不适配：上限判据没有地方可拦；`qico.dll` 属于 `imageformats` 插件，
要单独部署，漏打的症状是"PNG 能存、ICO 存不了"且**只在运行期暴露**。

所以自写一个纯函数编码器（`engine/IcoWriter.*`，只依赖 QtCore/QtGui）：

| 尺寸 | 条目 | 说明 |
| --- | --- | --- |
| 1~255 | BMP | `BITMAPINFOHEADER` + 自下而上 32bpp BGRA + 1bpp AND 掩码 |
| 256 | BMP | 目录项字节写 `0`（**`0` 即 256**） |
| 257~512 | **PNG** | 目录项宽高**各只有 1 字节**，结构上装不下 256 以上；真尺寸以 PNG 头为准 |
| > 512 | — | **拒绝**（`ico::kMaxIconEdge`） |

三点产品/工程口径：

- **512 是产品定案**（Windows 官方口径 256，512 是各图标工具的通行扩展上限）。
  超过就**拒绝并说明原因**（带实际尺寸、上限、怎么办），**不默默缩小**。
- **拒绝发生在合成之前** —— "太大了"这个答案只依赖画布尺寸，先合成一张
  千万像素的大图再丢掉纯属浪费。
- **进文件前必须把预乘还原成非预乘**，且这件事**放在编码器内部**
  （`ico::encode` 自己转）：散给调用方就必然出现"这条路径转了、那条路径忘了"。

★ **分流点只有 `MainWindow::writeImage()` 一处** ★
`saveDocument()`（Ctrl+S 到已有 `.ico`）与 `saveDocumentAs()`（另存为）都经过它，
所以不可能出现"另存为能存 ICO、Ctrl+S 又走回插件"这种不一致。

★ **干活的那半是 public 且不弹窗** ★
`MainWindow::exportIcon(path, errorOut)` —— 与「打开为图层」的
`importImageAsLayer()` 同一套路：带对话框的功能必须把"真正干活"的那半
做成脱离 UI 可调用的入口，否则它永远只能靠人眼验证。详见 `实现铁律.md` 第十九章。

### 3.13 关键实现约定（写代码前必读）

前面各节的架构决策，落到代码上有几条**必须遵守的约定**。集中列在这里，避免实现时遗漏：

| # | 约定 | 违反后果 |
| --- | --- | --- |
| 1 | `engine/` 下的头文件**不得** include 任何 `QtWidgets` 头 | 算法层无法独立测试，分层失效 |
| 2 | 所有写入像素的工具**必须先与选区蒙版求交** | 选区形同虚设 |
| 3 | `DrawCommand` 从第一天起就带 `layerIndex` 字段 | 多图层阶段全部工具返工 |
| 4 | 任何返回 `QImage` 的函数，若内部是从局部变量构造的，**必须 `copy()`** | 悬空指针，不崩溃但画面随机错乱 |
| 5 | 所有 `QImage` 构造后检查 `isNull()` | 大图操作时崩溃 |
| 6 | 调整类运算在 `Lut::applyToRgb()` 内做非预乘往返；混合与重采样**不做**这个往返 | 半透明区域色偏 |
| 7 | 面板类（图层面板/历史/导航器/状态栏）一律提供 `setDocument(Document*)` | 多标签化时全部返工 |
| 8 | 参考线、网格、选区框、裁剪框**不得进入 `composite()`** | 导出图片带上辅助线 |
| 9 | 需要屏幕尺寸恒定的叠加元素在 `painter.resetTransform()` 之后画 | 缩放后装饰被放大 |
| 10 | 全部源文件存 UTF-8 **with BOM**，`.pro` 含 `/utf-8` | 中文字符串乱码 |

> 第 9 条的具体例子：笔刷轮廓圈、裁剪框的角柄、参考线上的拖拽把手。它们是"控件"而非"图像内容"，必须保持固定的像素尺寸。

**数据流（以画一笔为例）**：

```
1. 用户在画布上按下左键
   CanvasView::mousePressEvent
     → 碰撞检测：命中当前图层？在选区内？
     → 构造 ToolEvent { imagePos, button, modifiers, isFirst=true }
     → m_activeTool->mousePress(e)

2. BrushTool::mousePress
     → 记录起点，在内部缓冲区记录本笔的累计脏矩形
     → 生成笔刷蒙版（直径 d、硬度 h、按距离计算 alpha 衰减）
     → 与选区蒙版求交

3. 鼠标移动，反复触发 mouseMove
     → 在上一点与当前点之间做插值（避免快速移动时点稀疏导致断线）
     → 更新内部缓冲区（绘制到临时图层）
     → 发出 repaint 请求（只刷脏矩形）

4. 用户松开左键
   BrushTool::mouseRelease
     → 把整笔的内容作为一个 DrawCommand 提交
        DrawCommand 记录：目标图层、脏矩形、旧像素、新像素
     → commandStack->push(cmd)
     → Document 发出 contentChanged(dirtyRect)

5. 画布响应
   CanvasView::onContentChanged(dirtyRect)
     → 只重算该区域的合成
     → update(映射到控件坐标的脏矩形)

6. 历史面板刷新（由 QUndoStack 信号驱动）
```

> **注意第 3 步的细节**：拖动过程中的实时预览有两种做法。(a) 直接改图层位图，松手时算好撤销数据；(b) 在画布上叠加一个临时图层预览，松手才真正写入。推荐 (a)，因为 (a) 的实现更直接，且 `contentChanged` 的局部重绘机制已经处理好了性能。但要注意在开始绘制前先把这一笔的"旧像素"区域拷出来，松手时才能构造 Command。

## 6. 开发阶段划分

### 阶段一：骨架跑通（可运行的空壳）

**目标**：打开程序能看到窗口，能打开一张图并显示，能缩放平移。

- `main()` 里**先设置高 DPI 属性**（`AA_EnableHighDpiScaling` / `AA_UseHighDpiPixmaps`）
- 建立 qmake 工程，配置 `QT += core gui widgets svg concurrent printsupport`
- `MainWindow` 基本布局（菜单栏 / 工具栏 / 状态栏 / Dock 面板）
- **`DocumentManager` 抽象**（第一版只支持单文档，但接口按多文档设计）
- **所有面板从一开始就提供 `setDocument(Document*)`**（见 3.13 约定 7）
- `Document` + `Layer` + `LayerList` 最小实现（单图层）
- `CanvasView` 的呈现管线：缩放、平移、棋盘格背景
  - **视图变换用 `QTransform` 建模**，不用 zoom + offset 两个标量
  - `paintEvent` 先用 `setTransform()` 统一切换到图像坐标绘制
  - 坐标换算 `widgetToImage` / `imageToWidget` 基于矩阵逆映射
- **文件生命周期**：新建 / 打开 / 保存 / 另存为 / 未保存提示 / 窗口标题 `*` 标记
  - 用 `QImageWriter` 而非 `QImage::save()`，以便设置格式参数
  - 打开时**读 EXIF 并自动应用旋转**（`QImageReader::transformation()`）
  - 详见 [画布与文件操作设计.md](画布与文件操作设计.md) 第 5 节

**验收**：能打开 jpg/png（带 Orientation 标记的手机照片能自动摆正），滚轮缩放（以鼠标为锚点）、空格拖动平移；在 4K 屏上界面清晰不模糊；能另存为 PNG/JPEG 并设置质量参数；改动后标题出现 `*`，关闭时弹未保存提示；**缩放状态下工具叠加层位置正确**（这是验证视图矩阵化是否正确的关键检查点）。

★ **本阶段回出两个真 bug**，都不在新增的算法里，而在**早就存在的公用代码**中：

- `commands/DrawCommand`：构造函数用 `currentStrokeId()`（"最近一次分配出去的
  编号"）填描边号，而唯一会推进编号的 `beginStroke()` **全工程无人调用** →
  所有命令撞号 → `QUndoStack` 按 id 相同调用 `mergeWith()` 把它们**静默合并**。
  症状："连点两下油漆桶 = 一条撤销记录"、**画笔"画两笔算一步"** ——
  也就是"一次点击 = 一条撤销记录"这句承诺从未成立过。
  修法：编号改为构造函数的**必填参数**，并提供具名工厂 `standalone()`
  （内部取新编号），同时删掉那个能被安静用错的 `currentStrokeId()`。
- `engine/Blend::compositeLayer`：逐像素写回时 `mixR * finalA` —— **二次预乘**。
  `mixR` 本身已经是预乘量（推导见 `docs/实现铁律.md` §12.2），再乘一次 alpha
  会把半透明内容压暗到 `outA` 倍。实测：半透明的纯红（位图 `a=128 r=128`）
  合成后变成 `r=64`。目标不透明时 `outA == 255`，这一步退化成乘 1，
  所以只有**透明画布**（新建文档的默认底色）与**柔边笔迹**才看得出来。
  修法：写回改为 `×255`，并在原处留下推导与实测记录。

两者共同点值得记一笔：**新工具的第一批 bug 往往出现在它踩到的旧代码上。**
`tool_paint_test` 里那两条"看起来在测新工具"的断言（撤销粒度、半透明取色）
实际钉住的是 `DrawCommand` 与 `Blend`。这也说明为什么每加一个工具都要
"从它的入口走一遍完整路径"，而不是只测它自己新写的那几个函数。）

（**实现说明（第二批：直线 / 矩形 / 椭圆）**：计划里是三个独立的工具类，
实际落成**一个 `tools/ShapeTool` 承载三个 Kind**（`Line` / `Rectangle` / `Ellipse`）——
三者的"按下取锚点 → 拖动重算 → 松手压一条命令"骨架逐字相同，只有 `buildMask()`
不同，拆成三个类会复制三遍拖动状态机与撤销收尾。引擎在 `engine/Shape`，
把形状光栅化成 **Grayscale8 覆盖度蒙版**（局部坐标，尺寸 == 包围盒），
合成仍复用画笔那条 `composeStroke()`。自检 `tests/shape_tool_test.cpp`（120 项），
五条关键断言做过植入验证。四处与计划不同：

1. **取 alpha 通道，而不是 `convertToFormat(Grayscale8)`。** ARGB32_Premultiplied
   转 Grayscale8 时 Qt 可能先反预乘，于是抗锯齿边缘的"半透明白"被还原成
   "不透明白" —— 蒙版边缘全是 255，抗锯齿**静默失效**。取 alpha 通道语义唯一明确。
   （这与阶段四"半透明像素查表要先反预乘"是同一类陷阱的两个方向。）
2. **拖动期间写真实像素做预览，但每次重算都从落笔前的整层快照出发。**
   计划只说"拖动预览"。若在上一帧的结果上继续画，重算就是**累加**：手停在
   同一位置多算几次，颜色会越来越深（半透明笔迹尤其明显）。从快照重算保证
   **幂等** —— 自检里有一条断言专门反复重算同一段拖动，要求逐位不变。
3. **重算区域 = 上一帧包围盒 ∪ 本帧包围盒。** 只取本帧会留下上一帧的残影
   （用户把矩形从左上拖到右下，左上那一块没被覆盖回去）。`embedMask()` 负责
   把局部蒙版搬进区域坐标系，其余位置必须显式清 0。
4. **矩形与椭圆共用 `U` 键轮换**（轮换算在 `MainWindow::activateToolByShortcut`，
   与 `M` 键轮换两种选区同构），直线单独绑 `L`。计划里三者的快捷键没定；
   给三个"同一家族"的工具各绑一个键反而更难记。

`tests/text_tool_test.cpp`（158 项，工具 + 参数对象；链 Qt5Widgets），
八条关键断言做过植入验证。六处与计划不同：

1. **★ 计划里说"不需要单独的 engine 文件，直接用 `QPainter::drawText`"——
   这句话是错的，本批回出来的第一件事就是它。** `drawText` 只能"画"，
   而文字工具要处理的是"一段文本 + 字体 + 对齐 + 行距 + 锚点 → 一堆像素"，
   这是一个有**可被测度量**（包围盒、行距、对齐位移）的排版问题。
   若把这段逻辑写在工具里，自检就只能"看图"（铁律第九章），
   而且合成会变成第四份实现。落成 `engine/Text` 后：蒙版复用
   `composeStroke`，排版可以断点断言，"engine 不依赖 QtWidgets"由
   `run_tests.sh` 守着。
2. **浮层归画布、内容归工具。** `QTextEdit` 是 QtWidgets 的类，
   而 `tools/` 不许依赖 `ui/`；`QTextEdit` 又必须挂在画布上才能定位到点击处，
   所以浮层只能由 `CanvasView` 创建。两端靠 `AbstractTool` 上的
   `requestTextEditor` / `setEditingText` / `hasInlineEditor()` 牵线 ——
   **画布不认识 `TextTool`**（写成 `static_cast<TextTool*>` 就把
   `ui → 具体工具` 焊死了）。
3. **锚点在"文本块首行顶部"，不是 Photoshop 的首行基线。**
   基线 = 顶部 + `ascent`，而 `ascent` 是字体属性 —— 用同一个锚点换字体，
   文字块会整体上下跳，跨字体就没法顶部对齐。代价是与 Photoshop 不可直接类比。
4. **不自动换行，只按 `\n` 断行；浮层也用 `NoWrap`。** 自动换行需要一个
   "折行宽度"，而点子文字的锚点语义里没有这个宽度。浮层若不 `NoWrap`，
   会出现"浮层里折行、确定之后不折"——**所见即所得**在这里就是同一件事
   只有一处真相。
5. **`pad = 3` 的包围盒余量。** 抗锯齿会溢出 advance、下划线画在基线以下、
   `floor/ceil` 取整各让一格 —— 三条理由各缺一条都会切掉字形的一点点边，
   而"墨迹四周都不贴蒙版边缘"这条**与字体无关**的不变量正好能钉住它。
6. **`TextOptions::toFont(dpi)` 是磅→像素换算的唯一实现**，`dpi` 取自
   `Document::dpiX()`（**不取屏幕 DPI**）。用 `setPointSize` 的话，
   同一份工程在两台 DPI 设置不同的机器上文字大小不一样。

★ 本批**回出两个真问题**（都不是"写错了算法"，而是"环境前提没兜住"）：
① 计划里那句"不需要 engine 文件"（见上）；
② **截图工具没设 `QT_QPA_FONTDIR`**：Qt 5.15 起不带字体，offscreen 平台
默认找不到字体目录，结果是六段文字里**只有一段**落了墨、
另外五段一个字形都没画出来**却不报任何错**（自证 1/6、撤销栈 1 条）。
两个文本自检从一开始就设了这个变量，所以自检一直全绿 ——
**"自检全绿"证明不了"截图工具也全绿"，两者各自有一套启动环境。**
已把 `qputenv` 补进 `shot_main.cpp`（必须在构造 `QApplication` 之前））

## 7. 关键技术难点与解决方案

### 7.1 大图性能

**问题**：一张 6000x4000 的图有 2400 万像素，每次重绘都全图合成 + 全图缩放会卡。

**方案**：
1. **合成缓存**：只在 `contentChanged(dirtyRect)` 时更新对应区域。
2. **缩放策略**：缩放/平移时不动缓存，只改 `drawImage` 的目标矩形。放大用 `FastTransformation`，缩小用 `SmoothTransformation`。
3. **降采样预览图**：图像超过 2 倍屏幕尺寸时，额外维护一份 1/2 或 1/4 的缩略图用于屏幕呈现，编辑操作仍作用于原图。
4. **分块处理**：滤镜运算按行分块，用 `QtConcurrent::blockingMap` 并行。

### 7.2 快速鼠标移动导致笔画断线

**问题**：`mouseMoveEvent` 采样率有限，快速甩动时两次事件间距可能几十像素，直接连点会画出一串离散圆点。

**方案**：在上一采样点和当前采样点之间做线性插值，步长取 `笔刷半径 / 2`，逐点落笔。更精细的话可以用 Catmull-Rom 样条做平滑，但对照片编辑来说线性插值足够。

```cpp
void BrushTool::strokeLine(const QPoint& from, const QPoint& to) {
    const qreal dist = QLineF(from, to).length();
    const qreal step = qMax(1.0, m_brush.radius() / 2.0);
    const int   steps = qCeil(dist / step);
    for (int i = 1; i <= steps; ++i) {
        const qreal t = qreal(i) / steps;
        const QPoint p(qRound(from.x() + (to.x() - from.x()) * t),
                       qRound(from.y() + (to.y() - from.y()) * t));
        stampBrush(p);
    }
}
```

### 7.3 笔刷硬度/柔边

**问题**：画笔边缘要能柔化，不能是硬邦邦的圆。

**方案**：预生成一个笔刷蒙版（`Grayscale8`），按径向距离计算 alpha：

```
对蒙版内每个像素 (dx, dy)：
    r = sqrt(dx² + dy²) / radius
    if (r >= 1.0)      alpha = 0
    else if (r <= hard) alpha = 255                     // hard = 硬度，0~1
    else               alpha = 255 * (1 - (r - hard) / (1 - hard))
```

硬边时 `hard = 1`，把 `r < 1` 全设为 255 即可。柔边取 `hard = 0.5` 之类。缓存的蒙版在笔刷参数变化时才重建，落笔时直接按位拷贝，很快。

### 7.4 选区边界的蚂蚁线

**问题**：要画出从选区蒙版提取的"流动虚线"边界。

**方案**：
1. 从灰度蒙版提取边缘轮廓。简单做法是用 `QRegion` 从二值化后的蒙版构造，再用 `QPainterPath` 描边。
2. 每 100ms 用一个 `QTimer` 触发重绘，绘制时用交替的 `QPen`（白/黑 `Qt::DashLine`），并让 `dashOffset` 随定时器递增，视觉上就是线条在流动。
3. 为了性能，只在缩放到能看见边界的比例时才绘制蚂蚁线。

### 7.5 撤销栈内存

**问题**：整层快照的 Command 在多次操作后会吃光内存。

**方案**：
- `QUndoStack::setUndoLimit(30)` 限制步数。
- 优先使用脏矩形方案，只有滤镜/变换这类全图操作才用整层快照。
- 整层快照可做 `qCompress` 压缩后存储，像素数据（尤其是大片同色区域）压缩率很高。
- 在 `DrawCommand` 中，如果脏矩形小于图层面积的 1/3，自动走脏矩形路径。

### 7.6 文字工具的中文输入

**问题**：`QPainter::drawText` 直接绘制无法输入中文，也无法编辑。

**方案**：用 `QGraphicsTextItem` 或内嵌一个 `QTextEdit` 浮在画布上，退出编辑时再渲染到图层。这是标准做法：

1. 点击时创建一个 `QTextEdit`（无边框、透明背景），定位到点击处，设置 `setFocus`。
2. 用户输入完成（失焦或按 Esc / Ctrl+Enter），获取渲染后的 `QImage`，写入图层，销毁 `QTextEdit`。
3. 字体、字号、颜色通过工具选项条控制。

### 7.7 MSVC 下的中文编码

**问题**：源码含中文字符串常量时，MSVC 可能按本地代码页解释，导致乱码。这是**中文项目在 MSVC 下最容易踩的第一个坑**。

**方案（三重保险）**：

1. **源文件统一存为 UTF-8 with BOM** —— BOM 能让 MSVC 自动识别编码，不依赖编译开关也正确
2. **`.pro` 里加 `/utf-8`**：
   ```qmake
   msvc {
       QMAKE_CFLAGS   += /utf-8
       QMAKE_CXXFLAGS += /utf-8
   }
   ```
3. **`CMakeLists.txt` 里加**（用 CMake 构建时）：
   ```cmake
   if(MSVC)
       add_compile_options(/utf-8)
   endif()
   ```

**不推荐**的替代方案：每个含中文的文件开头写 `#pragma execution_character_set("utf-8")` —— 要写几百遍，漏一个就等着排查。

**验证方法**：写一个含中文的警告框，Release 构建运行一次，看到的是正确中文而不是"锟斤拷"就对了。

> 另有一条相关约定：**用户可见的字符串一律用 `tr()` 包起来**。即使当前不做多语言，`tr()` 也能让 `lupdate` 工具将来能扫出全部待翻译文本；等真要加语言支持时，不用回头翻遍代码找硬编码字符串。

### 7.7b Qt5 / Qt6 兼容的实操注意事项

**问题**：要求同时兼容 Qt5 与 Qt6，但本机只有 Qt5.15.16，**无法编译验证 Qt6**。这意味着"兼容性靠写代码时的纪律保证"。

**方案**：把版本差异集中在 `src/compat/QtCompat.h` 一个文件里，其余代码全部写"两版通用"的写法。

**最容易踩的五个差异**（写代码时对着检查）：

| 差异 | 错误写法 | 正确写法 |
| --- | --- | --- |
| 鼠标/滚轮坐标 | `e->pos()`、`e->localPos()` | `zl::eventPos(e)` |
| 图像镜像 | `img.mirrored(true, false)` | `zl::mirrorImage(img, true, false)` |
| 文本流编码 | `ts.setCodec("UTF-8")` | `zl::setUtf8(ts)` |
| 遍历容器 | `foreach (auto x, list)` | `for (auto x : list)` |
| 容器类型 | `QVector<T>` | `QList<T>` |

**`QtCompat.h` 的实现思路**（保持极简，只用内联函数，不引入任何运行时开销）：

```cpp
#pragma once
// ── Qt5 / Qt6 兼容层 ──
// 所有版本差异判断只允许出现在本文件。其余代码一律使用这里的包装函数，
// 这样将来升级 Qt 时只需改这一个文件，不必考古整个工程。
#include <QtGlobal>
#include <QPointF>
#include <QImage>
#include <QTextStream>

namespace zl {

// 鼠标事件坐标：Qt6 删除了 localPos()，改用 position()
// 用模板避免为每种事件类型各写一份重载
template <typename EventT>
inline QPointF eventPos(const EventT* e)
{
#if QT_VERSION >= QT_VERSION_CHECK(6, 0, 0)
    return e->position();
#else
    return e->localPos();
#endif
}

template <typename EventT>
inline QPointF eventGlobalPos(const EventT* e)
{
#if QT_VERSION >= QT_VERSION_CHECK(6, 0, 0)
    return e->globalPosition();
#else
    return e->globalPos();
#endif
}

// 图像镜像：Qt6 把 mirrored() 改名为 flipped()，参数语义不变
inline QImage mirrorImage(const QImage& src, bool horizontal, bool vertical)
{
#if QT_VERSION >= QT_VERSION_CHECK(6, 0, 0)
    return src.flipped(horizontal ? Qt::Horizontal : Qt::Orientations())
              .flipped(vertical   ? Qt::Vertical   : Qt::Orientations());
#else
    return src.mirrored(horizontal, vertical);
#endif
}

// 文本流编码：Qt6 用 setEncoding()
inline void setUtf8(QTextStream& ts)
{
#if QT_VERSION >= QT_VERSION_CHECK(6, 0, 0)
    ts.setEncoding(QStringConverter::Utf8);
#else
    ts.setCodec("UTF-8");
#endif
}

} // namespace zl
```

> **注意 `mirrorImage()` 的 Qt6 分支**：Qt6 的 `flipped()` 一次只接受一个方向（`Qt::Orientation`），而 Qt5 的 `mirrored()` 一次接两个 bool。这里用两次 `flipped()` 串联实现等价语义。**这个细节如果写错了，翻转功能会静默地只翻一半** —— 属于典型的不报错但功能错，必须写测试验证。

**验证策略**（本机无 Qt6 的应对）：

1. 写代码时严格遵守 1.1 节的六条硬性规矩
2. 打开 `QT_DEPRECATED_WARNINGS`，它会在 Qt5 下就警告那些"将来会消失"的 API
3. 有条件时在另一台机器或 CI 上用 Qt6 编一次 CMake 工程

### 7.8 曲线插值的过冲问题

**问题**：曲线用普通三次样条（Catmull-Rom）插值时，经过陡峭段会产生过冲 —— 曲线在两个控制点之间反向回勾。

**后果**：映射到图像上表现为暗部细节反转、出现色带与噪点。用户看到的是一条视觉上"正常"的曲线，实际输出却在某些亮度区间出现非预期的反转。

**方案**：使用 **Fritsch–Carlson 单调三次插值**，在标准 Hermite 样条基础上对切线做圆盘约束，保证插值结果不产生过冲。具体公式与实现见 [曲线调整设计.md](曲线调整设计.md) 第 1.5 节。

补充两点实践细节：
- 端点切线必须用**单侧差分**，用中心差分会导致曲线在两端外翘。
- 相邻两段斜率符号相反时（峰或谷），中间点的切线必须置 0。

### 7.9 预乘 alpha 格式下的查表色偏

**问题**：本项目图层位图统一用 `Format_ARGB32_Premultiplied`，存储的是**已乘过 alpha 的分量**。所有基于 LUT 的调整（曲线、亮度、对比度、反色）如果直接对预乘值查表，等于在"已经被 alpha 缩放过"的数值上做映射，半透明区域的 RGB 会被 alpha 二次缩放，产生明显色偏。

**方案**：在 `Lut::applyToRgb()` 内部做格式往返，调用方无感知：

```cpp
QImage work = src.convertToFormat(QImage::Format_ARGB32);   // 非预乘
// ... LUT 运算 ...
return work.convertToFormat(QImage::Format_ARGB32_Premultiplied);
```

两次全图格式转换有开销（4000×3000 约 4~8ms），但对调整类操作**正确性优先**。另外在函数入口加 assert 校验输入格式，避免误用。

> 注意：这条规则**只适用于逐通道独立运算的调整**。混合模式（`Blend.cpp`）的运算本来就定义在预乘空间上，反而应该保持预乘格式，不要做这个转换。

### 7.10 尺寸类撤销的内存爆炸

**问题**：尺寸/旋转/翻转类操作要存**所有图层**的前后两份位图。4 图层 × 4000×3000 × 4 字节 = 192MB，前后两份就是 **384MB/步**。撤销栈 30 步的话，几次尺寸操作就能吃光内存。

**方案**：
1. **`qCompress` 压缩存储**（级别 3 是速度与压缩率的平衡点，对图像数据通常能拿到 80% 以上压缩率）。小于 8MB 的位图不必压缩，解压开销反而更亏。
2. **对尺寸类 Command 单独限步数**（如最多保留最近 3 次），不与画笔操作共用 50 步。或在 `QUndoCommand` 上加 `memoryCost()` 虚函数，按总内存预算（如 512MB）淘汰最老历史。
3. 解压后的 `QImage` **必须 `copy()`** —— `QImage` 的构造函数是浅引用，不拷贝数据，局部变量析构后指针悬空，且不会立刻崩溃。详见 [画布与文件操作设计.md](画布与文件操作设计.md) 第 2.1 节。

### 7.11 任意角度旋转的累积模糊

**问题**：任意角度旋转是重采样操作。如果在一块"已被旋转过的结果"上继续旋转，每次双线性插值都会让图像更糊 —— 转几次就废了。

**方案**：**记录进入对话框时的原图作为基准**，每次预览都从基准重算，而不是在上次预览结果上叠加。松手/确定时也是从基准全尺寸运算一次。

这条规则与曲线预览一致（见 7.9 的思路），但旋转更严重 —— LUT 变换只是查表，误差仅来自格式转换的舍入；旋转涉及真正的插值，误差是指数级累积的。

**另外注意预览与终值的重采样方式要分离**：拖动时用双线性（快），确定时才用用户选的 bicubic 做全尺寸运算。否则每次都跑 180ms 的 bicubic，交互会卡死。

### 7.12 90° 整数倍旋转的容差判断

**问题**：判断旋转角度是否为 90 的整数倍时用 `==` 会误判。`std::fmod(90.0, 90.0)` 可能返回 89.999999 或 0.000001，导致本该走无损路径的旋转退化成插值路径，每次旋转都损失一点清晰度。

**方案**：容差比较。

```cpp
const qreal r = std::fmod(std::abs(angleDeg), 90.0);
const bool isRightAngle = (r < 1e-6) || (90.0 - r < 1e-6);
```

**验证方法**：准备一张所有像素值各不相同的图，旋转 90° 四次，结果应与原图逐像素完全相同。通不过就说明走了插值路径。

### 7.12b 自实现重采样的两个经典错误

**错误一：做二维 4×4 卷积。** 对每个输出像素采样 16 个源像素，4000×3000 → 2000×1500 就是 4800 万次采样，慢到不可用。

**正解**：**分离成两次一维卷积** —— 先水平缩放宽、再垂直缩放高。复杂度从 `O(W1·H1·16)` 降到 `O(W0·H1·4 + W1·H1·4)`。再配合权重预计算（缩放比例固定，每组权重可复用），避免在每个像素上重算三次多项式。

**错误二：忘记归一化权重。** 三次卷积核在非整数偏移处的权重求和不等于 1，不归一化会导致图像整体变亮或变暗 —— 而且这个偏差随缩放比例变化，很难通过观察发现是"亮度错了"。

**正解**：每个输出位置的 4 个权重算出后立刻除以其和：

```cpp
float sum = w[0] + w[1] + w[2] + w[3];
if (qAbs(sum) > 1e-6f)
    for (int j = 0; j < 4; ++j) w[j] /= sum;
```

**验证方法**：把一张纯色图（比如 RGB 128,128,128）放大和缩小，输出应仍是完全相同的纯色。有偏差就说明归一化漏了。

### 7.12c 画布智能适配的内容包围盒计算

**问题**：画布缩小时要"智能适配"（自动平移内容避免裁切），前提是知道**内容实际在哪里** —— 需要求所有可见图层非透明像素的并集包围盒。

**性能**：逐像素扫描 4000×3000 单线程约 20ms。不能每次重绘都算。

**方案**：
1. 用 `QImage::createAlphaMask()` 再由 `QRegion::boundingRect()` 求界 —— Qt 内部有优化，通常比手写循环快。
2. **在 `Document` 里缓存结果**，只有位图内容变化的脏矩形触及到当前包围盒边缘时才失效重算。大多数绘制操作（画面中部）不会改变包围盒，缓存命中率很高。
3. 画布智能适配是**对话框里的单次操作**，不是每帧调用，20ms 完全可以接受。缓存主要是为了对话框预览的实时响应。

### 7.13 选区复制时的内容泄漏

**问题**：直接 `layer->image().copy(selection.bounds())` 会把选区**包围盒内**的所有像素都复制进来，包括选区外的部分。粘贴后这些内容就"漏"出来了 —— 做了椭圆选区却粘出一个矩形。

**方案**：复制时**把选区蒙版值乘进 alpha 通道**：

```cpp
const int a = qAlpha(px[x]);
px[x] = qRgba(qRed(px[x]), qGreen(px[x]), qBlue(px[x]),
              a * mask[x] / 255);          // 蒙版值参与 alpha
```

选区外变成透明，粘贴时自然不显示。羽化选区的边缘会得到 0~255 之间的 alpha，粘贴后形成柔边过渡 —— 这是用灰度蒙版而非 `QRegion` 的直接收益。

**注意顺序**：必须在预乘格式转换**之前**做（在非预乘的 `ARGB32` 上操作），否则 alpha 值与 RGB 分量的对应关系会被破坏。

### 8.1 qmake 工程文件（`.pro`）

> **`.pro` 全文见仓库根目录的 `ZlPhotoEdit.pro`。** 本节原先抄了一份副本，而且它还停留在设计期（列了 `NewDocumentDialog.cpp` / `NavigatorPanel.cpp` 等从未落地的文件），已删 —— 只保留下面的要点。

#### `.pro` 的 Qt5/Qt6 兼容要点

`.pro` 本身两版通用（qmake 的模块名 `core gui widgets` 在 Qt6 中不变），只有三处需要留意：

| 项 | 说明 |
| --- | --- |
| `QT += svg concurrent printsupport` | Qt6 中打印模块名仍是 `printsupport`，无需改名；若某模块在某个 Qt 中不存在，qmake 会直接报错，便于早发现 |
| `CONFIG += c++17` | Qt6 **强制要求 C++17**，Qt5 也支持，因此统一写 C++17 两版都安全 |
| `QT_DEPRECATED_WARNINGS` | 两版都支持，能提前暴露将来会被删除的 API 用法 —— **这是 Qt6 迁移最有价值的开关，务必保留** |

### 8.1b CMake 工程文件（`CMakeLists.txt`）

同一份 `CMakeLists.txt` 需同时支持 Qt5 与 Qt6。核心技巧是用 `find_package(QT NAMES Qt6 Qt5)` 先探测版本，再拿 `QT_VERSION_MAJOR` 拼出具体目标名：

> **`CMakeLists.txt` 全文见仓库根目录。** 本节原先抄了一份副本（会随仓库漂移），已删 —— 只保留下面的要点。

> **`find_package(QT NAMES Qt6 Qt5 ...)` 这两行的写法不能省** —— 只写 `find_package(Qt5 ...)` 就锁死在 Qt5 了。这套写法是 Qt 官方推荐的跨版本模板，Qt Creator 新建工程时生成的也是它。

**CMake 相比 `.pro` 的三个差异要知道**：

1. **源文件可以用 `GLOB_RECURSE ... CONFIGURE_DEPENDS`** 通配 —— 但注意 `.pro` 里我们仍然逐个列举，原因是 qmake 的通配**不会自动感知新增文件**，而 CMake 加了 `CONFIGURE_DEPENDS` 可以。两边的取舍不同，不矛盾。
2. **`AUTOMOC` / `AUTORCC` / `AUTOUIC` 必须显式打开** —— 这对应 qmake 里自动的 moc 处理。漏了会报"undefined reference to vtable"。
3. **`/utf-8` 要通过 `add_compile_options` 传** —— `.pro` 里是 `QMAKE_CXXFLAGS`，CMake 里没有这个变量。

### 8.3 编码约定（源文件必须遵守）

用户明确要求：**所有 `.h` / `.cpp` 使用 UTF-8 编码**，且**重要逻辑处添加中文注释**。具体落地：

| 要求 | 做法 |
| --- | --- |
| 编码 | 全部源文件存为 **UTF-8 with BOM**（带 BOM 能让 MSVC 自动识别，不依赖 `/utf-8` 开关也正确；但 `/utf-8` 仍必须留着 —— 双保险） |
| 换行符 | 统一 **LF**（整个仓库都是 LF、`core.autocrlf=false`）。★ 程序化编辑会把整文件翻成 CRLF → 改完必须复核 `tr -cd '\r' < f | wc -c` |
| 中文注释 | 涉及算法、边界情况、性能取舍、易错点的地方**必须**写注释。注释解释"**为什么**"而不是"做了什么" —— 例如"这里必须 copy()，否则是浅引用，源图释放后画面会错乱" |
| 中文注释禁止 | 不要把英文注释机械翻译成中文。代码本身能看懂的（如 `i++`）不需要注释 |
| 字面量 | 用户可见的字符串一律 `tr("中文")` 包起来，为将来多语言留口；不需要翻译的技术字符串用 `QStringLiteral()` |
| 禁止 | 不写 GBK / GB2312 编码的文件 —— 一旦混入，MSVC 会按 C4819 警告处理，中文全乱 |

**编辑器设置建议**（避免手工操作出错）：

- Qt Creator：`工具` → `选项` → `文本编辑器` → `行为` → `文件编码` 设为 **UTF-8**，勾选 **"如果编码是 UTF-8，则添加 BOM"**
- VS Code：`"files.encoding": "utf8bom"`，`"files.eol": "\r\n"`

### 8.4 Qt Creator 配置

1. 打开 Qt Creator 8
2. `工具` → `选项` → `Kits`，确认自动检测到了 `Desktop Qt 5.15.16 MSVC2022 64bit`
3. 打开 `ZlPhotoEdit.pro`，选择该 Kit，直接构建运行
4. 若要用 CMake：`文件` → `打开文件或项目` → 选 `CMakeLists.txt`，Kit 选同上，Qt Creator 会自动传 `CMAKE_PREFIX_PATH`

**三条并行支线的说明**：选区、滤镜、多图层这三块之间没有强依赖，在画笔跑通之后可以按任意顺序推进，甚至并行开发。唯一要注意的是多图层做完后，所有涉及像素操作的 Command 都要把"目标图层"作为参数（而不是默认第一个图层），所以在阶段二写 `DrawCommand` 时就预留 `layerIndex` 字段，后面就不用返工。

**中间支线的内部顺序**：先做 `Lut`（通用流水线），再做曲线，最后才是其它调整和滤镜 —— 因为亮度、对比度、反色、阈值这些都能复用 `Lut::applyToRgb()`，先把这条流水线立起来可以少写很多重复代码。曲线的完整设计见 [曲线调整设计.md](曲线调整设计.md)。

**尺寸与旋转的位置**：放在多图层之后做更省事 —— `GeometryChangeCommand` 要遍历所有图层存快照，单图层时写完到多图层还得改。剪贴板则可以提前到阶段三（选区刚可用时），它只需要选区和单图层。详见 [画布与文件操作设计.md](画布与文件操作设计.md)。

## 10. 明确不做的事

为了控制复杂度，以下功能不纳入标准版范围：

**图像处理类**：

- 图层组（嵌套图层）
- 图层蒙版（每图层一个附加通道）
- 智能对象 / 非破坏性编辑
- 调整图层
- 通道面板
- 路径 / 钢笔工具 / 矢量形状图层
- 色彩管理（ICC Profile，仅识别并保留标记）
- 液化 / 内容识别填充 / 神经网络滤镜

**工具与工作流类**：

- 套索 / 快速选择（选区 = 矩形 + 椭圆 + **魔术棒**）
- 渐变工具
- 仿制图章 / 修复画笔
- 动作录制 / 批处理
- 自定义画笔 / 画笔预设管理
- 图层样式（描边/阴影/发光）
- 变形 / 透视变换 / 自由变换（只做旋转/翻转/缩放）
- 3D / 视频 / 动画帧

**系统与格式类**：

- PSD 格式读写
- 插件系统
- 色彩管理（ICC）
- 脚本引擎
- 触摸板手势（可后续加）

**协作类**：

- 云端同步
- 多人协作

这些都可以在架构稳定后作为增量扩展。当初判断**图层蒙版**、**色阶**、**自定义工程格式**、**多文档标签页**是最有价值的四个扩展方向 —— 事后看**判对了三件、判错了一件**：

- ✅ **色阶**、✅ **多文档标签页**：都已落地。多标签页的架构基础（`DocumentManager` + 全体面板的 `setDocument()`）当初就预留了，所以阶段八只花了"换中央控件 + 一个 `activateTab()`"的力气（见 §3.8.3）。
- ⛔ **自定义工程格式 `.zlpe`**：**已定案不做**。判断错的地方在于它并不是"增量成本低"，而是"一旦有了就得背上一份格式兼容责任"，而本项目只做导出扁平图，用不上"图层可续编"。
- **图层蒙版**：仍是最有价值的进阶方向，尚未做。
