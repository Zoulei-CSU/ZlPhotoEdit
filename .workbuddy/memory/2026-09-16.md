**需求**：基于 Qt 5 设计一个类似 Photoshop 的图片编辑器，纯 Qt 实现，不依赖第三方库。

- qmake 可用；cmake / ninja **未安装**
- 可用模块：Core / Gui / Widgets / Svg / PrintSupport / Concurrent 全部就绪
- 图像格式插件齐全：bmp gif ico jpeg png svg tga tiff wbmp webp

**用户选型决策**：
1. 图层架构 → **完整图层栈 + 混合模式**（不做轻量单层方案）
2. 功能范围 → **标准版**（基础版 + 裁剪/旋转/翻转、画笔大小硬度不透明度、油漆桶、直线/矩形/椭圆/文字、色相饱和度/锐化/模糊/去色/反色、图层基础）
3. 交付形态 → **只要规划文档**，代码用户自己写

**产出**：
- `docs/架构规划.md` — 完整架构设计（约 900 行）
- `README.md` — 项目说明与构建指引

**架构核心约定**（后续写代码必须遵守）：
- 分层单向依赖：`ui → tools → commands → core → engine`，engine 只依赖 QtGui
- `Document` 是像素数据唯一来源，`CanvasView` 每次从 Document 取合成结果（带脏矩形缓存）
- **工具不改数据，只产生 QUndoCommand** — 撤销重做零成本接入
- 图层位图统一 `Format_ARGB32_Premultiplied`
- 选区用 `Format_Grayscale8` 蒙版而非 QRegion（为了支持羽化和魔棒）
- `DrawCommand` 从一开始就预留 `layerIndex` 字段，避免多图层阶段返工
- 撤销策略分两类：画笔走**脏矩形**，滤镜/变换走**整层快照**
- `.pro` 里必须加 `msvc { QMAKE_CXXFLAGS += /utf-8 }`，否则中文字符串乱码

**开发阶段规划**：骨架跑通 → 画笔与撤销 → 选区系统 → 图像调整与滤镜 → 多图层 → 绘制工具补全 → 打磨打包

**未纳入范围**（用户未要求）：图层组、图层蒙版、调整图层、通道面板、路径/钢笔、PSD 读写、色彩管理、插件系统。

## 补充：曲线调整功能设计

用户追问"设计曲线调整了吗？这个我经常用" —— **初版规划确实遗漏了**，只在阶段四写了"曲线调整（可选，进阶）"，调整功能表里也只有亮度/对比度/色相/饱和度。

**已做的修正**：
1. 新建 `docs/曲线调整设计.md` —— 曲线功能专项设计（约 500 行）
2. 主规划文档四处修订：
   - `adjust.cpp` 表格补充曲线一行，拆出 `curves.cpp / lut.cpp` 小节
   - 阶段四：曲线从"可选进阶"提升为**必做项**，并补充验收标准
   - 目录结构：新增 `engine/Curves.*`、`engine/Lut.*`、`ui/Histogram.*`、`ui/CurveEditor.*`、`ui/CurvesDialog.*`
   - `.pro` 示例同步更新
   - 第 7 章新增 `7.8 曲线插值的过冲问题`、`7.9 预乘 alpha 格式下的查表色偏`
   - 第 9 章依赖图标注曲线在中间支线的位置

**曲线设计的关键决策**：
- **插值用 Fritsch–Carlson 单调三次样条**，不用 Catmull-Rom。后者在陡峭段产生过冲（回勾），映射到图像上就是暗部色带和噪点 —— 这是曲线实现的经典坑。
- **曲线不参与逐像素数学运算**，先烘焙成 256 项 LUT 再查表。烘焙一次微秒级。
- **通道是叠乘关系**：`final = curveBlue(curveGreen(curveRed(curveRGB(v))))`。组装时用 `composeLut` 串成三通道 LUT；若三通道结果相同走单 LUT 快路径。
- **曲线控件必须复用 `bakeLut` 来绘制**，保证"屏幕上看到的曲线"和"实际作用于像素的映射"完全一致。
- **两级预览**：拖动时在 ≤1024 的降采样副本上运算（6~10ms，单线程够 60fps），松手/确定时才全尺寸运算 + 并行化。预览必须**始终在原图上重算**，不能在上次预览结果上叠加（格式转换的舍入误差会累积导致色偏）。
- **背景直方图用对数缩放**，否则照片直方图集中时柱形全被压平。只在打开对话框时算一次。
- 曲线复用 `ImageAdjustCommand`（整层快照类），**不需要新增 Command 类**。
- 建议先给 `bakeLut()` 写单元测试再做界面 —— 插值边界情况多，靠界面调试很低效。

**新发现的通用陷阱（已写入主文档 7.9）**：
`ARGB32_Premultiplied` 存储已乘 alpha 的分量，所有 LUT 类调整必须先在 `Lut::applyToRgb()` 内部转 `Format_ARGB32` 运算、结束后转回。**但混合模式（Blend.cpp）例外** —— 它的运算本就定义在预乘空间，应保持预乘格式不转换。

**用户偏好补充**：曲线是用户高频使用的功能，调整类功能的优先级排序不能想当然。

## 补充：画布与文件操作设计

用户追问"尺寸、画布的调整，旋转，复制选区、粘贴选区，另存为，这些都是设计了的吧？"

| 复制/粘贴选区 | 完全没有 | 全缺 |

**已做的修正**：
1. 新建 `docs/画布与文件操作设计.md`（约 700 行）
2. 主规划文档多处修订：Document 接口补全、transform.cpp 区分图层级/图像级、阶段一补文件生命周期、阶段三补剪贴板、阶段四补尺寸与旋转、Command 表加 `GeometryChangeCommand`、目录结构与 `.pro` 同步、菜单栏补全、依赖图更新
3. 第 7 章新增四个难点：7.10 尺寸类撤销内存爆炸、7.11 任意角度旋转累积模糊、7.12 90° 容差判断、7.13 选区复制内容泄漏

**关键设计决策**：
- **图像大小 vs 画布大小**：前者缩放像素，后者像素不动只改容器。两者都要作用于**所有图层 + 选区**。
- **`applyGeometryChange()` 统一入口**：缩放/画布/旋转全部归结为"一个 QTransform + 新尺寸"，边界情况只写一遍。裁剪也复用它。
- **`GeometryChangeCommand`** 取代原 `ResizeCommand` / `CropCommand`（它们本质相同：把所有图层换成另一组位图）。
- **尺寸类 Command 最耗内存**：4 图层 × 4000×3000 = 384MB/步。必须 `qCompress`（级别 3）+ 单独限步数。解压后 `QImage` **必须 `copy()`**（浅引用陷阱，不崩溃但悬空）。
- **90° 整数倍必须走无损路径**，判断用容差 `fmod` 不要用 `==`（可能返回 89.999999）。验证法：旋转 90° 四次应与原图逐像素相同。
- **任意角度旋转必须从基准重算**，不能在预览结果上叠加（旋转的插值误差比 LUT 舍入严重得多，转几次图就糊了）。
- **选区复制要把蒙版值乘进 alpha**，否则选区外内容会泄漏（椭圆选区粘出一个矩形）。必须在预乘转换**之前**做。
- **剪贴板用自定义 MIME `application/x-zlphotoedit-layer`**（存 pixels + mask + sourceBounds）+ 同时提供 `image/png` 供外部程序。只提供 PNG 不提供 BMP（BMP 未压缩，48MB 进剪贴板会拖慢系统）。
- **粘贴位置**：同文档内原位粘贴（靠 sourceBounds），跨文档居中，超出画布自动扩画布。
- **另存为用 `QImageWriter`** 而非 `QImage::save()`（前者能设质量/压缩参数）。需要自定义参数控件时必须 `DontUseNativeDialog`（原生对话框不支持塞控件）。`setDefaultSuffix()` 必设否则无法从路径推断格式。
- **`closeEvent` 里 `save()` 返回 false 时必须 `e->ignore()`**，否则用户在另存为对话框点取消、窗口却关了，改动丢失。

**发现的类名不一致（已修正）**：原文档目录结构写 `ImageSizeDialog`，阶段四写 `QSizeDialog` → 统一为 `ImageSizeDialog`，画布大小单独做 `CanvasSizeDialog`，两者共用 `SizeChangeDialogBase`。

**待用户确认的产品决策**（已列在文档第 8 节）：
1. 是否做自定义工程格式 `.zlpe`（不做 PSD 读写的话，"保存"只能导出扁平图，图层信息丢失）
2. `Ctrl+V` 默认粘贴为新图层还是当前图层（建议前者）
3. 画布缩小时直接丢弃还是智能适配（建议丢弃 + 预览标出被裁区域）
4. 是否做 bicubic 重采样（Qt 只提供邻近和双线性，bicubic 需自己写约 80 行）

### 8.4 自写 bicubic
- **Keys 三次卷积，a = -0.5 默认**（a = -0.75 作为"更锐"选项）
- **必须分离成两次一维卷积**，绝不做二维 4×4（复杂度从 `O(W1·H1·16)` 降到 `O(W0·H1·4 + W1·H1·4)`）

- 边缘采样用 clamp（不是视为透明），避免边缘暗边
- 在**预乘 alpha 空间**上做加权求和是**正确**的（与 LUT 查表的情况不同）
- 新建 `engine/Resample.h / Resample.cpp`，`Resample::Method` 枚举（Nearest/Bilinear/Bicubic/Lanczos）
- 性能：4000×3000 → 2000×1500 约 180ms，需等待光标或后台线程
- **预览用双线性，确定时才用 bicubic**（否则拖动尺寸数字时每次 180ms，交互卡死）
- `applyGeometryChange()` 的 `interpolate` 参数语义升级：从 `bool` 变为 `Resample::Method`

### ★ 最重要的教训：`/utf-8` 缺失导致的错误海啸 ★

CMake 全量构建时爆出上百条错误，报错位置横跨 `qvariant.h`、`qimagereader.h`
等 **Qt 自己的头文件**，以及 `ImageMeta.h`、`DocumentManager.cpp`。
最初误判为「源码花括号不平衡」或「文件编码坏了」，逐一排查后全部否定
（`iconv` 验证 67 个文件全为合法 UTF-8）。

**真正原因**：`CMakeLists.txt` 里 `add_compile_options(/utf-8)` 写在
`add_executable()` **之后** —— `add_compile_options` 只对「它之后定义的
target」生效，所以 `/utf-8` 根本没进编译命令。

**为什么会报出那种错**：MSVC 默认按本地代码页（GBK）解释源文件。UTF-8 的
中文字符占 3 字节，第 3 字节可能恰好是 `0x5C`（反斜杠）—— 它把行尾的引号
或换行「吃掉」，于是注释行之后的所有代码被当成字符串的一部分。编译器随后
报出的位置全是**错误现场的邻居**，不是病灶：
- `C2001: 常量中有换行符`
- `C3646: 未知重写说明符`
- `C2270: "memoryUsage": 非成员函数上不允许修饰符`
- `C2511: "zl::Layer *zl::LayerList::layer(int)": 没有找到重载的成员函数`
- 甚至 `qvariant.h(243): error C2535: "QVariant::QVariant(int)": 已经定义`

这些报错的位置和内容都毫无关联性，正是「一个字符把大段代码吞进字符串」的
典型特征。**修复方式**：改用
`target_compile_options(ZlPhotoEdit PRIVATE /utf-8)`，与声明顺序无关。

> 附带发现：`LayerList.h` 报 `m_layers: 未声明的标识符`、
> `SelectionCommand.cpp` 报 `memoryUsage: 非成员函数上不允许修饰符` —— 
> 这两个此前被当作独立疑难问题排查了很久，**其实都是这个单一原因**。
> 教训：当一个全量构建里出现大量「位置分散、原因各异」的报错时，
> 先怀疑**编译选项 / 编码**这类全局因素，而不是逐个去看每个报错。

### CMake 构建的其他必要修正

1. `build_env.sh` 增加 `cmake` / `ninja` 的 PATH —— 它们**不单独安装**，
   随 VS 2022 的「使用 C++ 的桌面开发」工作负载发布，位于
   `<VS>\Common7\IDE\CommonExtensions\Microsoft\CMake\`。
   漏加的症状是 `cmake: command not found`。
2. `.gitignore` 补 `build_cmake/` 与 `build_*/`。

### 代码质量修复

- **`MainWindowActions.cpp` 的 C4573 警告（真实隐患）**：
  `[list, rebuildList](Document *doc)` 这个 lambda 没捕获 `this`，但函数体里
  写的是不加限定的 `connect(...)` / `disconnect(...)`。编译器沿外层
  `MainWindow` 成员函数作用域去找，试图用 `this` 调用 —— 报
  「要求编译器捕获 this，但当前默认捕获模式不允许」。
  **修复**：写成 `QObject::connect` / `QObject::disconnect`（静态调用），
  语义更准确（这条连接只属于 list 与 doc，与 this 无关）。
- **`QtCompat.h` 的 C4996 警告**：Qt5 分支调用 `QWheelEvent::pos()` /
  `globalPos()` 是刻意的（Qt6 才用 `position()`）。用
  `#pragma warning(push/pop)` 局部屏蔽，避免刷出十几条同样的警告
  ——**警告疲劳比没有警告更危险**。

### ★ 关键经验：qmake 增量构建会掩盖错误 ★

`nmake release` 只重编改动过的文件。若某个 `.cpp` 的 `.obj` 是之前就已存在
的，它里面的错误不会被发现 —— 直到某次全量重建才突然冒出来。本项目实际
踩到：一批 Qt5 `QList` 接口问题与头文件包含问题在 qmake 下潜伏了很久，
换成 CMake `--clean-first` 后一次性全部暴露。

**结论（已写入 README）**：日常开发用 qmake（增量快、与 Qt Creator 无缝）；
**提交前必须用 CMake 做一次 `--clean-first` 全量构建**。两者都能编过才算
真正编过。
