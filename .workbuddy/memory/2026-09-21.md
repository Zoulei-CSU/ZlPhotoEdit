## ★ 两个真 bug —— 根因是同一个 ★

1. **生产**：`RulerWidget::canvasOrigin()` 写成 `m_view->mapTo(this, QPoint(0,0))`
2. **测试**：同一形态又犯一次 —— `cv2->mapTo(hr, QPoint(0,0))`（`hr` 不是 `cv2` 的祖先）

`QWidget::mapTo(parent, pos)` 是**沿父链往上找 parent**，所以 `parent` 必须是自己的
**祖先**。而**标尺与画布是兄弟**（都挂在中央网格宿主下）—— 父链走到头变成 `nullptr`，
紧接着 `w->mapToParent(p)` 解引用空指针 → **段错误**。

★ 症状极具误导性：`MainWindow` 构造 → `resize` → `show` **全部正常**，
崩在 `show()` 之后**第一次重绘**里。而构造、装配、菜单、图标、全部数学断言都是绿的。

**规律（已写进铁律第十八章）**：凡是要在两个**兄弟控件**之间换算坐标，
一律 `mapFromGlobal(b->mapToGlobal(p))`，别用 `mapTo` / `mapFrom`。
★ 把标尺从"浮在画布上"改成"网格里的一格"，会让**每一次**标尺⇄画布的换算
从"父子"变成"兄弟"——这类重构之后所有跨控件坐标换算都要重过一遍。

## ★ 关键实测结论（不是猜的）：qico 插件会**静默缩到 256**

一次性探针证实：`QImageWriter(path,"ico").write(300×300)` → **返回 true**，
写出的是 **256×256**（270398 字节 ＝ 256 尺寸的 BMP 条目），
`errorString()` 还是 `"Unknown error"`。所以：
- 512 上限**没有地方可拦**；
- 用户存 512 会拿到 256，**零提示**；
- 且 `qico.dll` 是 `imageformats` 插件，要单独部署。
→ 三条理由都写进了 `IcoWriter.h` 与 README。★ 写注释前先实测，不要"我猜 Qt 会…"。

## 设计要点

1. **512 是产品定案**：`>` 不是 `>=`（512×512 恰好放行）；超限**拒绝**而非默默缩小。
2. **两种条目**：≤256 走 BMP（40 字节头 + 自下而上 32bpp BGRA + 1bpp AND 掩码）；
   257~512 走 **PNG 条目** —— 目录项宽高**各只有 1 字节**、`0` 表示 256，
   结构上就装不下 256 以上。PNG 条目宽高写 0，真尺寸以 PNG 头为准。
3. **三个隐形坑**：`biHeight` 必须 **2×高**；AND 掩码**置 1=全透明**、最高位在左、
   半透明**不置位**；预乘必须还原成非预乘（转换放编码器内部，不散给调用方）。
   掩码**自己按位拼**，不用 `Format_Mono`+`createAlphaMask()`+`invertPixels()`（语义跨版本不一）。
4. **分流点只有 `writeImage()` 一处** → Ctrl+S 与另存为自动都覆盖。
5. **文案由引擎层出**（`rejectionMessage()`），界面层不重复写 "512"（两份真相）。
6. **最强的整体不变量**：`dwImageOffset + dwBytesInRes == 文件总长`（一次覆盖"记录长度⇄实际字节数"）。

## ⑥ 大图编辑卡顿：性能定位 + 方案评估（★ 本轮**未改 `src/` 一行**）

**用户诉求**：编辑大图时画笔/橡皮/鼠标绘制"非常非常卡"；问能否优化，若不能，
能否"编辑时只编辑缩略图、保存时再按编辑重放原图"。

**定位（实测，非猜测）**：每帧成本 = **整画布全图层重新合成**。
链路：`BrushTool::mouseMove → applyRegion → Document::markDirty()`（**整画布失效**）
`→ paintEvent → Document::composite() → blend::compositeLayers()`。
画笔本身是全项目最干净的实现（只算/只写脏矩形），**瓶颈在于它把"我只动了这一小块"丢了**。

**探针**：`.buildlog/probe_perf.cpp`（一次性，不入库）只链 `engine/Blend.cpp`，cl 直编。
测试机 **AMD Ryzen 7 4800H / 8 核 16 线程 / MSVC /O2**。

| 画布 | 层 | 全画布合成 | 只算笔尖 64px | 加速比 |
| --- | --- | --- | --- | --- |
| 1920×1080 | 3 | 108 ms | 0.25 ms | 441× |
| 3840×2160 | 3 | **431 ms** | 0.25 ms | **1739×** |
| 6000×4000 | 3 | **1256 ms** | 0.25 ms | **5107×** |
| 8000×6000 | 5 | **4134 ms** | 0.41 ms | **10011×** |

★ 另一组关键实测：**Multiply 与 Normal 耗时相同（0.99×）** → 时间**不在混合公式**，
而在公共的"还原非预乘"**除法**（`Blend.cpp:361/368`，每像素 2 次 `divsd`）。
→ 所以"换更省的模式"没有用，但"倒数查表"能拿 2~4×。
★ `base.copy()` 只占单层成本 **7%** → 省 memcpy 收益很小，别往那儿使劲。

**★ 一个必须记住的坑**：`Document.h:101-103` 的注释写"一次合成 10~30ms 已经够用"，
据此否决过脏矩形方案。实测是 **146~4134 ms**，慢了 **5~140 倍** ——
设计前提按 2000×1500 估的，而今天是 24MP 相机照片（6000×4000）。**注释待修正。**

**★ 对"编辑缩略图 + 保存时重放"的结论：不采用。**
决定性理由：瓶颈 **99% 在合成、0.7% 在呈现**（4K：431ms vs 2.9ms）——
降低呈现分辨率买不到那 431ms。加上质量损失（1px 线条糊掉）、所见非所得、
`DrawCommand` 存的是**像素补丁**而非笔触参数（重放前提不成立）。
→ **可提炼判据（应写进铁律）**：
> **全局参数化操作 → 可降采样预览；局部像素操作 → 必须全分辨率，但只需重算改动区域。**
（滤镜/调整/旋转对话框**已经**在用降采样预览，那里是对的。）

**推荐方案 A（脏矩形增量合成）正确性基石**：
本项目 16 种混合模式**全是逐像素（pointwise）**、无任何空间邻域运算
→ **某矩形内独立合成 == 全图合成结果的对应子区域（逐位相等）**。
改动面三层：engine 加 `compositeLayersRegion()`（**必须复用同一内核**）、
core 加 `markDirtyRegion()` + `m_fullInvalidate`（**无参 `markDirty()` 永久保留作兜底**）、
ui 的 `update()` 带矩形 + 把"选区轮廓失效"从"像素脏"里拆出来。
大坑：**移动图层要脏"上帧 ∪ 本帧"**（只脏本帧 → 拖动期留残影，松手即消失，极难复现）。

`update()` 不带矩形；蚂蚁线 120ms 定时器在拖动期也触发。

## ⑦ A / B 推进次序评估（用户问"一起做还是先后做，哪个投入产出比最大"）

**结论：先后做，A 先。"一起做"在任何次序下都不成立。** 已写入 `docs/性能优化评估.md` **§11**。

四条理由（以后同类"要不要并行做"的问题可直接复用这套判据）：
1. **收益不叠加，而是覆盖两个不相交的场景**：A 打"每帧"、B 打"一次性全图"；
   A 落地后 B 在热路径上的价值**归零**。预期不是 `1739×2.6`，而是"A 管热路径、B 管冷路径"。
2. **只有 A 跨"可用性阈值"**：A → `2.3 → 60 fps`（可用/不可用 的分界）；
   B 单独做 → `2.3 → 5~8 fps`（**依然是卡**，只是从"幻灯片"变"很卡"）。
3. **归因**：A 的症状是"区域残留旧内容"、B 的症状是"边界像素 ±1"，本来可以区分；
   混在一批上线，看到任何像素不符都要同时查两条路径 → 定位成本**相乘**而非相加。
4. **口径污染**：A 的唯一正确性基石是 `region vs 全图` **逐位相等（容差必须为 0）**；
   若先立"像素断言容差 ±1"的全局口径，这条基石将来极可能被顺手放宽 →
   "脏矩形算小了"这类 bug 就从断言下面漏过去。

★ **本轮新发现：B 的作用面比初稿宽。** 不止 `Blend.cpp:361/368`，还有
`:351`/`:367` 的 `/255.0` 与 `:361~363`/`:368~370`，**以及 `Adjust.cpp:386~389`**
（调整类走的是同构代码 `int r = int(qRed(px) / (qAlpha(px)/255.0))`）
→ **作用面 = 2 文件 7 处除法**。好处：B 顺带提速"应用调整"；
代价：验证面扩大到 `adjust_test.cpp`（`:161`、`:233~235`、`:263~266` 那批
"恒等表下逐位不变 / 半透明像素往返不变"断言）——
**B 要放宽容差的正是"专门用来抓细微 alpha 错误"的那批断言。**

★ **B 有三个形态，不是一个高风险形态**：
| 形态 | 表 | 逐位相同 | 备注 |
| --- | --- | --- | --- |
| B | `kInv[256]` / 2KB | ❌ 可能 ±1 | 最省缓存，但要改断言口径 |
| **B′** | 整表 `T[a][v]=(qreal)v/a` / **512KB** | ✅ | 存的就是那次正确舍入的除法结果 → **零口径变更**；吃满 Zen2 每核 512KB L2，**是否比 `divsd` 快须先实测** |
| **B″** | 只表化常数除 255 / 2KB | ✅ | 覆盖 `sa`/`da`/`Adjust.cpp:386`，**不覆盖 `R/A`**；收益取决于"alpha==255 占比"——**未测，不可先承诺收益** |

**建议次序**：①A 画笔+橡皮（只跑 `perf`/`brush`）→ ②实测选区轮廓重建成本 → ③A 形状/移动/油漆桶
→ **④阶段收口：此处提醒用户跑一次全量** → ⑤B 侦察（grep 清查全部像素精确断言）
→ ⑥B/B′/B″ 选型 → ⑦可选 C 呈现缓存 → ⑧未来瓦片化。

**唯一会改主意的条件**：若用户实际痛点是"打开 24MP 照片等 1.2 秒"或"应用一次色阶卡 1.5 秒以上"，
则把 **B 提到 A 之前** —— 但**仍然不是"一起做"**。

### 九、画笔 / 橡皮的轮廓圆不跟随（用户报的 bug，已修）

**症状**：用画笔或橡皮**按住**鼠标在画布上拖动时，表示落笔范围的小圆圈
**停在落笔点不动**；**不按住**时才跟着鼠标走。

**根因**：圆心画在 `BrushTool::m_hoverWidgetPos` 上，而这个缓存只在这两处更新：
`beginStroke()`（落笔瞬间）、`hoverMove()`（不按键的悬停）。
而画布是**按"此刻有没有按键"分派**的（`CanvasView::mouseMoveEvent`：
无键 → `hoverMove`，有键 → `mouseMove`）→「按住拖动」这条路**一次都到不了
`hoverMove`**，缓存自然永远停在落笔点。

**修法**（`tools/BrushTool.cpp`）：
1. `mouseMove()` 里补上悬停缓存更新，且放在**所有提前 return 之前**
   （图层被锁、没落成笔时 `m_layerIndex` 还是 -1，圈照样得跟）；
2. 该函数末尾**无条件** `return ToolResult::repaint()` —— 本帧没落笔
   （`dirty` 为空）时也必须请求重绘，否则笔刷拖出画布再拖回来，圈卡在边缘；
3. `paintScreenOverlay()` 去掉 `if (!view) return;`（`Q_UNUSED(view)`）——
   它是**死判断**（view 一个方法都不调用，唯一调用者传的是 `this`），
   代价却是自检里画不出这个圆。

★ 这是典型的**"事件分派组合"类缺陷**：不在像素里、不在撤销栈里，
所有像素/命令断言照样全绿，只在"按住 + 移动"这一种组合下才现形。
