### ★ 三个真实缺陷（都不是编译错误，全是"静默错"）★

#### 1. `Selection::setFromPath()` 在新文档上静默失效

`setFromPath()` / `applyPath()` / `selectRect()` / `selectEllipse()` 内部都需要一份
**"尺寸参考"蒙版**（要从 `QPainterPath` 反推画布尺寸是不可能的），
`m_mask.isNull()` 时它们**直接 return，一个标志位都不改**。

后果：在刚打开的图片上第一次拉选区，**完全没有反应**，无报错、无日志。

修法：新增 `Selection::prepareCanvas(QSize)`，在 `mousePress` 时调用。
底色填 **255（全选）** 而非 0 —— 这样 Add/Subtract/Intersect 在"原本没有选区"时
语义才正确（全选里减去一个框 = 挖洞，而不是"什么都没有"）。
且**刻意不动 `m_active`**：全 255 等价于"无选区限制"，保持 `isActive()==false`
才能让所有工具继续走"跳过蒙版乘法"的快路径。

#### 2. ★ 羽化半径口径错了 3 倍 ★（历史遗留 bug，被新测试揪出）

`Selection::feather()` 里原来内联的三次盒式模糊，把用户给的 `radius`
**直接当作每一趟的半径**。三趟串联 → 实际扩散 ≈ 3 × 标称值。

- 用户填"羽化 4 像素"→ 实际得到 12 像素的模糊，选区硬边彻底消失
- 不报错、不崩溃，只表现为"羽化好像比数字厉害得多"

同工程的 `tripleBoxBlur()` 注释里其实写明了"直接用传入的 radius 除以 3
作为每次的半径"—— **羽化这条路从来没除过**。

修法：在抽出来的 `featherGrayMask()` 里改成 `perPass = qMax(1, qRound(radius/3.0))`。
测试用两条断言把这个口径钉死：标称 6px → 距边界 3px 处应被染到、
距边界 8px 处应仍为 0。改回旧写法会立刻失败。

> 附带把这七十行模糊代码从 `Selection.cpp` 搬到了 `engine/Filters.cpp`：
> ① `Selection` 只该管状态标志与包围盒缓存，模糊是无副作用纯函数，本就属于 engine；
> ② 选区工具需要"先羽化形状、再合入"，得复用同一份实现，否则两处的模糊参数会漂移；
> ③ `engine/boxBlur` 是 ARGB32 专用的（内部转预乘 + QRgb 逐像素），
>    喂灰度蒙版会付出 4 倍内存和两次格式转换，所以必须是单通道的独立实现。

#### 3. `Selection::isAllSelected()` 恒定返回 false

原实现 `return m_active && m_allSelected;`。但这两个标志只有两种合法组合：
`(false, true)` = 全选、`(true, false)` = 有选区 —— **"同时为 true"永远不会出现**。
于是这个访问器恒为 false，即"明明处于全选却被告知不是全选"。

不会立刻炸（现有调用点都同时在判 `isActive()`），但任何按字面意思使用它的人
都会拿到与预期相反的分支。改成 `return m_allSelected;`（等价于 `!m_active`）。

### 关键设计决定

**拖动期间完全不碰 Document。** 画笔是"拖动即写位图"，选区不能照抄：
① 每次 `mouseMove` 都更新蒙版 → 撤销栈里躺着上百条命令；
② 蒙版是画布尺寸（12MB），一次布尔运算遍历 1200 万像素，每秒 60~120 次移动根本算不过来。
所以拖动只维护 `m_previewRect` + `paintOverlay` 画虚线框；松手才渲蒙版、羽化、合入，
包成**一条** `SelectionCommand`。附带好处：**Esc 取消是免费的**（没改过文档，丢掉预览矩形即可）。

**修饰键分两阶段解释**（对齐 Photoshop）：按下瞬间的 Shift/Alt 决定运算方式
（添加/减去/交集），拖动过程中的 Shift/Alt 决定几何约束（正方形/以起点为中心）。
必须分两阶段，因为"想画正方形"和"想追加到选区"这两种意图只能靠"什么时候按的"区分。

**蚂蚁线的轮廓提取不能用 `QRegion::addRegion()`。** `QRegion` 的矩形是**逐扫描行**的，
直接 addRegion 会把选区内部每一行的水平线都画出来（一片横条纹）。
改成逐像素找"内/外交界"、把连续段**合并成一条线段**（双向扫描，横向找上下边界、
纵向找左右边界）。合并成段还顺带解决虚线问题：Qt 的虚线图案**按子路径分别起算**，
子路径只有 1 像素长的话虚线会在每个像素处重启，看着像实线。

**蚂蚁线的性能三件事**：① 轮廓路径必须缓存（提取要几趟全图扫描，几十毫秒，
不能放进 paintEvent）；② 只扫描选区包围盒（`Selection::bounds()` 自带缓存）；
③ 动画定时器随选区开关，且每帧**只重绘轮廓外接矩形**而非整块画布。

**M 键轮换放在 MainWindow 而不是 ToolManager**：`ToolManager::findByShortcut()`
是"按 key 查工具、命中第一个就返回"，表达不了"一个键对应两个工具"。
只给矩形选框绑 M，椭圆返回 0，轮换逻辑在 `MainWindow::activateToolByShortcut()`——
那描述的是"用户按键习惯"，属于界面策略。

## 预览机制

拖动参数时在**降采样副本**（最长边 1024）上运算，结果交给 `CanvasView`
作为**临时呈现图**（`m_previewImage`）。文档全程不被修改，取消零成本；
确定时在同一条 `apply()` 上跑全尺寸并压**一条** `ImageCommand`。

**对话框不认识 `Document`** —— 子类只实现 `virtual QImage apply(const QImage&) const`，
由 `MainWindow::runAdjustment` 负责接入文档/撤销栈/画布。预览与提交共用同一
代码路径，保证「所见即所得」。

混合逻辑从 `blendWithSelection` 下沉为纯函数 `blendByMask(before, after, mask, maskBounds)`，
让预览（缩采样蒙版）与最终提交（原蒙版）共用 —— 避免「预览有选区效果、确定后没有」。

## ★★ 发现并修复：LUT「通道广播」严重 bug ★★

### 症状

`ui_smoke_test` 报：`BrightnessContrastDialog::apply()` 在**默认参数**（亮度 0、
对比度 0）下把彩色像素 `(128, 96, 64, 255)` 变成了 `(128, 128, 128, 255)`。

### 根因（在 `engine/Lut.cpp`，不在对话框）

`applyLuts()` 里有一条按单表优化的分支，判据是 `ChannelLuts::isMonochrome()`，
含义是**三条曲线长得一样**（`lutR(x) == lutG(x) == lutB(x)`）。
但实现时被误解成「**像素的 R/G/B 三个分量一样**」，写成：

```cpp
if (mono) { const int v = lutR[ir]; r = g = b = v; }   // 只查红通道再广播
```

两件事毫无关系。任何 `R≠G≠B` 的像素，其 G/B 都被红通道的结果覆盖 ——
**用户拉一下亮度滑块，彩色照片整体变成"用红通道值渲染"的单色图。**

潜藏至今是两个巧合叠加：

1. `applyLutRgb()` 构造的 `ChannelLuts` **天然**满足 `isMonochrome()`，
   所以这条错误分支覆盖了亮度/对比度/RGB 主曲线的**全部调用**；
2. 之前所有 LUT 断言用的都是**灰度像素**。灰度图上「各查各的」与
   「查一个再广播」结果完全相同，**根本测不出来**。

（验算：`ir = qRed(128,96,64) = 128` → `lutR[128] = 128` → 广播得 `(128,128,128)`，
与实际观测逐位吻合。）

### 修法

把判断**提到循环外**，只让 `lutG`/`lutB` **指向同一张表**
（省的是 256 字节表的 cache 占用，**不是**查表次数），
三个通道**始终用各自的输入值**查表：

```cpp
const bool mono = luts.isMonochrome();
const quint8 *lutR = luts.r.data();
const quint8 *lutG = mono ? lutR : luts.g.data();
const quint8 *lutB = mono ? lutR : luts.b.data();
// 循环内（预乘/非预乘两个分支统一）：
r = lutR[...]; g = lutG[...]; b = lutB[...];
```

顺带把循环内的 `if (mono)` 分支彻底消掉。

### 补的测试

`adjust_test.cpp` 新增 1.7 节共 **13 条彩色像素断言**：恒等表下彩色像素逐位不变、

## 三个 bug，只有一个是真的"看得见"

### ① `drawComposite()` 视图变换被施加两遍 ★ 真正的元凶 ★

`paintEvent` 第 2 步已把 painter 变换设成 `m_viewTransform`，并约定
「第 3~9 步全部用图像坐标书写」。但 `drawComposite()` 先把目标矩形手工
`m_viewTransform.mapRect()` 成屏幕坐标，再交给这个**已被变换过**的 painter：

```
T(p) = M(M(p)) = offset·(1 + zoom) + zoom² · p
```

**为什么之前 25 条断言全绿也没发现**：它们全是「矩阵把图像映射到哪」的
数学断言。而这是**渲染**层的错误，数学完全正确。

**发现方式**：给 `view_test` 加第 7 组「渲染占位」断言 —— 图层填纯红标记图，
`cv.grab()` 走完整 `paintEvent`，再从结果里量红色区域的包围盒。
第一次跑就精确命中：

```
期望图像矩形 x=10.0 y=45.6 w=1260.0 h=708.8
实测红色包围盒 x=13   y=61   w= 414   h= 232
414/1260 = 0.3286 = zoom        (13,61) ≈ (10,45.6)×1.328
```

这两个数字就是 `M·M` 的指纹。修法：`painter.drawImage(QRectF(srcAligned), ...)`
（用图像坐标），删掉手工 `mapRect`。

**难认之处**：棋盘格与边框都是先 `resetTransform()` 再按屏幕坐标画的，
**它们是对的** → 屏幕上是「正确的取景框 + 里面缩成一小块的图像」，
看起来像"图像尺寸算错了"。而且 `zoom→1` 时 `zoom²→zoom`、
`offset·(1+zoom)→2·offset`，100% 附近几乎看不出来。

### ② `rebuildViewTransform()`：translate 必须在 scale 之前

`t.scale(z); t.translate(o)` 的 `map(0,0)` 实测 `(5,20)`，`m_offset` 被 zoom 乘一遍。
QTransform 是**右乘**：后调用的**最先**作用于点。
修正为「translate → scale → 翻转 → 旋转」（从外到内）。

### ③ `setZoomAt()`：锚点缩放混用坐标系 + 乘法方向反了

锚点缩放必须在**控件空间**做：`m_viewTransform = m_viewTransform * a`
（`X * Y` 表示**先 X 后 Y**）。写成 `a * m_viewTransform` 会把 anchor 当成
图像坐标，实测 offset 从 `(-62.5, 7.0)` 漂到 `(-14.66, 29.21)`。

### ④ 启动 fit 偏差（顺手修）

主窗口构造顺序是「先建文档 → 再 show()」，`setDocument` 时控件还是默认
640×480，算出 16% 的 fit。先试 `m_pendingFit` 标志被 `show()` 自身的
resize 提前消耗，改成语义更稳的 **`m_userAdjustedView` 模式**：
- `zoomToFit()` 末尾置 `false`（"适合窗口"是一个**模式**，可随时经菜单重入）

# 色阶（Levels）对话框 —— 调整菜单补齐

新增 `src/ui/LevelsWidget.{h,cpp}` + `src/ui/LevelsDialog.{h,cpp}`，
菜单「调整 → 色阶」`Ctrl+L`（PS 约定，已核对全部快捷键确认空闲）。
引擎侧 `adjust::levelsLut` / `computeAutoLevels` / `Histogram` 早已就绪，本轮只补 UI。

## 三个设计决定

1. **灰点（gamma）手柄的位置由烘焙表反查，不另算一遍。**
   把输出范围固定成 0..255、交给 `adjust::levelsLut()` 烘焙，再查
   "输出首次达到 128 的输入值"。这与 `CurveEditor` 用 `m_bakedLut` 画曲线
   是同一条铁律 —— 手柄画在哪与实际映射永远同源。
   反解用闭式 `γ = ln t / ln 0.5`（与 `qPow(clamped, 1.0/gamma)` 互逆），
   并钳到 `[0.1, 10]`。**拖动期间直接用目标坐标定位**：反解被钳制后若再
   "正查位置"，手柄会在边缘往回跳一格，手感像卡住。

2. **「自动」只接管输入黑白场**，绝不整份覆盖。
   `computeAutoLevels()` 返回的是一份完整参数（gamma=1、输出 0..255），
   整份覆盖会把用户手工调好的 gamma 静默重置 —— 那是"按了自动画面反而变了"
   的经典来源。已用断言钉死：设 gamma=1.8 后点自动，必须还是 1.8。

3. **手柄行走"按比例分配高度"而不是固定像素累加**。
   固定像素在对话框被拉矮时会让最下面一行跑到控件外（看不见但还能点到）。
   同时 `setMinimumSize()` 兜底，防止手柄行退化成 0 高。

## 测试（新增 72 项）

  关键断言是**用真实 `QMouseEvent` 拖动中灰手柄**后检查
  "在原位按下 gamma 基本不变" —— 这条把"正查位置"与"反解 gamma"的
  互逆性钉住了，任一侧写错（例如把 1/γ 当 γ 用）会立刻失败。

## ★ 本轮踩到的两个真坑 ★

1. **同一文件的多个 `Edit` 并行执行会互相覆盖。**
   我在一条消息里发了两个针对 `MainWindow.h` 的编辑，结果只保留了后一个：

`resampleMethodName()` 定义在 `ImageTypes.cpp`，但 SOURCES 里没有它。

### 2. `rotatedBoundsSize()` 直角多 1 像素 ★ 引擎真 bug ★

`cos(90°)` 在 double 下 = `6.1e-17` 而非 0，`newW = W·|cos| + H·|sin|` 得到
比整数略大的值，`ceil()` 就多进 1。100×50 转 90° 得到 **51×100**。
修法：直角（`isRightAngle`）先精确处理、直接互换宽高；非直角 `ceil(x - 1e-9)`。
这条 bug 是 `geometry_test` [6]「转四次逐像素回到原图」抓出来的。

### 3. Qt5 `QDialogButtonBox::button(Reset)` 对自定义按钮返回空

`addButton(text, ResetRole)` 加进去的按钮，用
`button(QDialogButtonBox::Reset)` 取不到（返回 nullptr）。必须
`setObjectName("buttonReset")` + `findChild<QPushButton*>()`。
`ui_smoke_test` 一开始就报"复位按钮不存在"。

### 4. `CanvasSizeDialog::infoText` 的面积阈值吞掉了小画布的变化

原按 `|Δ面积| > 0.05 MP` 判断"画布扩大/缩小"，60×60 → 180×140
（面积从 0.0036 涨到 0.025 MP）变化量太小被吞掉，信息面板什么都不报。
→ 改用**百分比**（> 0.5% 才报），与画布绝对尺寸无关。

另：`QPainterPath(oldR)` 这种构造**不存在**（QPainterPath 没有 QRectF
构造），需 `path.addRect(r)`。三处因此报 C2440。

## ★ 续：真实运行截图时又揪出一个"画面错、数学对"的 bug ★

尺寸对话框代码与测试都绿了之后，用 `.buildlog/shot/` 的一次性截图工具
（走产品菜单动作 `actionImageSize` / `actionCanvasSize`，不碰任何测试替身）
截真实运行图做人工确认，结果**画布大小示意图整个是错的**。

### 症状

内容色块（应为"旧画布范围"大小）铺满了整块新画布，而"将被裁内容"的深红
块从画布四周溢出 —— 画面上是"红底上一个蓝框"，与真实情况（放大 30%、
什么都裁不到）完全相反。信息面板的文案、`contentOffset()` 与引擎的对账
**全都是对的**。

### 根因（`CanvasSizeDialog.cpp` 的 `CanvasPreviewWidget::paintEvent`）

```cpp
const QPainterPath contentPath = rectPath(contentInNew);      // ✗ 图像坐标
const QPainterPath contentPath = rectPath(m(contentInNew));   // ✓ 映射到控件坐标
```

`contentInNew` 是**图像坐标**下的矩形（3840×2160）。其余路径
（`newR = m(newRect)`、`oldR = m(oldInNew)`）都做了 `m()` 映射，只有内容
这一处漏了 —— 于是 3840×2160 的矩形按"控件像素"解释，直接盖住整个控件：

- `内容 ∩ 画布` 退化成整块画布（蓝铺满）
- `内容 − 画布` 退化成画布以外的全部区域（红溢出）
- 虚线用的是映射值，**看起来还是对的** —— 这就是它伪装得好的原因

### 定位手法（值得复用）

"数学断言全绿"时不要继续读代码猜，**让绘制函数把中间量打出来**：
临时在 `paintEvent` 里 `fprintf` 出 `widget 尺寸 / world / s / newR / oldR /
contentR`（映射后的值），重编截图工具跑一次，一眼就看到 `contentR` 与
`newR` 的关系。打完立刻撤掉（不要留在产品代码里）。

### 修法与守门

修完顺手把**绘制顺序**也定了：底色 → 旧画布"将被移除"区 → 内容 →
**原画布虚线** → 新画布边框。虚线原本画在内容之前，而内容包围盒常常
就等于整幅旧画布，于是虚线被蓝色实心块**整条埋掉**（图例写着"虚线 =
原画布范围"，图上一条都找不到）。
